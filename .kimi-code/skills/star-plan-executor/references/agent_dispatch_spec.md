# Agent Dispatch Brief

Delegate whenever collaboration tools are available and the work is bounded, independent, and materially benefits from a separate context or parallel execution. When delegating, dispatch a writing sub-agent on the EXEC tier's model — or the pool alias binding its configured depth — (conventions §10.8), where the harness can name one; use a read-only sub-agent, on the READ tier's model or its depth binding, only for a read-only orientation scope. With a tier's key empty the dispatch names no model at all. Execute locally when a step is small, sequential, tightly coupled to current edits, or likely to cause overlapping file ownership. Do not create one subagent per trivial action.

**Use one tier for implementation.** All implementing delegates use EXEC, including template edits, renames and formatting. READ is for read-only collection or orientation; PLAN is for independent design judgment. The phase owner performs sequential work locally; an EXEC phase delegate does not pass the same serial work to another EXEC delegate. Independent scopes may be delegated when the benefit warrants it. Empty or unavailable tier overrides follow conventions §10.8 and §13 without changing the task or its write limits.

**A coherent scope** follows one recorded work unit from EXEC_PLAN (conventions §1): one action or adjacent related actions with a shared final check. When per-action commits were chosen, each action is its own unit; the phase owner executes dependent actions locally and commits their verified states in order. Independent actions with disjoint files may still be delegated. Preserve any broader integration check before completion. Dispatch it once with the member action numbers and their checks, splitting at every STOP-line boundary. Verify returned evidence per action and keep one EXEC_LOG row per member; an incomplete return never completes unverified members or the unit.

**Delegation order and concurrency follow dependencies.** The phase owner executes dependent actions locally and may delegate independent scopes with disjoint files (conventions §6.2). It is the sole writer of EXEC_LOG, records each verified action immediately, and commits at the recorded granularity under conventions §1: grouped commits wait for every member check and the final check; a per-action choice gates each commit on that action's check and retains later integration checks. A worker returns evidence and never writes the shared log or makes the unit commit.

**Before delegating**, capture the action-start state and establish file ownership. A unit may contain earlier verified but uncommitted changes from this run; preserve them in the snapshot and dispatch brief. Name any changes already present when the run started or subsequently made by the user, exclude them from restores and staging, and never dispatch overlapping writers. Resolve uncertain ownership before dependent edits. The same snapshot discipline applies to local execution.

## What to give the agent

- **Scope** — one work unit from EXEC_PLAN, its member action numbers, each action's check and the unit's final check. State: "Do only this scope; do not continue into other units."
- **What it may write** — and nothing outside it: the exact files/modules to create or modify under `${CODE_NAME}/` (from the gap list); artifacts under `wkdrs/<run>/`; intermediate working files under `tasks/<plan-name>/`, never another plan's; and, for a STOP-line step only, the prepared launch script `execs/scpts/<run>.sh` — writing it is light, running it is not (`stop_line_rules.md`). Match existing code style and touch only what this step needs (AGENTS.md §3, surgical changes).
- **Context** — the relevant raw plan section, gap-list facts, and existing interfaces. Do not leak an intended answer when the delegate is being used for independent validation.
- **Runtime** — the absolute interpreter path the main agent already resolved, given verbatim. The agent does not re-read `.env`: its working directory may not be the project root. A missing package is a blocker it returns, never something it installs (conventions §3.5).
- **Boundary** — it may run **light validation only**. If its step is on the STOP line, it must **prepare the command and return it, NOT run it** (`stop_line_rules.md`).

## What the agent must return (structured)

- `changed` — files created/modified, one line each.
- `ran` — commands actually run + outcome, or `none`.
- `check` — `pass` / `fail` plus exact command/result evidence per member action and for the unit's final check; identify unfinished members.
- `blockers` — anything that stopped it, or `none`.
- `handoff` — any STOP-line command prepared for the user, or `none`.
- `model` — the model id the delegate's own runtime reports for its session (conventions §8), copied verbatim, or `unrecorded`.

## After the agent returns

The main agent reviews the diff and verifies the action's check before recording the result in EXEC_LOG. It may use the original execution as final evidence when it can inspect the exact command, exit/result, raw log or artifact, and the corresponding code version (commit, or a recorded dirty-tree diff); a delegate's summary or self-reported pass alone is never evidence. Re-run the narrow check when those inputs are missing or stale, and always after integration changes behavior, dependencies, or the checked code. Routine integration conflicts may be resolved only when existing implementation/integration authorization applies and the intended combined result is mechanically unambiguous; inspect the combined diff and re-run affected checks. A conflict that chooses between user changes, research intent, scope, or acceptance returns for direction, and `auto=unattended` alone grants no conflict resolution.

- Pass → mark the action `done` with artifact and check evidence.
- Fail → record the failure in EXEC_LOG, preserving the exact command, raw failure output, and code version, then restore this action's files before retrying — minus anything named pre-existing. Restore to the per-action snapshot of how the tree stood when this action began, not to `HEAD`: grouped commits may leave earlier verified actions uncommitted, as can a decision to decline commits, so resetting to `HEAD` would erase work EXEC_LOG already records as `done`. A restore never touches files outside this action's own, user edits made after the snapshot, or raw logs/results kept as evidence; a retry that would overwrite such evidence uses a new output path or gets specific overwrite authorization. Retry only when a concrete correction is available, at most twice. Otherwise the action is `blocked`: use an existing applicable user decision about its action-owned edits rather than asking again; absent one, ask before restoring them (conventions §7.7 — it stops for confirmation before a deletion), record which way it went, name the paths either way, and stop. Under `auto=unattended`, restoration is allowed only for the action-owned delta proven by its snapshot; ambiguity about ownership stops. No action ends leaving edits nobody has accounted for.
- Handoff → record the command under `Awaiting user` and return without running it. The main run applies `stop_line_rules.md`: a specifically authorized ordinary launch or the outer `star-auto` launcher may run it after the current review and cost guards pass; otherwise it stays with the user.
