# 勘察规范

只读侦察：把代码库变成一份架构设计（Step C1）值得信赖的**仓库地图**。勘察者绝不修改任何文件。

## 分组

一条关注点一个 subagent，最多 3 个并行（它们不写任何别的勘察者会写的文件，所以这里并行是安全的——但并非一概安全：会抓取远端的 fan-out 共用同一份按 host 的预算，规约 §6.9）：

| 分组 | 看什么 | 关键问题 |
|---|---|---|
| 结构与依赖 | 顶层目录、包布局、内部 import | 有哪些模块？import 朝哪个方向流动？有环吗？ |
| 配置系统 | 配置文件/目录、注册表机制、CLI 参数解析 | 一个实验怎么指定？走注册表还是普通 import？ |
| 数据管线 | dataset 类、transforms、loader、下载脚本 | 数据集从哪接入？有硬编码路径吗？ |
| 训练/评估入口 | train/test 脚本、engine、循环、调度器 | 启动方式是什么？单入口还是多入口？ |
| 脚本与工具 | tools/、scripts/、shell 文件、notebook | 哪些是必需的，哪些是一次性杂物？ |
| 测试与文档 | tests/、CI 配置、docs/ | 覆盖了什么？哪些能当快速验证套件用？ |

**轻量模式**（不到约 50 个 Python 文件的仓库——只看体量；新克隆动辄是这个数的 3–12 倍，所以来源不是判据）：把各组合并成一次扫描——由一个 subagent 或主 agent 自己完成。

## 每个勘察者的格式约定

- **范围**：只看自己这一组，只读；"不得修改、创建或删除任何文件。"
- **返回**（结构化）：
  - `inventory`——本组的目录/模块，每项一行：路径 + 职责。
  - `entrypoints`——发现的可运行入口（脚本、CLI 命令），在范围内时提供。
  - `mechanisms`——这一组怎么运作（配置风格、注册表用法、数据流向），3–6 条要点。
  - `smells`——只报可能促成迁移项的发现：死代码、重复、跨层 import、命名不一致、巨型文件。每条：路径 + 一行证据。
  - `unknowns`——没弄清的事及原因。

## 汇成仓库地图

主 agent 把各组报告汇成一份仓库地图：

1. **模块清单**——带注释的目录树，每个顶层目录一行职责。
2. **依赖方向**——哪些层 import 哪些层；标出越界之处。
3. **对可疑写法排序**——跨组去重，按"对计划工作的阻碍程度"排序；只保留值得立迁移项的。其余记为 `codearc.md` §3 的风格备注，不立迁移项。

   一条排过序的 smell，只有在主 agent 回到它标注的路径、按它给的证据重开确认这个发现仍然成立之后，才能变成一条编号的迁移项（conventions §6.6）。站不住的就丢掉，或降格成写进 `codearc.md` §3 的一条风格备注。确认时用的那个 `path:line` 写进迁移表的理由列——这是本 skill 里唯一一条通道：没有它，一条未经核实的受托者断言会穿过用户确认点，然后真的把文件搬走。

仓库地图直接输入给 Step C1，对用户只做摘要展示（不整篇倾倒）。
