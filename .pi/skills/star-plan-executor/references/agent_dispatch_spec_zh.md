# Agent 交办说明（Pi——本地履行）

仅当协作工具可用，且工作边界明确、相互独立、确实能从独立上下文或并行执行中获益时才委派。委派时调用你的子代理工具，实现工作使用可写子代理、跑在 EXEC 档的模型上（规约 §10.8，前提是这个宿主能指定受托者用哪个模型）；只有只读勘察范围使用只读子代理，跑在 READ 档的模型上。哪一档的键为空，那一档的派发就不指定模型。步骤很小、严格串行、与当前改动紧耦合或容易产生文件冲突时，由主 agent 本地完成。不要给每个琐碎动作都创建一个 subagent。

**实现统一使用一个档位。** 所有实现受托者都使用 EXEC，包括模板编辑、重命名和格式化。READ 用于只读收集或勘察，PLAN 用于独立的设计判断。执行阶段负责人在本地完成串行动作；接手该阶段的 EXEC 子代理不再把同一批串行工作转交另一个 EXEC 子代理。独立范围有明确收益时可以委派。档位为空或不可用时按规约 §10.8（模型选择）和 §13（宿主参数）处理，任务及写入边界不变。

**连贯范围**对应 EXEC_PLAN 中一个已记录的工作单元（规约 §1，提交范围）：一个动作，或有共同最终检查的几个相邻、相关动作。已有逐动作提交选择时，每个动作单独成为一个单元；阶段负责人在本地执行相互依赖的动作，按顺序提交各自已验证的状态。文件互不重叠的独立动作仍可委派。更大范围的集成检查仍须在完成判定前通过。委派一次时写明成员动作编号及各自检查，遇到红线边界就拆开。逐动作核对返回证据，每个成员在 EXEC_LOG 中各占一行；返回不完整时，不得把未验证的成员或整个单元记为完成。

**委派顺序与并发遵循依赖。** 执行阶段负责人在本地完成相互依赖的动作，可把文件互不重叠的独立范围委派出去（规约 §6.2，文件归属）。EXEC_LOG 只由该负责人写入：每个动作验证后立即记录，按规约 §1（提交粒度）和已记录选择提交：合并提交一个单元时，等待全部成员检查和最终检查通过；逐动作提交时，使用该动作自身的检查，后续集成检查仍须完成。工作子代理只返回证据，不写共享日志，也不替负责人提交该单元。

**委派之前**，保存动作开始时的状态并明确文件归属。同一单元可能包含本轮此前已验证、尚未提交的改动；快照和交办说明必须保留它们。运行前已存在或用户后来写入的改动需点名保护，不纳入恢复或暂存；不得派出文件重叠的并发写入者。归属不清时，先解决归属再继续依赖它的编辑。本地执行也遵守相同的快照规则。

## 交给 agent 什么

下面这些就是派发时写明、并由受派方在这一步全程照着守的条款:

- **范围**——EXEC_PLAN 中一个工作单元、成员动作编号、各动作的检查及单元最终检查。明确写：「只做这个范围，不要继续其他工作单元。」
- **可写文件范围**——此外一律不碰:`${CODE_NAME}/` 下要新建或修改的确切文件/模块(取自缺口清单);`wkdrs/<run>/` 下的产物;`tasks/<plan-name>/` 下的中间文件,绝不碰别的计划的;以及仅限红线步骤的那份备用启动脚本 `execs/scpts/<run>.sh`——写它是轻的,跑它不是(`stop_line_rules_zh.md`)。匹配既有代码风格,只碰这一步需要的地方(AGENTS.md §3,精准克制的修改)。
- **上下文**——相关的原始计划章节、缺口清单事实和现有接口。若委派用于独立验证，不要泄露预期答案。
- **运行环境**——Step 2 已经解析好的解释器绝对路径,逐字使用。不要每一步都回头读 `.env`:工作目录未必是项目根。缺包是它要返回的 blocker,绝不是它自己去装的东西(规约 §3.5)。
- **边界**——一个步骤**只能跑轻量验证**。落在红线上的步骤,**备好命令交回,不要跑**(`stop_line_rules_zh.md`)。

## agent 必须返回什么（记进日志）

- `changed`——新建/修改的文件,每个一行。
- `ran`——实际跑过的命令 + 结果,或 `none`。
- `check`——每个成员动作及单元最终检查的 `pass` / `fail`、确切命令与结果证据，并点明未完成的成员。
- `blockers`——让它停下的东西,或 `none`。
- `handoff`——为用户备好的任何红线命令,或 `none`。
- `model`——受托者自己的运行时为其会话报出的模型 id(规约 §8),原样抄录,或 `unrecorded`。

## agent 返回后

主 agent 必须审查 diff，并在写入 EXEC_LOG 前核验本 action 绑定的检查。能够检查确切命令、退出状态/结果、原始日志或产物、以及对应代码版本（commit，或记录在案的脏树 diff）时，可以直接采用原次执行作为最终证据；受托者的摘要或自报通过本身绝不是证据。缺少这些输入、证据已过期时重跑最窄检查；整合改变了行为、依赖或被检代码后始终重跑受影响检查。已有实现/整合授权、预期组合结果在机械上没有歧义时，可以处理常规整合冲突；检查组合后的 diff 并重跑受影响检查。若冲突要求在用户改动、研究意图、范围或验收之间取舍，就交回用户定方向；单凭 `auto=unattended` 不取得冲突消解权。

- 通过 → 记录产物与检查证据，将动作标为 `done`。
- 失败 → 把失败记进 EXEC_LOG，保留确切命令、原始失败输出和代码版本；重试前先恢复这个 action 的文件——已点明的既有改动除外。恢复到这个 action 开始时的逐 action 快照，而不是 `HEAD`：按单元提交或选择不提交时，更早的已验证 action 可能仍未提交，重置到 `HEAD` 会把 EXEC_LOG 已经记为 `done` 的工作一并抹掉。恢复绝不碰本 action 之外的文件、快照之后的用户编辑、或作为证据保留的原始日志/结果；重试会覆盖这类证据时，改用新输出路径，或取得具体覆盖授权。只有存在具体修正方案时才重试，最多两次。否则该 action 标 `blocked`：已有适用的用户决定说明怎样处理 action 自有编辑时直接沿用，不再问一遍；没有时，恢复前先问（规约 §7.7——这是把关删除的），无论哪种选择都记下来并点名路径，然后停止。`auto=unattended` 下只可恢复快照能证明归本 action 所有的增量；归属有歧义就停止。没有哪个 action 可以留下无人认领的改动。
- 有 handoff → 记入「待用户执行」，不运行并返回。主运行随后按 `stop_line_rules_zh.md` 处理：有具体授权的普通启动，或外层 `star-auto` 启动器，只有当前审查与成本守卫通过后才可运行；否则继续交给用户。
