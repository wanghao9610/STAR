An optional `involve=low|medium|high` token may accompany `PLAN_NAME` (e.g. `… involve=low`): it sets the `involve` level for this run (conventions §7.7), belongs to neither `PLAN_NAME` nor the description, and is stripped before either is read.

## Role

You drive a **leaf execution sub-plan** to its done-criterion by changing code and running light validation. Upstream, `star-plan-decomposer` produces the executable sub-plan (§1 objective / §2 inputs & deps / §3 task breakdown / §4 deliverables / §5 done-criteria / §6 local risks); this skill produces the **result**: code under `${CODE_NAME}/`, intermediate working files under `tasks/<plan-name>/`, generated artifacts and durable execution records under `wkdrs/<run>/`, and a verified done-criterion. Derive `<plan-name>` from the selected plan filename by removing `_plan.md`.

You **execute; you do not re-plan the research or re-decompose.** If §3 or §5 is too vague to execute, send the user back to `star-plan-decomposer`.

## Core Principles

1. **Read before you write.** Before planning any change, orient in `${CODE_NAME}/`: read the modules/entrypoints the sub-plan's §2 names, and produce a "current state vs §3 requirements" gap list. Never assume code exists; `code/` may be an empty codebase (only `.gitkeep`), where the plan builds the structure from scratch — or, better, starts from a reference codebase first via `/star-code-architect`. Reference: `references/orient_checklist.md`.
2. **Plan behind a confirmation point, execute behind an agent.** The executable plan (EXEC_PLAN) must be **user-approved** before anything is written or run. `/star-plan` is the user's switch, not a tool this agent can reach, so Step 3 stays the mode this skill imposes on itself: from the moment it starts until that approval arrives, nothing is written and nothing is run. Execution goes to `star_subagent` (`agent: "star-implementer"`), **one per step / step-group**: the main agent orchestrates and verifies each before starting the next. Reference: `references/agent_dispatch_spec.md`.
3. **Stop before heavy experiments.** Agents write code and run **light validation only** (runnable checks, small-scale / no-finetune checks like an MVP done-criterion). Before any long/multi-GPU training run or costly API call, **stop**: write the prepared command into EXEC_LOG's "Awaiting user" area and hand it back. Rules: `references/stop_line_rules.md`.
4. **Files are the source of truth; record every step — and keep the sub-plan true.** Execution state lives in `wkdrs/<run>/` (`EXEC_PLAN.md` + `EXEC_LOG.md`), intermediate working files in `tasks/<plan-name>/`. Update the log after each verified step. The sub-plan gets a lightweight `exec_status` + `exec_runs` pointer — plus, where execution provably diverges from it, or settles a value it left open that a method document will cite, a **user-confirmed write-back** of the affected §2–§5 content and a `## Revision History` entry (`references/plan_sync_rules.md`), so the plan a user rereads later matches what was executed.
5. **Every step ends in a check; the run ends in the done-criterion.** Verify each step narrowly before dispatching the next; the run finishes on the sub-plan's §5 done-criterion. Reuse the project's `/verify` and `/run` skills where useful. This is Goal-Driven Execution (AGENTS.md §4) and Verification (§11), executed.
6. **Use the project runtime and launch entry point.** Invoke run commands through the project's run entrypoint `execs/run.sh` where one exists. Create `tasks/<plan-name>/` for this plan's intermediate files, and put reusable launch scripts, including prepared STOP-line commands, under `execs/scpts/<run>.sh`.

## Workflow

### Step 0: Resolve the target plan

1. Interpret `PLAN_NAME` (slug / numeric prefix / full filename) against the plans the opening load's digest lists; it is the listing, so do not list the directory again.
2. **Only leaves are executable.** If `PLAN_NAME` resolves to a node with children (non-empty `children:` frontmatter), do not execute it: list its leaves (prefix + slug + one-line objective) and ask which to execute (recommend the first ready in dependency order), or offer to execute them in dependency order, one at a time.
3. If no argument was given or the match is ambiguous, list available plans and ask.
4. Read the resolved sub-plan in full.

### Step 1: Readiness check

1. **Executability.** §3 Task Breakdown and §5 Done-Criteria must be concrete. If they are still largely `[TBD]` / `【待定】`, say decomposition is unfinished and offer: *go back to `/star-plan-decomposer` to flesh it out* (recommended) / *execute anyway (shallow, gaps stay `[TBD]`)*.
2. **Dependencies.** Check §2 Inputs & Dependencies: are the named datasets (`datas/`), weights (`inits/`), and code modules present? Are the upstream sibling leaves in the leaf's `depends_on` frontmatter all `exec_status: done`? Read their state from the digest, which already carries every sibling's frontmatter, rather than opening each one. If a hard dependency is missing, **stop and report** — do not fabricate inputs. A missing dataset or weight is a decomposition gap, not a blocker to work around: name the data-readiness leaf that should own it, or route to `star-plan-decomposer <parent>` to add one.
3. **Not dropped.** A leaf carrying `dropped:`, or with a dropped ancestor, is not executed: name the node the drop was written on and stop. Reviving it starts with clearing that field through `star-plan-reviser` — running a direction the user already decided against spends compute on work nothing will count.
4. **Right-sized.** An executable leaf can still be the wrong unit of work, and nothing re-checks that after the split: the plan may have been decomposed weeks ago, or written by hand. Apply the sizing judgement the decomposer applies to its own drafts — one independently checkable chunk (its `references/subplan_rubric.md`, item 8). Every signal is in the text Step 0 already read, so the check costs no call of its own.

   - **Strong, any one is enough**: §5 states more than one independent check; §3 crosses the STOP line more than once, each hand-back a natural leaf boundary; §3 mixes acquiring data, building code, and running experiments in one unit, where a dataset is owed a leaf of its own.
   - **Weak, two together count as one strong**: §3 runs past 12 steps; §4 spreads over unrelated artifact families or more than one run directory.

A lone weak signal is one sentence in the reply, never a question — interrupting a right-sized leaf costs more than missing an oversized one. Where the check fires, the split preview goes in the text above the call: 2–5 cards, each a slug, a one-line objective, and the done-criterion that unit would own, then the execution order in one line. Name it a preview and say what that means — no file written, no prefix assigned, no `depends_on` drawn, and `star-plan-decomposer` still picks its own axis and confirms its own list. Its cut lines are the signals that fired (one unit per done-criterion, per STOP-line crossing, per kind of work), not a fresh axis analysis. Needing more than 5 cards is itself the finding — say so in a line instead of listing them. Then ask: *split it first* (recommended once a strong signal fired) — the run ends here having written nothing, the command goes back as `/star-plan-decomposer <leaf> <the preview in one clause>` with the sketch carried as a lead (conventions §7.12), and execution resumes at `/star-plan-executor <the leaf it produces>` — or *execute it as it stands*, which costs: every STOP-line crossing stops and resumes the run, one `blocked` step holds up everything behind it, and a failure re-runs the leaf entire. Executing part of the leaf is not offered — narrowing the scope is a decision nobody made (conventions §10.4).

   **Fresh runs only, and asked once.** A leaf whose `exec_runs` is non-empty, or with a run in flight on a branch or worktree, skips this check outright: splitting mid-run leaves that run's `wkdrs/<run>/` hanging off a node no executor revisits — what `star-plan-decomposer` stops to warn about. Where item 1 is already routing back to the decomposer, this rides in that question rather than following it. Record the verdict and the signals in `EXEC_LOG.md`'s "Notes / decisions" when Step 4 creates it (conventions §7.8), so a resume does not reopen it and a later reader knows the leaf was flagged and run anyway.

### Step 2: Orient in the codebase

Follow `references/orient_checklist.md`:

1. Read `.env` and resolve `CODE_NAME`, `CONDA_HOME`, `PYTHON_HOME` (conventions §3). If the environment those paths name is missing or cannot run python, recommend building it with `/star-env-builder` before executing; a package the run needs but the environment lacks is `/star-env-builder add <package>` — this skill installs nothing itself.
2. Map `${CODE_NAME}/`. If empty, declare **empty codebase**.
3. For each §3 step, decide whether the code to do it **exists / needs modifying / needs creating** — this mapping is the **gap list**.

### Step 3: Enter plan mode → produce the executable plan

1. Say in one line that you are drafting the EXEC_PLAN and will write and run nothing until Step 4's approval. `/star-plan` is the user's switch, not a tool you can reach, so this step is the mode, held by you rather than enforced by the host — which is exactly why it is stated out loud.
2. Refine §3 + the gap list into **EXEC_PLAN**: an ordered list of actions, each annotated `{files to touch / command to run (via conda) / artifact under wkdrs/<run>/ / the step's own check}`. The terminal action binds the §5 done-criterion.
3. **Draw the STOP line explicitly** (`references/stop_line_rules.md`): mark which actions the agent executes vs which are "prepare command, hand to user" (heavy experiments). **The finished plan is the second reading of the leaf's size**: if it runs past 12 actions or crosses the STOP line more than once and Step 1's sizing check did not fire, carry that to Step 4's confirmation point as one more option — *go back and split it first*, ending the run before anything is written — rather than as a question of its own.
4. **Collect material divergences** from the sub-plan's §2–§5 into EXEC_PLAN's "Divergences from sub-plan" table, in delta form (ADDED / MODIFIED / REMOVED / ENRICHED — `references/plan_sync_rules.md`). A contradiction at the sub-plan's own granularity is a divergence; extra concreteness is not — except a value the plan left unstated that a method document will cite, an ENRICHED row naming that section.
5. **Settle the branch and worktree lines** (conventions §11): if any EXEC_PLAN action modifies a pre-existing tracked file under `${CODE_NAME}/`, the plan carries `branch: <run>` and recommends executing on it; a plan that only adds new files, or writes only `tasks/<plan-name>/` and `wkdrs/<run>/`, carries `branch: none`. Record the branch the checkout is on as `base:`, whatever its name. The worktree line answers whether this checkout is free right now (§11.7): any busy signal (HEAD on another run's execution branch; uncommitted changes on paths another run's records claim; handed-back commands whose results are not collected — a possible live job, asked about, never checked by a command; or the user naming parallel work) → `worktree: ../<root-dirname>--wt/<run>`, which forces `branch: <run>` even where the gap list said none (§11.8); no signal → `worktree: none`. Signals and procedure: `references/branch_rules.md`.

### Step 4: Confirmation point — the user approves

**Before the call, run the design check.** Send `references/design_check.md` out for a blind read: one read-only `star_subagent` (`agent: "star-auditor"`) briefed with exactly three files — the EXEC_PLAN just written, the leaf sub-plan, and the root plan (name the checklist's `_zh` twin when the plan's frontmatter says `language: zh`; the delegate never picks) — and the scope "ONLY these three files. Do not rank, do not decide, do not run anything." It returns, per item: `item`, `verdict: pass | fail | unclear`, `evidence`, `fix`. The main agent re-opens the cited line for every `fail` it means to raise — an absence `fail` quotes nothing, so for those it re-reads the section the item belongs to — then puts at most five findings on the page **above** the call, one line each; a `fail` it cannot confirm is dropped. The check reports; this confirmation point decides, and nothing here stops the run. Where no delegate is available the main agent runs the checklist itself (conventions §6.1).

1. Present EXEC_PLAN + the changes it will make: files to be written, commands to be run, where the STOP line falls, rough cost/runtime — and the divergence table, stated as "approving this plan also syncs these back into the sub-plan". Ask at the same confirmation point whether each verified step gets its own commit (recommended), naming any path that already carries uncommitted changes — those are never staged. Say what saying no costs: if a later step has to be restored, the only record of where each step started is the one this run keeps itself (`references/agent_dispatch_spec.md`). Where Step 3 set `branch: <run>`, the branch question rides the same confirmation point (conventions §11): name the base branch it forks from, that taking it takes the per-step commits with it — only commits merge — and its one precondition, that nothing is currently running from this checkout; declining executes on the base branch as before. Where Step 3 set `worktree: <path>`, the tree question rides it too (§11.7): name the busy signal that recommends it, the path, the symlinks it will get (`.env`, `datas/`, `inits/`), and that the whole run — commits, records, follow-on skills — then lives in that tree while this checkout stays put; declining executes here, waiting on whatever made the checkout busy. Wait for explicit user approval before anything is written or run.
2. On approval the changes begin — an approved branch first: `git switch -c <run>` from the recorded base, so everything below is born on it — or, where the tree was approved, `git worktree add <path> -b <run> <base>` instead: no checkout switches, the symlinks go in and the `.env` resolution is re-proven, the tree's absolute path lands as `worktree:` in both records, and everything below happens inside the tree (`references/branch_rules.md`) — then create `tasks/<plan-name>/` for intermediate working files. Persist `wkdrs/<run>/EXEC_PLAN.md` from `assets/exec_plan_template.md` and initialize `wkdrs/<run>/EXEC_LOG.md` from `assets/exec_log_template.md`. **Run name = `<prefix>_<slug>`**; append a user-supplied suffix (`_v2`, a date) to distinguish re-runs — never invent timestamps. **Append** the run to the sub-plan's `exec_runs` rather than replacing it: that history lets `/star-expt-analyst aggregate` see every run of this leaf, not only the last. A plan still carrying a single `exec_run:` is migrated here to `exec_runs: [<that run>]` before the new entry is appended.
3. **Sync divergences into the sub-plan.** If the divergence table is non-empty, the approval just given covers it: update the affected §2–§5 passages in place, append a `## Revision History` entry, bump `updated`, and mark each row `synced` (`references/plan_sync_rules.md`).

### Step 5: Execute–verify loop (one step / step-group at a time)

For each step in EXEC_PLAN, in order:

1. Write the step's brief out before touching anything, per `references/agent_dispatch_spec.md`: this step's goal, the exact files to touch, the resolved interpreter path, the step's own check, and "**only** this step; result stated as changed / ran / check / blockers / handoff". The brief is what the delegate is given, and what keeps the step from widening once it is running.
2. With the step's edits made, **run the step's own check as its own command** and read the output (a step is not verified by having been written; nothing counts as a pass without the check's output in front of you). Pass → record it in `EXEC_LOG.md`, update the sub-plan's lightweight status, and — when the confirmation point approved per-step commits — commit this step's files; on an execution branch that commit also stages the run-record updates this step caused, because only commits merge (conventions §11.2). Fail → the check's output is the evidence: read the `file:line` the failure names, and re-read this step's whole diff only when deciding `blocked`, or when the failure looks like a sub-plan-granularity problem (item 4). Restore this step's files before retrying; bounded retry (≤2) with the failure fed back; still failing → mark the step `blocked`, settle what happens to its edits (`agent_dispatch_spec.md`), and stop with the log.
3. **If the step is on the STOP line** (heavy experiment) → do **not** run it; write the prepared command into EXEC_LOG's "Awaiting user" area, add a row to the "Cost" section with its expected cost (GPUs × hours, or call count and spend), and stop, handing it to the user. When the user returns with the result, fill the actual into that row — the only place the root plan's §4 compute budget is reconciled; where the actual cannot be recovered write `unrecorded`, never blank.
4. If a retry or blocker changes the approach at the sub-plan's granularity (a step added/dropped/replaced, a deliverable path or done-criterion shifted), record a delta row under EXEC_LOG's "Pending amendments" and continue — these sync at Step 6, not mid-run.

Keep the main agent's reply concise; details live in the log.

### Step 6: Finalize / done-criterion verification

After all agent steps are `done`, verify the sub-plan's §5 done-criterion (reuse `/verify`, `/run` where useful). Met → set the sub-plan's `exec_status: done`, then offer once to delete the plan's `tasks/<plan-name>/` **scratch** — promote anything worth keeping into `wkdrs/<run>/` first, and record the choice in `EXEC_LOG.md`; keeping it is a fine answer. **The offer never covers the plan's own tool scripts** (conventions §9): list them by name as retained, and delete one only if the user names it. Not met → follow the sub-plan's §6 local fallback, or report the gap. Then run `references/exec_rubric.md` and report failing items (≤5, ranked, each with a concrete fix).

**Amendment sync (tactical signal).** If EXEC_LOG's "Pending amendments" is non-empty, put the batch on the page first — one numbered row per amendment: which section it changes, from what to what, and why — then ask **one** question (*sync all / sync all but the rows I name / answer my questions on the rows I name first / skip*, recommendation marked — conventions §7.13) and write confirmed rows back per `references/plan_sync_rules.md` (§2–§5 updated in place + `## Revision History` entry + `updated` bump, then check the rows off). Tactical only: anything touching §1/§6, a parent plan, or a kill-criterion is a plan-level finding — routed back to the plan below, never synced.

**Route it back to the plan (plan-level finding).** If the result contradicts an assumption the parent plan depends on — i.e. it matches a root §5 **kill-criterion**, or an MVP done-criterion the plan called the "cheap early test" came back negative — you do not edit the parent's §1–§6 (that stays with the coach/decomposer). Instead: record it in the run's `EXEC_LOG.md` "Notes / decisions" (which this skill owns), and in the Step 8 report **point it out explicitly** and recommend feeding it back via `/star-plan-reviser <slug>` (audit the evidence and revise the plan under per-item approval), `/star-plan-coach <slug>` (revisit risks/method), or `/star-plan-decomposer <slug>` (re-scope the sub-plans).

### Step 7: Recorded state & resume rules

- **Source of truth**: `wkdrs/<run>/EXEC_LOG.md` — each step `pending`/`in_progress`/`done`/`blocked` + artifact path + any "Awaiting user" commands.
- The sub-plan frontmatter carries only `exec_status` + `exec_runs` (append-only, newest last; the last entry is the current run).
- On re-invoke, read the run dir and resume from the first unfinished step. If STOP-line commands were awaiting and their outputs now exist, resume at done-criterion verification.
- **The branch is found before the run dir.** A branch `<prefix>_<slug>*` matching the leaf is a run in flight on it, even when the base checkout shows the leaf unexecuted — the base branch is canonical (conventions §11.3). Confirm the working tree carries no unrelated uncommitted changes (name them and wait if it does), `git switch` to the branch, and resume from its `EXEC_LOG.md` as above. A recorded `branch:` that no longer exists is a blocker to report, never re-created silently.
- **A run whose records carry `worktree:` lives there.** Confirm the tree exists (`git worktree list`), resume inside it, and never switch this checkout. A recorded tree gone from disk is the same blocker as a vanished branch: `git worktree prune` clears the stale metadata, and the tree is never rebuilt silently.
- **A review's findings reopen steps.** If the run dir holds a `CODE_REVIEW_<date>.md` carrying blocker or major findings the log does not record as settled, those come before anything else on re-invoke: reopen each step a finding lands in (status back to `in_progress`, the finding's id in its note), or append one remediation step to `EXEC_PLAN.md` where a finding spans several; confirm the batch once, the way Step 4 confirms the plan; then run it through Step 5's execute–verify loop. An awaiting STOP-line command is handed back again only after that. A finding the user decides not to act on is recorded as settled in the log with that decision, so the next re-invoke leaves it alone.
- **On an execution branch, the run ends at the merge confirmation point.** When every step is `done`, the §5 done-criterion holds, and the newest review's blocker/major findings are settled, the one remaining action is the merge (conventions §11.4) — always asked, whatever the involve level. Procedure in `references/branch_rules.md`: squash by default, the base branch merged in first when it moved, the leaf's light checks re-run on the base branch after, the branch's deletion its own question — and the discard path, carrying `wkdrs/<run>/*.md` and the sub-plan's run entry to the base branch before anything is deleted. On a worktree run the squash needs no switch — the main checkout already stands on the base — and the tree is settled after: non-md artifacts moved back first, then `git worktree remove` without `--force`, each its own question (§11.9).
- The write-back applies once: rows marked `synced` (EXEC_PLAN) or checked off ("Pending amendments") are never re-applied; unsynced pending rows are re-offered at Step 6.

### Step 8: Report

What was verified (with evidence), where artifacts live, which commands were handed back to the user, which amendments were synced into the sub-plan, and remaining risks. If Step 6 reported a plan-level finding (a root kill-criterion hit), state it and name the feedback path (`/star-plan-reviser` / `/star-plan-coach` / `/star-plan-decomposer`). Name the review Step 9 is about to start, and where commands were handed back at the STOP line, name it above the awaiting command. Say where the review leads: confirmed blocker/major findings come back through `/star-plan-executor <leaf>`, which reopens the affected steps and verifies them before the command is handed back again — and on an execution branch a clean review leads through it too: re-invoking this skill reaches the merge confirmation point (conventions §11). Name the run's branch and its unmerged state whenever one exists, and the run's worktree path whenever it lives in one — follow-on skills work inside that tree. Where commands were handed back at the STOP line, add that once their outputs exist, `/star-expt-analyst <leaf>` scores the results against the §5 done-criterion and says what they mean. Keep it under ~500 words.

### Step 9: Start the review

**The report is not the end of the turn.** With its text out, start `star-code-reviewer` on this leaf in the same reply — the way this host starts a skill, the leaf as its argument, as ordinary a move as Step 5 taking its next step — to audit the implementation against the conventions and the sub-plan. It is one of the eight skills the agent may start and its target is settled, so it runs rather than prints: `/star-code-reviewer <leaf>` printed to the agent itself is a handoff to nobody (conventions §10.6). This is the run's last action in either ending — after a completed run, before revising or moving on; and before the user runs a command handed back at the STOP line.

1. **An awaiting STOP-line command changes nothing about this.** It stays printed and the user's (conventions §2); standing next to a command only the user may clear does not make the review one of those. Where a run ends with both, starting the review is what makes the report's order real, and what it found is handed back with the command.
2. **One narrow exception, asked once.** An exploratory leaf whose handed-back command is cheap may skip the review and run that command instead — offer it rather than deciding it, with the review recommended, and ask before the review starts. Nothing else on this step is a question: a review costs less than any run it might save.

## State & File Rules

- Intermediate working files live under `tasks/<plan-name>/`; execution state and generated artifacts live under `wkdrs/<run>/`. Never write execution logs into `metds/plans/` — the sub-plan gets only `exec_status` + `exec_runs` + `updated`. `tasks/<plan-name>/` holds this plan's own tool scripts (durable) plus its disposable scratch, whose lifecycle this skill owns: offer its deletion once at finalize when §5 is met, never the scripts (conventions §9). Generated artifacts and durable evidence never live there; never delete it unasked, and never touch another plan's `tasks/` directory.
- Code changes go under `${CODE_NAME}/`; data under `datas/`; weights under `inits/`; run scripts under `execs/scpts/` with `execs/run.sh` as the entrypoint (AGENTS.md §8).
- Never launch heavy or irreversible jobs (long/multi-GPU training, full-dataset eval, costly API) autonomously; those cross the STOP line to the user.
- All run commands go through `.env`'s `CONDA_HOME` / `PYTHON_HOME`; never system python, never hardcoded local paths (AGENTS.md §9).
- Edit the sub-plan's frontmatter (`exec_status`, `exec_runs`, `updated`) freely; edit its §2–§5 **only** through the user-confirmed write-back procedure (`references/plan_sync_rules.md`), always in place and always paired with a `## Revision History` entry. Never rewrite §1 or §6 and never touch a parent plan — objective- or strategy-level divergence goes back through `star-plan-coach` / `star-plan-decomposer` (route it back to the plan).
- Git: one commit per verified step, staging only the files that step touched — plus, on an execution branch, the run-record updates that step caused — and only when the confirmation point covered it; name pre-run dirty paths at the confirmation point (conventions §1). Branch create, merge, and discard happen only at their §11 confirmation points, and worktree create and remove likewise (`references/branch_rules.md`); never rebase an execution branch, never delete one whose records have not first been carried to the base branch, and never `git worktree remove` before the non-md artifacts are moved out — nor ever with `--force`.
- Allowed step status: `pending` / `in_progress` / `done` / `blocked` / `skipped`.

## Dialogue Discipline

- EXEC_PLAN goes to the user through `star_questionnaire` and needs an explicit approval before anything is written or run — still stop before heavy experiments, still confirm before any change is written back into the sub-plan.
- **Material a question is about goes in the text of the same message, above the question** — the pending-amendment batch, the EXEC_PLAN put up for approval. The options carry the answers and none of the material; read the message back before it goes out, since options with nothing above them mean the material was skipped rather than shortened.
- The sub-plan's body language follows its `language`; keep technical terms in English inside Chinese plans.
- Involve (conventions §7.7). Always asked here: the Step 4 confirmation point (including its commit, execution-branch, and worktree questions), the STOP line (Step 5), the merge confirmation point and a branch's or worktree's discard, removal, or deletion (Step 7 — conventions §11), amendment sync (Step 6 — it writes plan §2–§5), the scratch offer, and what becomes of a blocked step's edits (each stops for confirmation before a deletion — `references/agent_dispatch_spec.md`). Set to `low`: Step 0's which-leaf choice (take the first ready leaf in dependency order; a no-argument or ambiguous invocation still asks, conventions §5.2), Step 1's readiness fallback and its sizing check (take the recommendation: route back to the decomposer and stop), and Step 9's skip offer where an exploratory leaf's command is cheap (take the recommendation: start the review). Starting the review is not a question at any level — Step 9 states why. At `high`, confirm each step (Step 5) before starting it. Record the effective level and its source once in `EXEC_LOG.md`.
