# aggregate 模式——跨 run 的结果汇总表

单 run 分析回答*这个 run 是否达到了计划的预期*。aggregate 回答*整个实验计划显示了什么、每个数字从哪来*——把每个 run 已验证的数字编译成一份结果汇总表 `wkdrs/results/results.md`：论文结果节据以撰写的素材，也是 `metds/evaluation.md` 的对应物——后者定义它们是在什么协议下测出来的。

本文件定义范围、写入目标、信任模型、分组轴、结果汇总表绝不做的事、排除，以及写入规则。

**内容有效性与工程工作。** 把缺分析的 run 记为缺口前，按 `.agents/skills/star-flow-status/references/source_state_zh.md` 检查其当前工程豁免。有效豁免单独列为无指标的工程工作，不计为未测量或数值结果；过期/未知的豁免声明交回执行器。使用分析报告前，核对其绑定并要求覆盖当前叶子及祖先计划；旧式或过期分析转给生产者核验。结果表最终获授权写入后，用 `--report` 绑定所有应纳入考虑的分析，包括被排除的分析，并用 `--exemption` 绑定所列工程日志；若某证据缺失构成排除原因，用 `--file` 绑定其缺失状态。复用时要求覆盖当前报告清单，以发现新增 run。下述原始数字复核继续适用，绑定不替代它。

## 范围

`aggregate` 不带计划名时覆盖所有计划树；带计划名时覆盖该节点的子树。收集范围内每个叶子，以及**它 `exec_runs` 里的每一个 run**——一个叶子若为换 seed 或修 bug 重跑过，就有好几个；结果汇总表全都呈现，不只是最后一个。逐 run 取首个匹配：

- 当前有效的工程豁免 → 单列无指标工程工作，不计缺分析；
- 仍声明豁免但绑定未通过 → 转回执行器重新分类；
- 最新分析的绑定对当前约束及证据有效 → 一个可汇总的实验 run；
- 最新分析缺绑定或已失效 → 分析生产者先核验，不把旧数字或旧判定带入结果表；
- 未获当前工程豁免、且 run 目录没有分析报告 → **缺口**：列出它，转交给 `star-expt-analyst <run 目录>`。不要在这里读它的日志——aggregate 读的是报告，不是原始 run；
- 叶子压根没有 `exec_runs` → 从未执行；列为缺口，转交给 `star-plan-executor <slug>`。

没有可用实验分析时，先在聊天中列出已核验工程工作及真正缺口，再停止；不伪造数值结果表，也不把工程豁免计作缺分析。

## 写入目标跟随范围

**范围决定文件名，因为一份范围窄的结果汇总表悄悄替换掉更宽的那份，正是结果节丢行的原因。**

- **所有计划树**（`aggregate`，不带计划名）→ `wkdrs/results/results.md`。项目结果汇总表。
- **限定范围**（`aggregate PLAN_NAME`）→ `wkdrs/results/results_<slug>.md`，`<slug>` 为被限定节点的 slug——`wkdrs/results/results_core-method.md`。谁聚合哪棵子树，就有一份对应的文件。

两者绝不写入对方的路径。限定范围的运行绝不能覆盖 `wkdrs/results/results.md`：它包含的 run 本来就少，覆盖会删掉子树以外的每一行，只留下一个看上去仍然完整的文件。`scope:` frontmatter 记录这份文件覆盖了什么；文件名才是拦住这次冲掉的东西。

限定范围的结果汇总表是**视图，不是分叉**。它由同一批报告、在同一信任模型下重新生成，绝不携带项目结果汇总表不会有的数字。两者都存在且不一致时，以项目结果汇总表为准，限定的那份即已陈旧——重新编译，而不是手工对账。

## 信任模型:回到源头复核,绝不转手相信

一份 EXPT_ANALYSIS 报告是**已验证**的：里面每个数字入报告前都在其引用的来源处重开确认过（核心原则 2）。但那不是照抄它的许可：报告写完后 run 可能已变，而结果汇总表里的数字正是会被抄进论文的那个。

对每个将要进入 `results.md` 的数字：

1. 从报告的指标表里读出它，连同记录的来源（`path:line` 或键名）与 split。
2. **重开那个来源**，确认它仍然说的是报告所说的。
3. 一致 → 该数字进入结果汇总表，携带 `{run、来源、报告日期}`。
4. 不一致，或来源已不存在 → 该数字**不**进入。把该 run 放进 §5 已排除，写明两个值与原因，并建议重跑 `star-expt-analyst <slug>` 刷新报告。

绝不从没有任何报告覆盖的原始日志里读指标。那是单 run 分析，属于带自己 D 维验证的单 run 流程——不属于这里。

## 规模

一次汇总涉及 ≤ ~6 份报告时通常由主 agent 直接读更省事。多于这个数,就把**报告路径**切成几遍只读收集,一次一遍,每一遍拿到确切清单和下面这份返回格式:

```yaml
- run: <slug>
  report: <它读的那份 EXPT_ANALYSIS 的路径>
  report_verdict: <该报告自己的判定,原文照录>
  verdict_reason: <该报告自己给这条判定写的那一行原因,原文照录>
  metric_rows: [<该报告指标表的各行,原文照录,各自保留 source、split、seeds、spread 与 commit>]
  absent: [<报告判为 unmeasurable、或点名缺失的判据>]
  protocol_note: <该报告的协议注意事项,原文照录,没有则 none>
reports_read: <n>
```

别的都不返回。这样切分站得住，靠的是上面那条信任模型，不是任何一遍本身：复核的是**被引用的源头**，从来不是报告，所以收集器转录过的东西不会成为任何数字最终的读取处。`protocol_note` 逐份报告原文照录、绝不合并——合并协议正是"绝不合并在不同协议下测得的数字"所禁止的。收集器绝不回源复核、绝不按主张归组、绝不排除任何 run、绝不写文件。`reports_read` 少于这一遍拿到的报告数，意味着差额还要补读（规约 §6.3）。

## 按主张分组,而非按 run 分组

计划树是按拆解组织的；读者需要的是按**数字显示了什么**来组织。从根计划 §4 分组：

- **主张 → 实验映射**给出每条主张 / benchmark 一张表；
- **消融设计**给出每个消融一张表，行是各变体；
- 设计没有映射到的 run 进最后的"其他 run"块——列出来，绝不悄悄丢掉。

表内的行是 §4 指派给它的 run，按 §4 给出的顺序（没有则按前缀）。一个 run 一行，不是一份报告一行。消融表下面写一行 `varied: <计划里写明的、各臂之间不同的那些项>`——取自根 §4 的消融设计与各臂自己的 §2/§3；计划里没写就写 `varied: 计划未写明`，这本身就是一条发现。每张表下面都写一行 `N runs scored on <split> for this claim`——对同一个阈值试十五次和试一次是两种不同的主张，读者不该靠数行数才知道自己在看哪一种。

## 结果汇总表绝不做的事

- **绝不把差值归因于某个原因。** 表显示的是变体 → 数字。某个变体*为什么*赢，需要一次这个 skill 并不运行的受控对比（核心原则 5）。根 §4 说某变体*测试*什么，那是表题；在这里下的结论不是。
- **绝不合并不同协议下测出的数字。** split 不同、指标定义不同、评测入口不同，就是不同的表——或者一张表加 `⚠` 并写明两种协议。悄悄并成一列，就是一张错的论文表。
- **绝不算出一个没人测过的 baseline 差值。** 计划写明的 baseline 数字是一行；没测过的是 `not measured`，不是推算出来的差值。
- **绝不复述协议。** benchmark 怎么跑归 `metds/evaluation.md`；结果汇总表引用它、只呈现分数。

## 已排除的 run

报告判定为 `invalid` 或 `inconclusive` 的 run，或其数字复核未通过的 run，**不**出现在结果表里。它进 §5 已排除，附判定与一行原因——这行原因和判定一起写在那一遍的返回里，所以排除一个 run 不必把那份报告再整份打开一遍。悄悄排除一个 run，结果表就是这么开始撒谎的：读者必须能看见被拿掉了什么、并数得出来。

**`not met` 的 run 不排除**——负结果也是结果，它带着自己的判定留在它该在的表里。

## Frontmatter 格式约定

```yaml
---
type: results
language: <en|zh>
generated: <YYYY-MM-DD>          # 真实日期；绝不编造
scope: <这些数字来自哪个子树，或 "all plan trees">
sources:                          # 输入给这份结果汇总表的每一个 run
  - run: <prefix>_<slug>
    report: <EXPT_ANALYSIS_<YYYY-MM-DD>.md | none for engineering>
    verdict: <met|partially met|not met|inconclusive|invalid|— for engineering>
---
```

`type: results` 标识编译产物；`generated:` 与 `sources:` 日期保留为来源信息。时效由 source_state 对当前报告和工程豁免清单的内容绑定判断，同日变化也会使其失效。

## 写入规则

只作用于上面由范围选定的那个目标——绝不作用于另一个。

- **不存在** → 写。
- **存在且带 `type: results`** → 先确认它的 `scope:` 与本次编译的范围一致。一致 → 与新编译内容比对，展示变更清单（每张表一行：`added` / `rewritten` / `removed` / `unchanged`，以及变了什么），再问覆盖还是跳过。所有表都 `unchanged` → 核验当前输入后刷新来源信息和内容绑定，不发问，因为读者引用的数字一个都没动；正文逐字节不变。**不**一致——文件范围比本次更宽——→ 停下并说明，绝不收窄；那正是文件名规则要防的那种冲掉。
- **存在但没有该 frontmatter** → 人工撰写的。说清它现在有什么、编译会用什么替换它，然后询问。放着不动是合法结果；编译到用户指定的另一个路径也是。
