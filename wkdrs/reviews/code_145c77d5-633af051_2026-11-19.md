## 2. Verdict

**Blocked.** The hooks follow Devin's documented input and output shapes, and the commit-guard logic is byte-for-byte the shared copy apart from 12 harness-specific lines. But four confirmed majors remain:

- **Hook config:** the `INVOLVE=low` auto-approve gates also approve MCP tools (F1).

Three of the unconfirmed items decide whether the two gates do anything at all, and whether the guard's block wins over a gate's approve (U1–U3). One short live Devin run would settle them.

## 3. Findings

### Major

- **F1** `.devin/hooks.v1.json:4` and `:19` — Both PreToolUse matchers are unanchored. Devin matches them as substrings of `tool_name`, so at `INVOLVE=low` the two approve gates also fire on other tools whose names contain `exec`, `edit` or `write`, and approve them.
  - **Rule:** rubric E (configuration wiring must not silently broaden a setting). The Claude original matches exactly `Bash`.
  - **Evidence:** `lifecycle-hooks.mdx:349-350` reads "`"exec"` | Tool names containing `exec`" and "`"^exec$"` | Only the `exec` tool".
  - **Reproduced** in a scratch clone with `INVOLVE=low`:
    - `{"tool_name":"mcp__remote__exec_command","tool_input":{"command":"ls"}}` piped into `star_bash_gate.sh` prints `{"decision":"approve",…}`.
    - `{"tool_name":"mcp__fs__write_file","tool_input":{"file_path":"<root>/src/a.py"}}` piped into `star_involve_gate.sh` prints `{"decision":"approve","reason":"involve=low"}`.
    - The edit regex also matches `todo_write` and `write_to_process`.
    - The red lines still hold: `rm -rf build` under the MCP name gets no approve.
  - **Fix:** use `"^exec$"` and `"^(edit|write|notebook_edit)$"`, and update the two matcher assertions in `test_hook_shell.sh`.

- **F2** `docs/mds/star-workflow/research-workflow-conventions.md:312` — Conventions §10 item 1 says every harness manifest carries its own guard against implicit invocation of the seven † skills. On Devin none exists. Devin loads the shared `.agents/skills` manifests, which have no `triggers` field.
  - **Evidence:** `devin skills list` shows `/star-proj-adopt [user,model]`, and the same for all fifteen skills, so the model can start a † skill on its own.
  - **Contradictions this commit adds or leaves:**
    - `research-workflow-skills.md:99` (and the zh copy) opens "Each harness enforces it", then says Devin's limit is the description "rather than an enforced gate".
    - `README.md:337` (and zh:329) still says the † skills "run only when named".
  - **Also affected, before this commit:** the same claim is already false for Antigravity, which reads the same manifests.
  - **Rule:** rubric E/A. Docs must not claim a protection that does not exist (conventions §10.1).
  - **Fix:**
    - Preferred: give Devin the guard. Devin honours `triggers: [user]` (`creating-skills.mdx:82`, default `[user, model]`), as the `.devin/skills` wrappers already show. Either add it to the seven shared manifests, if every other reader of `.agents/skills` ignores the key, or ship per-skill Devin overrides. Then have CI check it in both directions.
    - Otherwise: say plainly in §10.1, the skills guide and both READMEs that on Devin and Antigravity the rule binds by convention only.

- **F3** `execs/configure.sh:473` — For Devin, an `@<depth>` is dropped, with the log line "@${depth} is ignored — Devin exposes no per-agent thinking depth". That's false. Devin lists a separate model UID for each depth, and an agent's `model:` takes the same values as `--model`.
  - **Evidence:**
    - `devin models list` includes `claude-opus-5-5-{low,medium,high,xhigh,max}` and `swe-2-{medium,high,max}`, and says "Pass a family slug, alias, or model UID to `--model`".
    - `creating-skills.mdx:100`: "The model name uses the same values as the `--model` CLI flag".
    - `subagents.mdx:270`: agents use "the same YAML frontmatter as skills".
  - **Repro:** `STAR_PLAN_MODEL=devin:swe-2@max` stamps `model: "swe-2"` and logs "ignored". `swe-2-max` is a listed UID.
  - **Rule:** conventions §10.8 (apply a depth wherever the harness can express one).
  - **Fix:** for Devin, append `-<depth>` the way `cursor_model_stamp` does, when the result is a valid UID stem. Otherwise, correct the log line, `.env.example:69-71`, `.devin/skills/star-auto/SKILL.md:16` and conventions §13 (Devin) to tell the user to write a depth-carrying UID, such as `devin:claude-opus-5-5-high`.

- **F4** `.devin/rules/skill-roots.md:19` and `.devin/skills/star-auto/SKILL.md:18` — Both send every read-only collection or blind read to the built-in `subagent_explore` profile. Devin documents that profile as unable to "edit files or fetch arbitrary URLs".
  - **Effect:** `star-refs-reviewer` sends one read-only sub-agent per paper to read it (Step 3) and to walk its references and citations (Step 4). On Devin those collectors cannot fetch the paper pages or the Semantic Scholar/arXiv records they need.
  - **Evidence:** `subagents.mdx:128`: "`subagent_explore` | Read-only codebase exploration and research | Read-only codebase tools plus web search; cannot edit files or fetch arbitrary URLs". `.agents/skills/star-refs-reviewer/SKILL.md:75,81` dispatch read-only sub-agents to read and expand papers.

  - **Fix:** keep `subagent_explore` only for code-reading collections. Map fetching read-only collectors to `star-read`, restricted with `allowed-tools` (`subagents.mdx:314`) so they stay read-only. Say so in both files.
