# 研究工作流 Skill 通用规约

**语言：** [English](research-workflow-conventions.md) | 简体中文

STAR 研究工作流中每个 skill 都遵守的规则。十五个 skill（§10 列出全部）各有自己的工作流、可写文件范围和质检表。它们共用的部分只在这里存一份。

**优先级。** 遵循当前指令层级。在用户控制的工作流文件中，用户对本任务的明确要求或已有授权优先于技能默认流程。本文件统一规定范围、权限、证据和来源记录；技能只写自己的具体约束与明确例外。措辞更严本身不撤销已有授权，也不推翻已记载的例外。确认点只有在相应决定或权限仍缺失时才需要新答复。

本文件既是给 skill 的约定，也是给读者的说明：这套工作流会对你的仓库做什么、不会做什么。

## 1. Git

**永不提交的 skill**——git 只读使用（`status` / `diff` / `log`，读执行分支时另加 `branch --list` 与 `show`，§11）：`star-flow-status`、`star-refs-reviewer`、`star-expt-analyst`、`star-expt-digest`、`star-metd-summarize`。

**可以提交的 skill**，及各自能 stage 的范围：

| Skill | 提交时机 | stage 范围 |
| --- | --- | --- |
| `star-proj-adopt` | 每个阶段结束时提供一次 | 只暂存该阶段写过的路径；在被接入的仓库里，原本就未提交的改动只列出，绝不捆进提交 |
| `star-idea-storm` | 会话结束时提供一次 | 本次会话创建或编辑过的 idea 文件 |
| `star-plan-coach` | 会话结束时提供一次 | 本次会话创建或编辑过的计划文件 |
| `star-plan-decomposer` | 运行结束时提供一次 | 本次所写子计划及父计划的索引更新 |
| `star-plan-reviser` | Step 7 有写入修订时提供一次 | 目标计划；父计划的 `## Sub-plans` 行变化时，连父计划一起 |
| `star-code-architect` | 每完成一个阶段或验证完一个迁移组一次 | `${CODE_NAME}/` 及本 skill 拥有的规约文件 |
| `star-env-builder` | 每次运行至多一次 | 仅 `${CODE_NAME}/requirements*` |
| `star-plan-executor` | 每个已验证动作一次，且仅在确认点批准了逐步提交时；外加 §11 的执行分支操作——创建、合并、弃用——各在自己的确认点上 | 该动作触碰的文件；在执行分支上，连同这些动作更新过的运行记录（§11.2） |
| `star-code-reviewer` | 修复轮之后可选的一次 | 仅修复轮触碰的文件 |
| `star-code-release` | 每完成一个阶段一次（gather / polish / readme） | 仅该阶段的路径：被移入的文件，以及这次移动破坏的调用点、打磨轮触碰的文件、`README.md` |

**通用规则：**

1. **只 stage 本次运行创建或编辑过的文件。** 绝不 `git add -A`，绝不 `git add .`——一次全量 add 会把 checkpoint 和草稿一并卷进来。
2. **提交信息前缀就是 skill 自己的名字**：`star-plan-executor: <run> step 2 — <摘要>`、`star-plan-coach: <slug> — <里程碑>`。一个 skill 一个前缀，提交历史因此按 skill 分得开。
3. **不推送、不改写历史**（`rebase`、`amend`、`reset --hard`）、**不打 tag——也不切分支**，唯 §11 定义的执行分支除外：`star-plan-executor` 只在具名确认点上创建、合并或弃用它。分支和远端归用户。
4. **运行开始时就已有未提交改动的路径，永不 stage。** 在提交提议里列出这些路径——`low` 档则列在收尾回复里——让用户先自行提交或 stash。
5. **记录每次获准提交。** `medium` 或 `high` 缺提交授权才问；`low` 采纳范围内的提交建议并记录。同一提交范围已获批准时不重复询问。开始时记录 `git status`，排除原本就脏的路径，最终回复列出实际提交。
6. **绝不强制 add 被忽略的路径。** `.env`、`datas/`、`inits/` 默认被 git 忽略，不进历史。`wkdrs/` **并非**整体被忽略：其下除 `*.md` 外都被忽略，因此工作流自己的报告——执行日志、分析、digest、审查、结果汇总表——是有意让它们能进版本库的，一次 run 的记录能活得比产生它的机器更久。`tasks/` 则整体被跟踪：计划自有的工具脚本本就持久，旁边的草稿也小到不值得单开一条规则。

**守卫。** 每套工具目录都带一个 `star_commit_guard.sh` 钩子，拒掉破坏规则、且代价高昂的命令：整批或强制 stage（`add -A`、`add .`、`add -u`、`add -f`、`commit -a`）、第 3 条点名的历史改写（`commit --amend`、`rebase`、`reset --hard`、`filter-branch`）、一键就能踩破 §11 的强制分支操作（`branch -D`/`-f`、`switch -C`/`-f`、`checkout -B`/`-f`），以及暂存文件超过 10 MB 的提交。`push` 是有意不在其中的。它也拒掉备好的红线命令的启动——处于命令位置的 `execs/scpts/<run>.sh`，或对 `wkdrs/<run>/.await` 标记的写入——只要 `wkdrs/<run>/` 里没有 `CODE_REVIEW_<date>.md`，或最新一份的日期早于 `EXEC_LOG.md` 里最新的日期（§2）。守卫是压在文字规则底下的一层地板，永不取代它——它一次只读一行 shell，读不确切的一律沉默。被它拒掉的命令，归用户自己运行。

## 2. 红线

skill 可在用户要求的范围内改代码并跑**轻量验证**。重任务、付费或不可逆操作需要具体授权：先备好命令、产物和已知成本，再询问尚未批准的部分。用户此前明确要求运行该命令、且资源范围已明确时，就满足这次确认；周边实现工作的授权本身不覆盖启动。`star-auto` 调用（§10.7）也授权目标与 `stop=` 边界内备好的重命令；未给 `stop=` 时保留该调用原有的不设上限授权。每次启动与陈述的成本都记入决策记录（§7.8）。成本或是否符合指定限制无法判断的命令交回用户。自动授权不覆盖破坏操作，唯 §11.4 明确规定的受保护空 worktree 移除除外。

**轻——skill 可以跑：**

- 单元测试与跑通性检查、import 检查、`python -m compileall`、小 batch 的一次前向。
- 小规模、**不微调**的子集推理。
- 空跑、配置校验、shape / dtype 检查、几步过拟合的合理性检查。
- 任何在**普通资源上几分钟内跑完**、且只写在该 skill 可写文件范围之内的动作。

**越过红线——交回用户：**

- **长时或多卡训练 / 微调**——任何完整训练。
- **全量数据集评测**——耗时数小时或占用大量算力的。
- **高开销 API 调用**——按次计费的大批量 LLM / VLM 推理。
- **`sudo` 或系统包管理器**（apt、brew）、驱动或 CUDA toolkit 的系统级安装，以及 **CUDA 源码编译**（flash-attn 一类）。
- **删除任何环境**，以及覆盖用户可能想保留的产物。
- 成本或运行时长**无法界定、或无法对照用户授权判断**的动作。获取缺失信息，或交回备好的命令。

下载体积阈值是**各 skill 自定的**——`star-env-builder` 的安装计划一旦获批，框架级下载照跑；`star-code-architect` 则把超过约 1 GB 的交回用户。各 skill 写明自己的阈值；上面这份清单是无论如何都越过红线的部分。

**怎么交接。** 给用户确切命令，经 `.env` 环境（§3）调用，有项目运行入口（`execs/run.sh`）时走它；说明它产出什么、落在哪，以及要带回什么输出才能验证判据。把命令写成可运行脚本是轻的；运行它不是。启动守卫（§1）守住 executor 简报里写的先后：备好的命令 `execs/scpts/<run>.sh` 会被拒掉——`star-auto` 之下也一样——直到这个 run 的审查存在且不早于它的日志；被拒的启动点名的是先跑 `star-code-reviewer`，不是一次要重试的失败。

## 3. `.env` 与项目运行时

`AGENTS.md` §9 的操作化版本。

1. **项目根的 `.env` 是 `CODE_NAME`、`ENV_NAME`、`CONDA_HOME`、`PYTHON_HOME` 的唯一来源。** 绝不猜本地路径、绝不硬编码、绝不凭别的项目的记忆填。
2. **以 `PYTHON_HOME` 为准。** 已设置 → 按其取值使用，`CONDA_HOME` 与 `ENV_NAME` 可留空，此时不走 conda、直接调用该解释器。留空 → 由 `$CONDA_HOME/envs/$ENV_NAME` 推导，两者都必须设置。两者都没有 → 这是要上报的 blocker，不是可以编造的值。
3. **`.env` 缺失** → 对需要解释器的 skill：从 `.env.example` 创建，请用户填好机器相关的值，在此之前停下。绝不为了继续跑而编造一个值。**这一条只约束即将跑东西的 skill。** 不需要运行时的 skill——状态汇报、计划编辑、文献调研——记下缺失、把 `INVOLVE` 当作 `medium`（§7.7）、`STAR_LANG` 当作未设（§7.6）处理，然后继续；只读 skill 绝不创建该文件，因为它自己不写文件的规矩优先于本条。
4. **shell 是无状态的。** `source activate` 活不到下一条命令。把解释器一次性解析成绝对路径——`$PYTHON_HOME/bin/python`，见 §3.2——之后每条命令都走它。绝不用系统 python。
5. **只有 `star-env-builder` 创建、修复或改动环境。** 其他 skill 永不安装或升级任何东西。缺失的工具（ruff、matplotlib、bibtexparser、pandas）意味着**这项检查只能做一部分**：没有它照跑，在报告里说明，并转交给 `star-env-builder`。为了跑完自己的检查而去装它，超出边界。
6. 跑不了 python 的环境是**要上报的 blocker**，不是绕过去的问题。

## 4. 真实日期

1. **写进文件的每个日期都取自运行时的系统时钟**（`date +%Y-%m-%d`）。绝不凭记忆写日期、绝不从上下文推断、绝不照抄模板或示例里的那个。
2. **抓取日期**是实际抓取的那天。**报告日期**是报告写下的那天。**备份戳**是备份发生的那天。
3. 同一天重新生成的带日期文件覆盖当天那份；**换一天**则新写一份。

## 5. 计划名解析

1. **`PLAN_NAME` 用来匹配 `metds/plans/*_plan.md`**：按 slug（`open-vocab-det-seg`）、按数字前缀（`00`）或按完整文件名；`metds/plans/…` 路径也算。已丢弃的计划按同样方式从 `metds/plans/dropped/` 匹配——丢弃把它搬到了那里（§9）。
2. **按明确参数与当前任务上下文解析目标。** 仍缺失或有歧义时，列出最接近的候选（前缀、slug、一行状态）并问一个直接问题。用户或当前已获授权的运行已确定的目标不重复选择，不猜测实质不同的计划。
3. **`parent:` 才权威；前缀只是提示。** 整棵树用各文件的 `parent:` frontmatter 重建。数字前缀只供人类排序与提示——在"根取最小空闲数字"规则之前创建的项目里，两个无关的根可能共用一个数字。
4. **叶子 = `children:` 为空或缺失的计划。** 只有叶子可执行。
5. **`depends_on` 存兄弟前缀**，是 executor 与 `star-flow-status` 使用的机器可读执行顺序。它保持无环，并与父计划 `## Sub-plans` 索引一致。概要单元（§0）没有前缀，绝不出现在 `depends_on` 里：展开成文件之后才进入这张图。
6. **绝不重编号前缀。** 每个更深的前缀、每个 `parent:` / `traces_to` 引用都建立在它上面。

## 6. 委派

1. **对有实质收益、范围明确且相互独立的工作进行委派。** 主代理决定分区与并发，小型串行或紧密耦合的工作留在本地。输入大、返回小且整合不必重做整个任务时，委派才值得；第 7 条另管有价值的独立复核。遵守宿主委派策略：已授权的技能步骤可满足“需用户请求”的条件，但不能越过明确禁令。无可用且获准的委派时本地完成，并在必要时说明缺少独立视角，不为宿主无法提供的工具反复询问。技能的规模建议是默认值，不是配额。
2. **交给子代理的是**：确切的文件清单、它必须返回的评分表或返回格式、以及逐字写明的范围（"只做这些条目"）。并发的子代理**文件互不重叠**，派几个都一样。**同时跑几个由主 agent 自己定**——按这份工作的规模来，而不是照固定数字；唯一的硬约束：打到远端 host 的子代理共用该 host 的同一份预算，那里的并行派发要么把预算分开、要么串行（§6.9）。**返回格式必须在某个 reference 文件里具名写出、逐项列明字段**，并以"除此之外什么都不返回"收尾。"返回一份填好的*<产物>*"不是返回格式：产物模板里带着子代理绝不能填的字段——它并不在其中的那次写入会话的 `model_id` 与 `model_trail`（§8）、skill 留给主 agent 的章节、以及后面某一步才定下来的取值。
3. **主代理整合返回并负责验收。** 检查修改的产物，并独立核验检查证据：实际命令、退出状态或原始结果、范围与代码版本必须支撑结论。证据缺失或不确定、整合改变了被测行为、或仍欠必需验收时重跑，不仅因检查由子代理执行就重复。子代理不判总体结论。每个分配的文件必须有已审覆盖、明确未知项或后续补读。
4. **只读子代理**——最常见的一类，读日志、读论文、读包、读计划——把你给它的表格填好返回。它不写任何文件，也不读自己清单之外的东西。只有一个例外：**去抓取远端内容的子代理要把抓回来的原始内容写进本次运行自己的缓存**——交给它的每个条目一个文件，放在 skill 指定的前缀下——因为字节只在抓取它的代理手上。除此之外它什么都不写，并发子代理的缓存前缀互不重叠。
5. **实现型子代理可以改文件，且没有具名的交办说明就绝不启动。** 写成文件的交办说明有两份：`star-plan-executor`（`references/agent_dispatch_spec_zh.md`）与 `star-code-architect`（`references/orchestration_spec_zh.md`）；其他 skill 派子代理改文件，就在派发的那一步写清同样的条款，并参照这两份里更贴近本次工作的那份。每份交办说明都要：写明该子代理的可写文件范围并以"此外一律不碰"收尾；把主 agent 已解析好的解释器绝对路径直接给它，而不是打发它重读 `.env`；禁止它安装或修复任何东西（§3.5——缺包是它要返回的 blocker）；要求派发前它名下的文件在 git 里干净，运行开始时就已改动的路径单独点名为既有改动；它失败时把这些文件恢复原样，好让重试从已知状态出发。
6. **一条说法在穿过确认点或引发写入之前，必须先被确认。** 这一条不能靠第 3 条覆盖：子代理报出"某路径有问题"、"某行是这个数"、"某处引用已过期"时，它根本没有跑过任何检查。在这类说法进入用户要回答的问题、或本次运行要改的文件之前，主 agent 亲自打开它标注的位置确认成立。站不住的就丢掉，或降格成不引发任何改动的一条备注。
7. **换个视角复核的子代理**——被派去重读主 agent 自己刚做完的东西——只有同时满足两点才值得派：主 agent 的盲区是结构性而非偶然的（它看不见自己从未写下的那句话），且被复核的产物为下游工作把关。否则主 agent 自己查自己。它是唯一一类主 agent 事后仍要自己再读的委派：换来的是第二双眼睛，不是省下一次阅读。
8. **参与度档位同样管到委派**（§7.7）。`high` 档，并行派发要在动手前连同切分方式一起说明；`low` 档则不声张地跑。任何档位下，决策记录（§7.8）都要写明本次运行做了并行派发、怎么切分——切分和别的裁量题一样，是一次判断。
9. **请求预算属于 host，不属于 agent。** skill 向远端 host 承诺的抓取速率上限——`source_policy_zh.md` 与 `scan_policy_zh.md` 各设了一份——是整个会话对该 host 一起花的，所以同时跑 N 个抓取者，真实速率就是 N 倍。并行派发抓取的步骤，要么把预算按子代理个数分开、在交办说明里把各自那份写成具体数字，要么一次只抓一个并说明串行。数字维护在各 policy 文件里，步骤引用而不复述。
10. **子代理跑在哪个模型、以及宿主支持时采用多深的思考，是 §10.8 的规则，不归本节管。** `.env` 里三个档位键决定它——只读子代理跑 READ，实现型的（第 5 条）跑 EXEC，第 7 条那种换视角复核的跑 PLAN。键为空时，委派完全按第 1–9 条描述的方式运作；宿主只应用其委派接口实际提供的模型与深度控制。

## 7. 对话纪律

工具中立的那一半。**怎么问**——agent 有结构化提问工具就用它，没有就用纯文本——因工具而异，留在各自的 `SKILL.md` 里。

### 自然写作契约

聊天回复与工作流正文直接陈述实质内容，不写赞美、预告式开场、继续服务邀请、夸大意义、模糊归因或空泛的积极结尾。它们遵循[自然写作指南](human-writing-guide.zh-CN.md)：有经作者确认的样本时使用该样本；依据模式组合进行复核，不机械禁用单个词或句式；必要时在段落尺度重写。风格编辑不得改变事实、数字、日期、引文、引用、来源 URL、路径、命令、字面字段、状态、完成判据、技术区别、不确定性边界、负结果或归属，也不得在没有作者与证据支持时增加个性或具体细节。

公式化表达问题只是一项建议性复核信号。它既不能证明文本由 AI 生成，也不授权为了让措辞显得像人而改变研究记录。

1. **每条聊天回复控制在约 500 字以内。** 写出的文件不计入。细节属于产物；回复是摘要。**唯一的例外**：一份回复的长度由它必须逐条列出的东西决定时——`star-flow-status` 的计划树——改由该 skill 写明的形状约束（每节点一行），而不是没有上限。
2. **只询问尚未确定的决定或权限。** 已有明确批准在其范围内继续有效。先准备具体方案并完成独立的已授权工作；提出问题后，依赖答复的动作须等明确答案。无人值守也不能把未答问题当成批准。第 13 条规定可见清单如何作为一次决定审阅。
3. **问题具体且便于回答。** 适合时用当前宿主支持的提问接口，否则用简短文字。给出推荐及有用备选的实际后果；真正开放的问题不强加选项。不强制固定选项数，也不调用当前模式不可用的工具。
4. **如实汇报。** 缺口绝不往上凑。跳过或没做全的检查绝不说成跑过。没改动的文件、状态或计划，绝不说成或暗示改过。
5. **结论先行**，然后是证据，最后是转交给下一个 skill 的建议——而对那八个 agent 可以自己启动的 skill，"转交"就是直接把它跑起来，而不是打印一条等人来敲的命令（§10.6）。打印出来的命令若建议以不同于 `.env` 里 `INVOLVE` 解析所得的参与度档位运行（第 7 条），要把写法原样写进命令——`star-plan-executor 03 involve=low`——照抄粘贴即可用；与 `.env` 已给档位相同时，裸命令就是完整的建议。
6. **语言只解析一次。** 用户明确的语言要求优先于所指内容；否则有效的 `.env` `STAR_LANG`（`en` 或 `zh`）决定回复和新工作流文档。未设或无效时跟随对话，没有用户回合则用调用文本的语言；转述子代理回复也遵守这一选择。已有文档保留 frontmatter 语言。按需读取对应语种的引用和模板；`SKILL.md` 是执行指令，`SKILL_zh.md` 是供人阅读的对照版。中文文档中的技术术语、指标、路径和 BibTeX 字段保留英文，代码注释始终英文。所需 `.env` 控制一并读取，未变化时在本次运行内复用。
7. **`involve` 档位控制尚未决定的裁量事项，不撤销用户已有权限。** 必须确定的事项包括研究目标、验收标准、关键输入、成本或权限的实质变化，目标歧义，以及尚未被具体授权的删除或覆写。同一操作与范围已有明确批准、或有记载的授权例外时，即满足规程确认。遵循项目默认值的常规可逆实现细节属于可推导项，不是必答问题。所有档位都保护证据、贵重产物和用户既有改动。

   档位由用户设定；skill 在**每次运行开始时、问出第一个问题之前解析一次**，按优先级从三个来源取值：`.env` 里的 `INVOLVE`（`low` / `medium` / `high`；其他情况 → `medium`），再被调用参数里的 `involve=<level>` 覆盖，再被运行中的自然语言（"少问点""都问我"）覆盖——最后一条指令在本次运行的余下部分生效。读 `INVOLVE` 就是第 6 条说的那次一行 `.env` 查询。持有持久运行日志的 skill 把生效档位及其来源在日志里记一次。

   **这个写法不是参数。** `involve=<level>` 在解析任何其他内容之前就从调用参数里剥离——计划名（§5）、模式、范围、日期窗口都在其后。**每个** skill 都如此，`SKILL.md` 提没提到都一样：拿第一个参数去匹配 `metds/plans/*_plan.md` 的 skill，不得把 `involve=low` 当成计划名或模式词，不接受参数的 skill 同样要剥离它。

   - `medium`——默认档：本文件与每份 `SKILL.md` 原样执行。档位不增不减。
   - `low`——按推荐项处理安全的裁量事项并记录（第 8 条），包括已授权范围内的提交（§1.5）。执行器展示实施计划后继续，不进入审批模式；常规提交、分支和 worktree 选择按推荐执行。这不等于改变研究范围或使用未经批准资源的权限。只有后果重大的决定或权限仍缺失时才询问。
   - `high`——skill 原文打包进一个确认点的、或在确认点之间自行决定的裁量题，逐条单独问出（第 2 条）。

   凡是问出的问题，第 2 条一字不变：档位只决定哪些裁量题要问，从不决定问出的问题可以默认已答。
8. **先决定，后披露。** 每次运行都留一份决策记录——skill 持有 `EXEC_LOG.md` 时写进它的"Notes / decisions"，否则列进最终回复的"Decisions taken"清单——每道落定的问题一行，形如 `问题 → 所取选项 → 它定下了什么`。在 `low` 档，它收录每个未经询问就拿定的裁量题，条数非零时最终回复必须报出。在 `medium` 与 `high` 档，它收录用户答过的选择。问题一落定就追加一行——一本流水账，绝不是在每个问题前重播一段越滚越长的回顾。
9. **技能可规定任务特有的决策边界，并说明原因和范围。** 必须尊重已有明确授权与记载的例外。不能仅因技能措辞更严，就把每次文件更新或常规选择当成新的审批。
10. **把线索接住。** 用户连答一长串问题时会丢掉线索。三个便宜的习惯，且刻意不在每个问题前重播回顾——那段回顾会越滚越长，直到用户开始略读。

    - **给问题挂上锚点。** 依赖前面答案的问题，用半句话提到它——"阶段轴 → 4 个单元；现在：哪一个承载数据叶子？"。一行，只带这道问题倚赖的决策，绝不是整段历史。
    - **在边界处回顾，不在问题之间。** 每个阶段、步骤或章节收尾时——用户本来就在此停顿——用 2–3 句复述：定下了什么、它产出了什么（写了哪个文件、置了哪个字段）、接下来打开了什么。
    - **点明退路。** 边界合上的东西若仍可更改，就说清怎么改：哪个 skill、带什么参数能重新打开它，重新打开的代价是什么。
11. **写出那件事，而不是它的名字。** 读者不该先解开某个词才知道发生了什么，所以非出现不可的名字要把意思一起带上，写在同一句里。它管到本次运行写进文件的正文，不止聊天；它止步于结构：标题、表头、字段名，以及被 skill 逐字匹配的每一个字面量，一律原样保留，解释写在旁边，绝不替换它。第 6 条挑语种，这一条管挑定之后的措辞：中文回复不把技术名词、指标名、路径译成中文。

    **只用来指向别处的字面量，在聊天里必须把说明带上。** `§4`、`C4`、`Step B1`、run 名、计划名前缀——对一个已经丢了上下文的读者，它们本身什么都不是；所以在聊天回复里，这类记号原样保留，第一次出现时用括号带 3–8 个字说明它指向什么：`§4（实验设计一节）`、`C4（训练前诊断能预判收益）`。不是整场对话只带一次——读者不会往回翻。同一条回复里后面再出现可以不带；实在写不下的地方（问题选项的标题、表格单元格）把说明放到它下面那一行。写进文件的正文里，解释写在记号旁边、写在第一次要紧的地方，不是每次提到都写。

12. **自由文本承载用户意图、约束和明确授权。** `<skill> [目标] [描述] [involve=<档位>]` 是共同形状：剥离控制 token、解析目标（§5），再按语义理解剩余文字。背景本身不构成授权；明确要求执行指定操作可满足对应确认（§7.2）。保留明确的只读要求与限制，不默默扩大所选模式或目标。`star-auto` 单独解析 `stop=`，其条件始终有效（§10.7）。首参数本身是主题或想法时同样处理。
13. **一张拟好的清单是一个问题，不是一项一个问题。** 当一次运行产出一份需要用户逐项接受或否决的编号清单——修订候选项、修复项、待同步的改动——整张清单先写进承载这个问题的那条消息正文里，放在调用之上：每项一行，写明它改什么、从什么改成什么、依据是什么、推荐怎么做。然后就这份清单**只问一次**，四个选项：

    - *全部按清单采纳*——每一行都是带着自身依据的局部改动时，标为推荐；
    - *除我点名的以外全部采纳*——点名的编号进入第二轮，其余在这一轮定案；
    - *先解答我点名的几项*——这一轮不定任何一项，解答连同同一张清单再问一次——对某一行有疑问不等于同意了其余各行；
    - *一项都不采纳*——什么都不写，本次运行已经落盘的东西就是交付物。

    被点出的行开启第二轮，形状照旧；缩到只剩一行就直接问那一行。**四行及以内**时清单本身放得进选项，就直接就这些行发问——所在宿主树的提问工具接受多选就一次多选——不必绕编号；第 3 条把一个问题的选项数封在四个。

    **这不是第 2 条禁止的打包批准**——它禁止的是批准一份用户看不见的清单；这里材料整张摊在调用上方、一行是一行，用户点名的每一行都会单独回来。选项只承载答案、绝不承载材料：一条只剩光秃秃选项的消息是把清单弄丢了，不是写短了。

    **区分实质不同的决定。** 新增成本、破坏性修改或未定研究选择须带着各自后果明确呈现。此前已授权的操作不重复问，不把新增权限请求藏在常规清单里。

    **档位照样拨动它**（第 7 条）：`high` 把清单逐行走一遍，`low` 取推荐项并记录在案（第 8 条）。

    **引导式提问不是清单。** 辅导类的连问——每个答案决定下一个问什么——没有拟好的东西可以摊开，仍按第 2 条一次一问。

## 8. 产物登记表

每个 skill 的持久产物，汇成一张表。`star-flow-status` 把它当作覆盖检查的依据：某个阶段“已覆盖”，指的是下表的产物存在、状态字段是最新的。这张表必须保持诚实——某个 skill 改了自己写出的东西，就在同一个 commit 里更新对应行。

| 阶段 | 产出方 | 路径 | 状态字段 |
|---|---|---|---|
| 接入 | `star-proj-adopt` | `metds/adopt.md` | `adopted:`、`backfilled:` |
| 想法 | `star-idea-storm` | `metds/ideas/<slug>_idea.md` | `finalized:` |
| 文献 | `star-refs-reviewer` | `metds/refs/refs_index.md`、`<ABBREV>.md`、`reference.bib`、`related_work.md`、`<slug>_survey.md` | 索引是否存在 |
| 代码库 | `star-code-architect` | `metds/codearc.md` | 是否存在 |
| 环境 | `star-env-builder` | `wkdrs/env_<名称>_<日期>/ENV_REPORT.md`、`freeze.txt` | 目录名里的日期 |
| 计划 | `star-plan-coach`、`star-plan-decomposer`、`star-plan-reviser` | `metds/plans/<前缀>_<slug>_plan.md` | `status:`、`finalized:`、`updated:`、`dropped:` |
| 运行 | `star-plan-executor` | `wkdrs/<run>/EXEC_PLAN.md`、`EXEC_LOG.md` | 计划的 `exec_status:`、`exec_runs:`；日志的 `branch:` / `merged:`（§11） |
| 代码审查 | `star-code-reviewer` | `wkdrs/<run>/CODE_REVIEW_<日期>.md`，否则 `wkdrs/reviews/code_<范围>_<日期>.md` | 文件名里的日期 |
| 计划复审 | `star-plan-reviser` | `wkdrs/<run>/REVIEW_<日期>.md`，否则 `wkdrs/reviews/<前缀>_<slug>_<日期>.md` | 文件名里的日期 |
| 实验分析 | `star-expt-analyst` | `wkdrs/<run>/EXPT_ANALYSIS_<日期>.md`、`wkdrs/<run>/analysis/` | 文件名里的日期 |

| 方法文档 | `star-metd-summarize` | `metds/{overview,framework,dataset,training,evaluation}.md` | `generated:`、`sources:` |
| 发布 | `star-code-release` | `README.md`、`wkdrs/release/RELEASE_<日期>.md` | README 的溯源标记（日期 + `sources:`） |

**每份产物都记录写它的模型。** 每个产出方把 `model_id` 写进自己创建的产物——产物有 frontmatter 就作为 frontmatter 键，没有就写在文件首行里（`CODE_REVIEW`、`REVIEW`、`refs_index.md`、`UPSTREAM.md`，以及 `README.md`——它的文件首行是一条 HTML 注释）。取值是运行时为当次写入会话报出的模型 id，原样抄录——而运行时确实会报：它就写在你的会话上下文里，由 STAR 的 `SessionStart` 钩子注入，Claude Code 还会写进系统提示。那一行缺失、或带来的是一条恢复命令而不是 id 时，各运行时的退路在 `model_id_spec.zh-CN.md`——写 `unrecorded` 之前先按它执行；`unrecorded` 只留给会话里任何地方都没写明模型的情况。绝不凭行为推断，绝不去想"这大概是哪个模型"，也绝不把一份产物的值抄到另一份上。

写入前的解析必须配上写入后的检查。每个产出方 skill——包括所有写报告的 skill——在最后一次写入之后、报告完成或提议及执行提交之前，对本次写过的每份产物各运行一次会话上下文给出的溯源检查。Codex 上填好参数的命令形如：`bash .codex/hooks/star_model_id.sh --check <artifact> <rollout> <session_model>`。期望值依次取 resolver 输出、`SessionStart` 的精确模型、`unrecorded`；实际值取产物里的 `model_id`。非零退出就是阻断：先修正溯源值并重新检查；检查失败时既不能报告完成，也不能提交。这同样不允许从 "GPT-5 family" 这类家族描述恢复取值——描述不是 id。

两条限制要说明，因为这个字段会用来横向比较不同模型的产出：

1. **它是自报的，不是核实过的。** 会话中途换过模型时，取值可能仍停留在切换前。把它当作出处的证据，而不是出处的证明。
2. **它描述的是一次写入，不是文件的全部历史。** 对写一次成型的产物——每份带日期的报告，以及每份整体重生成的编译文档——两者是一回事。对计划这种由多个 skill、多个模型在数月里反复编辑的文件，frontmatter 只写明最近一次写入者；逐次编辑的记录在 `## Revision History` 条目里，那里各自带着自己的 model id。

**而 `model_trail` 记录跨写入者的流水。** `model_id` 只记录一次写入，但有好几类产物是跨多次会话写成的——一个叶子分几天执行、一份计划被修订数月——单个字段只描述得了最后一次。所以每份产物还带一个只追加的 `model_trail`：每次写入会话一条 `{ date, model, skill, scope }`，其中 `scope` 用该文件自己的词汇说明本次写了什么（步骤、章节、条目）。新条目一律加在列表末尾、排在所有旧条目之下，所以不论在哪个运行时都是旧的在前；绝不改写既有条目，并让 `model_id` 始终镜像最后一条，这样直接 grep 仍然有效。整体重生成——编译文档——则开一条全新的 trail，并用一条记录说明它替换了上一代。

某份产物若已有逐事件的行，那些行同样带模型，且比 trail 更细：计划的 `## Revision History` 条目、`EXEC_LOG` 步骤表的 `model` 列、`refs_index.md` 的 `Model` 列。阅读时优先看它们——它们说的是某个模型写了哪一**步**、哪一**条**，而不只是哪一次会话。

`star-expt-digest ledger` 把全部 trail 汇总进 `wkdrs/digests/MODEL_LEDGER.md`，那是唯一能一眼看全整条流水的地方。它是生成物，从不手工维护：要修正某一行，改它来源的那条 trail 再重新生成。它由自报的 trail 编译而来，继承同样的限制，且不含任何质量信号：写得多不等于做得好。

**唯一的例外。** 在 `backfill` 阶段，`star-proj-adopt` 可以往 `metds/plans/` 的叶子上写 `exec_status:` 与 `exec_runs:`——且仅此二者——每个叶子都经用户单独确认。计划文件的其余一切，在接入的两个阶段里，仍归「计划」那一行写明的产出方所有。

这张表有两个性质比它的内容更要紧：

1. **编译文档上的 `sources:` 记录的是“读取当时”各源计划的 `updated` 值。** 它让过期判断靠精确比对完成，不必依赖文件 mtime。
2. **没有任何机制强制这张表。** `star-flow-status` 在报告末尾统计“形似报告、却不匹配此表任何一行”的文件数。

已丢弃子树的产物保留这张表里的每一个名字；变的只是目录，去 §9 列出的 `dropped/` 位置。

## 9. 项目布局

skill 写出的东西各归其位。每个去处互斥——文件属于哪一个，由它**是什么**决定，而不是由哪一步产生了它。

| 内容 | 去处 |
|---|---|
| 项目代码 | `${CODE_NAME}/`（取自 `.env`） |
| 数据 | `datas/` |
| 模型权重 | `inits/` |
| 某次 run 的产物、执行记录、报告 | `wkdrs/<run>/` |
| 跨 run 的汇编产物 | `wkdrs/` 下的保留子树：`reviews/`、`results/`、`digests/`、`release/`、`env_*`、`ideas_*`、`refs_*`——不要拿这些、以及 `dropped/`，当 run 名 |
| 计划、笔记、方法文档 | `metds/` |
| 先前会话学到、又没有别的文件认领的事实 | `.star/memory/`；只对本机成立的放 `.star/memory/local/`，git 忽略（`memory_spec.zh-CN.md`） |
| 项目文档 | `docs/mds/<topic>/`、`docs/htmls/`、`docs/srcs/`（`docs/mds/star-workflow/` 由上游管理） |
| 计划自有工具脚本、计划执行期草稿 | `tasks/<plan-name>/` |
| 运行入口 | `execs/run.sh` |
| 可复用启动脚本 | `execs/scpts/<run>.sh` |
| 已丢弃子树的文件 | 同名搬到一边，`star-plan-reviser` 的丢弃搬过去、恢复搬回来：`metds/plans/dropped/`、`wkdrs/dropped/<run>/`、`tasks/dropped/<plan-name>/`、`execs/scpts/dropped/` |

这张表装不下的两条规则：

- **`execs/` 根目录是封闭的。** 它只放 `run.sh` 与 `update.sh`，不放别的。新增 `.sh` 进 `execs/scpts/`；不是启动脚本的东西根本不进 `execs/`。
- **`tasks/<plan-name>/` 里有两类文件，只有一类可弃。** **计划自有的工具脚本**——该叶子自己的校验、索引、数据准备工具，也就是 §5 done-criterion 会去跑的那种——是持久的：在计划存续期间就住这里，finalize 绝不删它。其余都是**草稿**，只有“在 finalize 时丢掉也不心疼”的才属于这里。生成产物两者都不是：值得引用的产出、能复现某次运行的配置，都进 `wkdrs/<run>/`。

## 10. Skill 名册

十五个 skill，在 Claude Code、Cursor、Pi 与 Qwen Code 中写作 `/star-<name>`，在 Codex 中写作 `$star-<name>`，在 Kimi Code 与 DSH 中写作 `/skill:star-<name>`。每个具体做什么见 [research-workflow-skills.zh-CN.md](research-workflow-skills.zh-CN.md)；每个写什么见 §8。

| Skill | 档位 | 职责 |
| --- | --- | --- |
| `star-proj-adopt` † | exec | 把已经开工的项目接入工作流 |
| `star-idea-storm` † | plan | 把模糊的兴趣收敛成站得住的研究题目 |
| `star-plan-coach` † | plan | 写出顶层研究计划 |
| `star-refs-reviewer` | exec | 建立相关工作的证据底座与文献库 |
| `star-code-architect` † | plan | 搭起或重整代码库 |
| `star-env-builder` | exec | 构建并验证 Python 运行时 |
| `star-plan-decomposer` † | plan | 把计划拆成可执行子计划 |
| `star-plan-executor` | plan | 执行一个叶子子计划 |
| `star-code-reviewer` | exec | 拿规约与计划审查代码 |
| `star-expt-analyst` | plan | 用 done-criteria 给一次运行打分 |
| `star-expt-digest` | read | 汇总这段时间的整体进展 |
| `star-plan-reviser` † | plan | 拿执行证据修订一份计划 |
| `star-flow-status` | read | 只读的状态总览与唯一的下一步动作 |
| `star-metd-summarize` | plan | 把计划编译成方法文档 |
| `star-code-release` † | exec | 把仓库准备到可发布 |

1. **标 † 的七个是 slash-only。** 只有用户点名时才跑（第 7 条的常设授权是唯一例外）：每一个都守着一个属于研究者的决定，而一个由 agent 自作主张走到的决定，等于没有人做过这个决定。这张表是事实来源；每个 harness 的清单都以自己的写法带着禁止隐式调用的守卫，CI 会拿这七处与这里的标记双向比对——标了 † 却缺守卫、或没标 † 却带着守卫，都会让构建失败。
2. **其余八个可在任务明确匹配时选择。** 选择技能只覆盖用户要求的任务，并保留该模式的写入边界。状态、解释或不修改的评审请求不授权实现、修复、安装或其他会写入的后继。继续执行必须有用户既有的执行目标或新的明确要求。
3. **目标没定下来就不拾起。** §5.2 本来就禁止去猜用户指的是哪个计划；没人点名的运行把这条往前延一步——当哪个叶子、哪个运行目录、多大范围没有被文件本身定死时，列出候选并发问，而不是直接开跑。
4. **一次调用一个 skill，里面一个工作单元。** 一个叶子、一次运行、一份报告——运行中途悄悄扩大范围正是这条规则要防的事。下一个单元是下一次调用。
5. **不是用户发起的运行要自报家门**——开跑前一行，写明匹配上了什么、取了哪个目标；结束时在决策记录（§7.8）里留一行，用那份记录的形状：`匹配到什么 → 跑了什么 → 写了哪些文件`。"别自己开跑"和别的指令一样，在本次会话余下部分持续有效。
6. **只有下一步推进既有的已授权执行目标时才接续。** 只要求报告或只读的任务止于交付物与建议，即使推荐的技能属于八个也不启动后继。在执行目标下，当前运行结束后可于同一回合启动匹配且目标已定的非标记后继；说明范围并保留所有成本、写入和权限限制。七个标记技能仍需明确调用或 `star-auto` 授权。逐条判断命令：获准的评审可先于仍需启动授权的重命令。后继不会仅因出现在报告中就获得权限。
7. **`star-auto` 是明确的常设授权。** `star-auto <目标> [stop=<停止线>] [involve=<档位>]` 通过名册追逐所述目标，可启动七个标记技能，各运行仍保留自身范围和产物归属。`low` 下记载的 `auto=unattended` 执行链授权覆盖常规实现、不删代码的机械修复、指定路径提交、创建分支/worktree、干净且已评审的 squash 合并及受保护的空 worktree 移除（§11.4），也允许目标与停止线内备好的重命令（§2）。仍缺权限或实质决定未答时，依赖它的动作停下；不隐含更广的删除、覆写、force、push 或弃用。未配置档位时 auto 默认为 `low`。完整流程：[`star-auto`](../../../.agents/commands/star-auto.zh-CN.md)。
8. **一次运行在哪里执行、用哪个模型。** `.env` 里三个键各指定一个模型：`STAR_PLAN_MODEL` 管研究判断——计划、计划复核、分析与独立盲审——`STAR_EXEC_MODEL` 管实现与产出，`STAR_READ_MODEL` 管只读扫描、采集与汇总。上表的档位列写明某个 skill 的运行归三档中的哪一档，三个键与 `STAR_LANG`、`INVOLVE` 在同一次一行的 `.env` 查询里一并读出（§7.6），绝不为它们单发一次调用。**键为空，运行的行为就什么都不变**：它仍在会话或宿主原本给它的模型上跑，本文件其余每一条读起来都与三个键未设时一模一样。

   **一个键可以按宿主各指定一个模型。** 键值要么是一个模型名——读到这个键的宿主都用它——要么是逗号分隔的 `<宿主>:<模型>` 条目，标签沿用 `STAR_HARNESSES` 的记号：`claude`、`codex`、`cursor`、`dsh`、`kimi`、`pi`、`qwen`。一次运行取标签为自己所在那棵树的条目，没有则回落到不带标签的条目，两者都没有就把这个键读作空；**没有任何树认领的标签一律忽略**，日后新增的宿主正是放在这个位置。条目里第一个冒号即标签的结束处，模型名自身含冒号时就写成带标签的形式；每个名字按它自己宿主的写法拼写——`pi:anthropic/claude-fable-5`、`claude:fable`、`claude:claude-opus-5[1m]`。此处以及每一份 skill 清单里说的「档位值」，都指这条规则为读它的那个宿主解析出的结果，而不是查询返回的原始字符串。 **条目可以以 `@<深度>` 结尾**——`low`、`medium`、`high`、`xhigh`、`max` 或一个正整数——即这一档的运行在能设定深度的宿主上所用的思考深度；两档因此可以指定同一个模型，只在深度上不同。只有拼成上述深度之一的后缀才会被读作深度，模型名自身带 `@` 时原样交给它的宿主；没有深度控制的宿主只读取模型名。Claude Code 从 `bash execs/update.sh --models` 写入各档清单的 `effort:` frontmatter 取得深度，其受托者继承派发运行的深度。Codex 无需写静态文件：只要当前 `spawn_agent` 接口与所选模型接受该后缀，每次按档位派发都把它显式传给 `reasoning_effort`；因此 Codex 配置的深度本身就是路由差异，即使档位模型是当前模型的别名也会派发，运行中途换档也能同时更换模型与深度。接口或模型拒绝该深度时，不得声称已经应用：保留可用的执行路线，并一次说明限制。

   **模式覆盖该次运行的名册档位**，因为同一个 skill 在这个模式下做的事，和在那个模式下做的并不是一回事：`star-expt-analyst aggregate` 与 `star-expt-analyst watch` 是 READ，`star-refs-reviewer synthesize` 是 PLAN，`star-proj-adopt backfill` 是 PLAN，`star-code-release check` 是 READ。**有两次运行在中途换档。** `star-plan-executor` 的执行与验证那一段跑在 EXEC 上，其余部分留在 PLAN；`star-code-architect` 的迁移执行跑在 EXEC 上，设计工作留在 PLAN。这里定的是规则；各自怎么交接这个阶段、子代理可以写什么，属于该 skill 自己那份宿主清单——运行已经在该模型的别名上时，两者不再派发，除非宿主能在逐次派发时应用该阶段配置的深度。

   **在主会话里启动的运行，把自己交给一个跑在本档模型及可选深度上的子代理**，条件是以下四条同时成立：本档的键非空；该值不是本会话正在跑的那个模型的别名，或者它带有宿主可逐次派发应用的深度——别名指模型 id 里的系列名，如 `opus` 之于 `claude-opus-5[1m]`，或 id 本身，上下文窗口后缀不计；会话正在跑的模型，以会话上下文里那条溯源提示给出的解析命令运行一次所打印的为准（§8），打印不出就取那条提示写明的 id，两者都没有、且也没有可用深度要求派发时，运行留在原地；本次运行自己不是已经带着 `tier=` 令牌的子代理，于是交接只发生一次、绝不递归；以及运行里不再剩下任何必须问到用户的问题——任何档位都要问的确认点（§7.7），或本档位仍会问的裁量题——在运行开始时按模式、档位和磁盘上的文件判断：哪怕只有运行中的发现才会引出的确认点也算剩下，STOP line 的交还算返回而不算提问，档位不问就取推荐项的裁量题不算；这一条存在，是因为子代理无法向用户提问。不满足就在启动的地方跑完，键已设时用一行说明原因，键为空则不提。这个决定写在清单工作流开头、第一步之前的那一段里——除两个教练式 skill、以及宿主可以按其清单自带的模型 fork 的两个 READ 档 skill（`star-flow-status`、`star-expt-digest`）之外，每份清单都有：fork 出来的运行本来就在那个模型上，而 fork 派不出受托者。`star-plan-coach` 与 `star-idea-storm` 永远不自行迁移：它们的教练式问答每个阶段都要问用户一个问题，第四条对它们永远不成立；因此在 Codex 中直接调用时沿用主线程的 effort，而 `star-auto` 可以用配置的 PLAN effort 启动它们，并把问题递回。与 `involve=`（§7.7）一样，**`tier=<档位名>` 在解析任何其他内容之前就从调用参数里剥离**——计划名（§5）、模式、范围、日期窗口都在其后——每个 skill 都如此，它自己那份清单提没提到这个令牌都一样。

   **迁移出去的运行交给子代理的东西是固定的**：完整读取该 skill 的宿主清单并照它执行、原样的调用文本、`involve=<档位> tier=<档位名>`、`STAR_LANG` 为空时一行写明的对话语言（§7.6），以及运行手上有的 `auto=unattended` 授权。它等子代理返回，并把回复原样转达；子代理写下的文件就是本次运行的产物，其中记录的溯源（§8）是子代理的模型，不是会话的。运行内部，子代理路由跟着工作走，而不是跟着 skill 走：只读采集器跑 READ，实现型子代理（§6.5）跑 EXEC，§6.7 那种独立盲审跑 PLAN——把做完的东西重读一遍属于研究判断。宿主同时提供模型与逐次深度控制时，两者都按该档传入；只提供其中一种就只应用那一种，绝不把不支持的深度拼回模型名。

   **第 7 条从外部套用同一条规则。** `star-auto` 循环在开跑前用同一种方法读一次会话的模型，然后直接以各自档位的模型和宿主支持的逐次深度启动每一次运行，所以由它启动的运行本来就在该在的地方，不会再自己迁移。它对第四条有自己的处理：由它启动的运行遇到答不了的问题就把问题递回来，由循环按第 7 条分流。每一次启动、每一次并行派发，都把档位、实际拿到的模型，以及请求的深度或 `default` 写进决策记录（§7.8），与第 5 条本来就要求它声明的内容并列。

## 11. 执行分支与 worktree

只有 `star-plan-executor` 在获准的运行范围内管理本节的执行分支和 worktree。改变 checkout 前在 EXEC_PLAN 记录隔离选择。常规创建按 §7.7，合并、弃用与清理按下述具体授权和产物保护条件。操作细节在 `references/branch_rules_zh.md`。第 1–6 条管分支，第 7–9 条管 worktree。

1. **缺口清单决定建议。** 修改已有受跟踪代码时建议执行分支；仅新增文件、或写本运行的 tasks 与记录时通常留在基础分支。记录原因，尊重已有隔离选择。尚未确定的提交、分支与 worktree 选择按 §7.7：`low` 取安全推荐，`medium` 与 `high` 按各自粒度询问未定项。选择分支同时需要对应的指定路径提交，因为未提交的工作无法合并。
2. **命名、起点、记录。** 分支名 `<run>`，与 `wkdrs/<run>/` 目录同名成对；它从批准当时 checkout 所在的分支分出——绝不假定是 `main`——`EXEC_PLAN.md` / `EXEC_LOG.md` 的 frontmatter 记下 `branch:`、`base:`，此后再记 `merged:`。在分支上，每步的提交把这一步更新过的运行记录（日志行、子计划的状态）一并暂存，因为只有提交才会被合并。清单扫描只能按名字形状去匹配，所以既没有叶子、也没有 run 记录认领的分支不是执行分支——不要动它。
3. **基础分支始终是准据。** 合并之前，本次 run 写下的一切只存在于分支上，所以从基础分支看，这个叶子就是还没做完——这个读法是对的，不是缺口：`depends_on` 指着未合并兄弟的下游叶子保持受阻，把那个兄弟合并进来才解锁。`star-flow-status` 会列出执行分支，未合并的 run 始终可见。
4. **合并必须有适用授权**，且叶子为 `done`、最新评审没有未解决的 blocker/major。普通运行缺合并授权才问；`low` 下有效的 `auto=unattended` 授权覆盖已通过评审的干净 squash 合并及 `branch_rules_zh.md` 中受保护的清理。默认 squash，保留逐步提交是明确的另一选择。合并提交前，在已整合的基础分支验证受影响的轻量检查，再将成功的 `merged:` 记录连同整合改动暂存；清理前确认提交含该记录，检查或提交失败则保持其未设置。无人值守时先移出持久产物，只有状态为空才无 force 移除 worktree，并保留已合并分支。其他删除或弃用须具体授权。
5. **通过合入基础分支同步，不用 rebase。** 在明确获准的整合任务内，双方修改意图清楚的机械冲突可自行解决，再验证受影响行为。解决冲突需要取舍研究决定或覆盖用户工作时询问。仅有无人值守自动授权不覆盖冲突解决；除非用户另有授权，否则保留状态并报告。
6. **弃用先保全记录。** 删除未合并分支前，将其 `wkdrs/<run>/*.md` 记录、计划的运行条目和结论带到基础分支，也保留非 Markdown 产物。负结果是证据。弃用与删除需要具体授权，可以由此前明确要求满足，但无人值守授权本身不包含这两项。
7. **worktree 用来隔离忙碌的 checkout。** 信号包括另一运行的分支、另一运行拥有的未提交路径、尚未收集结果的启动命令或明确的并行工作。查看运行标记与可用的只读证据；尚无结果不能证明作业仍在运行，进程探测失败也不能证明它已停止。状态不明时优先使用隔离 worktree、不切换那个 checkout；只有这样仍不能安全避开冲突时才问。常规创建按 §7.7，移除须保留全部产物并符合第 4 条授权。
8. **进树的 run 一律带分支；树、分支、run 目录同用 run 名。** 树里的提交要有自己的归宿，而基础分支正被别的 checkout 检出，所以缺口清单本来判 `branch: none` 的计划，一进树就改为 `branch: <run>`。创建是一条命令，在被调用的 checkout 里跑：`git worktree add ../<根目录名>--wt/<run> -b <run> <base>`——树、分支、起点一步成型；树的绝对路径记进 EXEC_PLAN / EXEC_LOG frontmatter 的 `worktree:`，后续会话靠这个字段找到 run 的家。git 只把被跟踪的文件放进新树，所以建树后从主 checkout 链入 `.env`、`datas/`、`inits/`（`.star/memory/local/` 有则一并链）——绝不链 `wkdrs/` 与 `tasks/`：它们含被跟踪文件，整目录一链，在 git 眼里就成了一个符号链接。合并在检出着基础分支的那棵树里做——通常就是被调用的 checkout；用户把它切走了，就说明情况并发问。
9. **移除之前，先把产物挪出来。** 树里 `wkdrs/<run>/` 与 `tasks/<plan-name>/` 下非 md 的未跟踪产物只存在于这棵树，`git worktree remove` 会连树带它们一起删。次序固定：合并（或第 6 条的记录抢救）→ 把这些产物挪到主 checkout 的相同路径——期间计划已被丢弃的 run，路径以它的 `dropped/` 位置为准（§9），被暂缓的丢弃搬移跟在这次抢救之后 → `git worktree remove` 且绝不带 `--force`——树里还剩零散文件时 git 自己会拒绝，这道拒绝是安全网，不是要绕过的障碍 → 分支删不删再单独问。树的目录被人工删掉是要上报的 blocker；`git worktree prune` 清理过期元数据，绝不无声重建。

其他技能在运行记录的 `worktree:` 中工作。若将从另一运行的执行分支提交，保留无关改动，并按已有授权选择不冲突的路径；只有归属或目的地仍不明确才问。不要切换可能被活动作业重新读取的 checkout。执行器按上述条件负责创建和清理；用户已准备的 worktree 可直接使用，不重复询问创建。
