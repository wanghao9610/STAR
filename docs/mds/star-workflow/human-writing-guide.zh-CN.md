# STAR 研究记录中的自然写作

**语言：** [English](human-writing-guide.md) | 简体中文

STAR 产出的不是一篇孤立文章，而是一条从想法出发、经过计划和运行、进入分析、方法文档与发布 README 的研究记录链。
本项目中的自然写作必须让这条链更容易阅读，同时不能让它更难审计。
本指南约束正文和回复；证据、状态、所有权、执行与溯源仍以[研究工作流规范](research-workflow-conventions.zh-CN.md)为准。

## 1. 风格编辑的判据

项目中每条持久陈述都属于三类之一：已记录证据、从已记录证据得出的推论，或由后续工作流步骤负责的开放事项。
风格编辑可以改善三类内容的表达，但不得把一条陈述从一类移动到另一类。

统一使用下面这个判据：

> 改写后，下一个工作流 skill 能否从文件中还原同一个事实、状态、未确定性和决定？

如果不能，这次编辑改变的是研究记录，而不只是语言。
这比“保持原意”更严格：丢掉 citekey、淡化负面结果、藏起 `[TBD]`、改动命令或漏掉 run 名，都可能保住大意，却破坏工作流。

## 2. 完整指南的应用位置

所有回复都继承 `AGENTS.md` 中的短规则：答案先行，不写赞美、预告式开场、继续服务邀请和空泛的积极结尾。
六个产出正文的 skill 会在真正起草叙述性文字时加载本指南全文：

| 工作流阶段 | Skill 与正文载体 | 正文要完成的任务 | 润色不得移动的内容 |
|---|---|---|---|
| 收敛选题 | `star-idea-storm` → `metds/ideas/<slug>_idea.md` | 写清一个问题、扫描所得缺口、为何是现在、首次验证和风险 | 种子、有来源支撑的缺口、点名论文、约束、裁决、kill-condition |
| 把选题写成计划 | `star-plan-coach` → `metds/plans/<digit>_<slug>_plan.md` | 让六个已确认章节可供后续拆解和执行 | 章节状态、决定、引用、阈值、`[TBD]`、技术区别 |
| 建立文献基础 | `star-refs-reviewer` → `metds/refs/` 下的笔记、`related_work.md` 和综述 | 分开论文声称的内容与它同本项目的关系 | 引文、citekey、来源深度、归属、未确定性、负面结果 |
| 报告实验变化 | `star-expt-digest` → `wkdrs/digests/EXPT_DIGEST_<日期>.md` | 写清覆盖区间内发生的变化和仍未解决的事项 | 区间、来源层级、run 名、数字、临时标签、不利结果 |
| 编译方法 | `star-metd-summarize` → 五份 `metds/*.md` 方法文档 | 重组有计划支撑的方法内容，但不设计方法 | 计划出处、数值、路径、`TODO`、验证标签、冲突 |
| 编译发布面 | `star-code-release` → `README.md` 及可选中文版本 | 说明仓库中可核验的内容和运行方式 | 命令、路径、run、结果条件、出处、来源缺失时的 `TODO` |

其他 skill 使用共享规约里的短契约。
当产物主要是代码、结构化状态、评分裁决或有界执行记录时，无需加载本指南全文。

## 3. 分开记录层与正文层

改写前，先把目标分成三层。

### 记录层：原样复制或不动

- YAML frontmatter、状态值、日期、计划名、run 名、模型标识和 `traces_to` 链接；
- 事实、测量值、阈值、seed、方差说明、表格数值和完成判据；
- 引文、citekey、论文题名、来源 URL、抓取日期和来源深度标签；
- 路径、命令、flag、环境键、函数名、字段名、字段值和代码；
- 未确定性边界、负面结果、未消解冲突、`[TBD]`、`TODO` 和“尚未验证”标签。

### 正文层：能改善交接时可以改写

- 引入已有证据的顺序；
- 把证据连接到局部推论的句子；
- 解释某项结果为何改变计划决定；
- 约束、方法选择、实验与风险之间的过渡；
- 保留来源层级和论断强度的摘要。

### 所有权边界：转交，不用润色掩盖

缺失数值不是风格问题。
过期计划、run 缺少分析、引用尚未核验，或只存在于聊天里的方法细节也不是。
保留明确缺口，并把它转给负责补齐记录的 skill。
不得为了让段落显得完整而增加看似合理的细节、个性、轶事或“合乎情理”的结论。

## 4. 工作流产物特有的失败方式

### 想法与计划

不得把新颖性写成“开创性方向”“重要里程碑”等仪式化表述。
应点名扫描过的工作、尚未覆盖的能力，以及让这个问题值得测试的约束。
保留 `not scanned`、`[TBD]`、已搁置方向、备选条件和 kill-condition；它们是控制状态，不是应该被抹平的难看文字。

### 文献笔记与综述

已有 citekey 和核验记录时，不要写“已有研究表明”。
不得用 venue 声望或引用数替代与本项目的直接重叠度。
论文主张、收集器返回内容和主 agent 针对本项目的判断必须可以区分。
一个段落可以综合多篇论文，但每条被映射的局限都必须能从对应笔记还原。

### 实验 digest

失败、部分完成、过期或尚未分析的 run，不得在汇总时获得成功叙事。
分别写清分析文件已经证实的内容、日志自报的内容，以及仍属临时判断的内容。
不得从时间先后推断因果，也不得在实验不支持时把“改动 X 后指标上升”改成“X 导致指标上升”。
结尾停在未解决决定、所需分析或转交命令上，不用对未来进展的乐观表态收尾。

### 方法文档

`star-metd-summarize` 编译计划，不会从代码、日志、`wkdrs/` 或聊天记忆中修补计划。
叶子尚未完成时，其贡献要标为未经验证。
叶子与父计划冲突时，按工作流规则保留解析后的来源或显式冲突。
模板章节没有计划覆盖时保留 `TODO`；流畅的占位文字仍是编造的方法内容。

### 发布 README

README 是编译出的文档，不是宣传文案。
描述仓库已经核验的能力，不描述希望它产生的影响。
结果必须带着 run 和条件；命令从已解析脚本逐字带过来；图片路径只在文件存在时出现。
必备章节缺少来源时，用 `TODO` 点名产出方；映射规则要求空则省略时，直接省略，不作辩解。

### 回复与交接

先写答案、改动、发现或阻塞原因。
写出动作及其后果，不要只报一个需要读者自行解码的阶段名。
`finalized:`、`§4` 等工作流标签只在同时说明当前所需含义时使用。
停在最后一个有用事实、决定、命令、文件或阻塞原因上，不追加赞美或继续服务邀请。

## 5. 按工作流顺序起草和修改

长回复或持久正文产物按以下顺序处理：

1. **解析所有权。** 确定产出 skill、确切目标路径、语言规则和它允许读取的文件。
2. **读取记录。** 使用该工作流步骤点名的来源；不得用聊天记忆替代缺失来源。用户提供了写作样本时，在这里读取。
3. **冻结受保护内容。** 列出必须逐字或逐项保留的事实、字面量、状态、引用、数字、未确定性和负面结果。
4. **确定交接。** 写清下一个读者或 skill 必须从这段文字理解什么、决定什么。
5. **围绕实质内容起草。** 区分已记录事实、有支持的推论和开放事项；使用计划与代码架构中的稳定技术术语。
6. **按段落复核模式。** 查找集中出现的公式化行为，不逐个替换观察词。
7. **对照来源。** 恢复任何丢失的限定语、出处指针、状态、命令、路径或不利结果；删除新增论断。
8. **只写本步骤拥有的内容。** 保留 frontmatter、表格、代码块、链接目标和字面字段，再把缺口转给产出方。

一次运行产出多份文档时，还要比较各自的开头、方法回顾、限制和结尾。
模板要求的重复结构可以保留；没有证据支撑的重复修辞不应保留。

## 6. 值得复核的公式化模式

以下是复核信号，不是禁用形式，也不是 AI 作者身份的证据。
多个模式集中出现，或出现明确的聊天机器人残留时，才复核该段。

- **夸大意义：** 重要性、变革或广泛影响出现了，却没有对应论断和证据。
- **模糊归因：** “专家”“行业报告”或“已有研究”取代项目已经持有的引用或记录。
- **无依据的分析尾巴：** “thereby demonstrating”“highlighting”“从而彰显”或“进而说明”追加了证据未建立的影响。
- **预设式对比：** 反复使用“不仅 X 而且 Y”、强凑三项或虚设被否定选项，只制造戏剧性而不承载技术区别。
- **术语轮换：** 近义词替换规范的方法、数据集、指标、状态或组件名，并悄悄改变其范围。
- **隐藏主体：** 被动语态或抽象名词链掩盖谁设计、测量、确认、推断或决定。
- **均匀节奏：** 等长句、重复句首和口号式碎句让段落服从模板，而不是服从推理。
- **装饰性脚手架：** 问候、赞美、章节预告、过多标签、“希望这对你有帮助”或继续服务邀请包围着有效内容。
- **填充语或回避词堆叠：** 铺垫表达延迟论断，多层限定语则掩盖而非校准未确定性。

不得禁用破折号、被动语态、连接词、第一人称、三项列举、标题、粗体或长句。
当它们承载真实比较、保留用户确认的声音、暴露必要结构，或准确界定证据边界时，应保留。
句式节奏应随推理变化，绝不能靠注入随机的不规则来变化。

## 7. 写入文件前的验收检查

不得给出数值化“人类分数”。
使用与下游工作流风险直接对应的检查：

| 检查项 | 要回答的问题 |
|---|---|
| 可追溯性 | 每条研究论断是否仍能定位到支持它的来源文件、引用、run 或已记录决定？ |
| 状态保真 | 状态值、`[TBD]`、`TODO`、临时标签、负面结果和未消解冲突是否仍然明确？ |
| 因果纪律 | 正文是否以证据允许的同等强度区分观察、比较和因果结论？ |
| 所有权 | 编辑是否留在产出 skill 的读写边界内，并转交缺失记录而非编造？ |
| 术语一致 | 计划、代码、实验与正文是否用同一规范名称指代同一对象？ |
| 声音 | 结果是否符合用户样本或本项目克制的技术默认值，没有装饰性个性？ |
| 交接 | 下一个 skill 能否识别决定、剩余未确定性，以及所需的确切文件或命令？ |

论断保真和状态保真是发布条件。
其他检查用于定位修改工作；没有一项用于判断文本由谁撰写。
