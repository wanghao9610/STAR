# Agent 交办说明（Cursor Task）

仅当协作工具可用，且工作边界明确、相互独立、确实能从独立上下文或并行执行中获益时才委派。委派时调用你的子代理工具，实现工作使用可写子代理、跑在 EXEC 档的模型上（规约 §10.8，前提是这个 harness 能指定受托者用哪个模型）；只有只读勘察范围使用只读子代理，跑在 READ 档的模型上。哪一档的键为空，那一档的派发就不指定模型。步骤很小、严格串行、与当前改动紧耦合或容易产生文件冲突时，由主 agent 本地完成。不要给每个琐碎动作都创建一个 subagent。

**在这个偏好之内,模型仍旧跟着步骤走。** 机械改写的步骤——填模板、挪文件、改计划已经点名的符号、跑格式化、设一个计划已写明的取值——要用的判断很少:用你的子代理工具派可写子代理、跑在 READ 档的模型上,因为这一步自己的检查会兜住错误,而这里换档位只改账单、不改结果。写或改逻辑的步骤——计划只说要达成什么、没说要敲什么——改取 EXEC 档的模型;对应的键为空时,两种步骤都随会话原有的模型走。两边都读得通的步骤算逻辑:便宜的 agent 在逻辑上出错,代价是一次重试加主 agent 的复核,比省下的档位更贵。

**连贯范围**指至多 3 个 EXEC_PLAN 动作：它们碰同一批文件、拆开就没有意义、共用同一个 check。除此之外都是各自独立的动作。一个范围只委派一次、只检查一次，写进 EXEC_LOG 时每个成员动作各占一行并带上范围标识——没有返回的范围，每一行都停在未完成，恢复时就不会把它读成已完成。碰到红线边界要拆开。

**委派顺序与并发由主 agent 自主决定。** 按 EXEC_PLAN 的 action 顺序与依赖关系自由编排：消费上游产出的 action，等那一步的检查通过后再委派；相互独立的 action，并发还是串行由主 agent 自行判断——不设并发上限，除依赖本身外不强加任何顺序。并发的写文件受托者之间文件互不重叠（规约 §6.2）；`EXEC_LOG.md` 只有主 agent 一个写手——每验完一个 action 的返回结果就由主 agent 记录并提交它——所以"只 stage 这个动作碰过的文件"在任意并发数下都成立。

**委派之前**，这个动作名下的文件在 git 里是干净的。运行开始时就已经改动过的路径，单独点名为既有改动，并排除在下面所有恢复动作之外：它不归本次运行去回退。

## 交给 agent 什么

- **范围**——该步目标,逐字取自 EXEC_PLAN,加上它绑定的 check。明确写:"**只**做这一步;不要推进到后续步骤。"
- **可写文件范围**——此外一律不碰:`${CODE_NAME}/` 下要新建或修改的确切文件/模块(取自缺口清单);`wkdrs/<run>/` 下的产物;`tasks/<plan-name>/` 下的中间文件,绝不碰别的计划的;以及仅限红线步骤的那份备用启动脚本 `execs/scpts/<run>.sh`——写它是轻的,跑它不是(`stop_line_rules_zh.md`)。匹配既有代码风格,只碰这一步需要的地方(AGENTS.md §3,精准克制的修改)。
- **运行环境**——主 agent 已经解析好的解释器绝对路径,逐字给它。agent 不再自己去读 `.env`:它的工作目录未必是项目根。缺包是它要返回的 blocker,绝不是它自己去装的东西(规约 §3.5)。
- **边界**——它**只能跑轻量验证**。若它的步骤在红线上,必须**备好命令并返回,不要跑**(`stop_line_rules_zh.md`)。

## agent 必须返回什么（结构化）

- `changed`——新建/修改的文件,每个一行。
- `ran`——实际跑过的命令 + 结果,或 `none`。
- `check`——绑定 check 的结果:`pass` / `fail` + 证据(测试输出、指标、产物路径)。
- `blockers`——让它停下的东西,或 `none`。
- `handoff`——为用户备好的任何红线命令,或 `none`。

## agent 返回后

主 agent 必须审查 diff，并在写入 EXEC_LOG 前核验本 action 绑定的检查。能够检查确切命令、退出状态/结果、原始日志或产物、以及对应代码版本（commit，或记录在案的脏树 diff）时，可以直接采用原次执行作为最终证据；受托者的摘要或自报通过本身绝不是证据。缺少这些输入、证据已过期时重跑最窄检查；整合改变了行为、依赖或被检代码后始终重跑受影响检查。已有实现/整合授权、预期组合结果在机械上没有歧义时，可以处理常规整合冲突；检查组合后的 diff 并重跑受影响检查。若冲突要求在用户改动、研究意图、范围或验收之间取舍，就交回用户定方向；单凭 `auto=unattended` 不取得冲突消解权。

- 通过 → 记录产物与检查证据，将动作标为 `done`。
- 失败 → 把失败记进 EXEC_LOG，保留确切命令、原始失败输出和代码版本；重试前先恢复这个 action 的文件——已点明的既有改动除外。恢复到这个 action 开始时的逐 action 快照，而不是 `HEAD`：逐 action 提交可能已经被拒绝，那时更早的已验证 action 同样没提交，重置到 `HEAD` 会把 EXEC_LOG 已经记为 `done` 的工作一并抹掉。恢复绝不碰本 action 之外的文件、快照之后的用户编辑、或作为证据保留的原始日志/结果；重试会覆盖这类证据时，改用新输出路径，或取得具体覆盖授权。只有存在具体修正方案时才重试，最多两次。否则该 action 标 `blocked`：已有适用的用户决定说明怎样处理 action 自有编辑时直接沿用，不再问一遍；没有时，恢复前先问（规约 §7.7——这是把关删除的），无论哪种选择都记下来并点名路径，然后停止。`auto=unattended` 下只可恢复快照能证明归本 action 所有的增量；归属有歧义就停止。没有哪个 action 可以留下无人认领的改动。
- 有 handoff → 记入「待用户执行」，不运行并返回。主运行随后按 `stop_line_rules_zh.md` 处理：有具体授权的普通启动，或外层 `star-auto` 启动器，只有当前审查与成本守卫通过后才可运行；否则继续交给用户。
