# 拆分轴

拆分轴指*用什么方式*把父计划切成子计划。选一个（允许混合，但要确认）。用一个简洁问题通过你的提问工具提出这些轴，推荐项放第一位。先完整读父计划，以及根计划的 §3（方法）、§4（实验）、§6（里程碑）——下面各轴切的是根计划的总体方向，父计划只决定这一层切它的哪一部分。

## 一层只放同一类

同一节点的子计划互为**同辈**：同一类单元，体量相当。一层给出的是类别，类别内的条目再往下一位数字。拆分轴决定*选哪些类别*，它从不允许把类别和它自己的成员并排。

清单草拟出来、第 3 步展示之前先做这道检验：某个单元是不是另一个单元所指类别的*一个实例*？`02_ablation-budget-alloc` 与 `03_main-expts` 并排就通不过——一个是单条消融，另一个是全部主结果。把实例归到类别下再递归：

```
02_ablation-expts                   这一层给出类别
 ├ 020_ablation-budget-alloc        它的成员，再深一位数字
 └ 021_ablation-evict-policy
```

体量是这道检验的另一半：值一周的单元不该与值一个下午的并排。任一半不过关，这一层就把 10 个兄弟的名额花在本不是同辈的东西上，并压平前缀本该编码的结构——树的深度从此说明不了体量。

来源不同没关系：来自不同拆分轴的单元仍可以是同辈（见混合拆解）；粒度不同才是问题。

## 三种轴

### 1. 阶段 / 里程碑 —— 默认推荐

沿根计划 §6 的时间线阶段拆。每个里程碑成为一份子计划。

- **何时用**：根计划的里程碑已写得比较成形（通常如此——coach 会把便宜的排在前面：先实现基线，再做验证可行性的最小实验，其余从 deadline 倒推）。
- **产出**：时间上有序的子计划链；依赖大多是线性的（每个阶段交接给下一个）。
- **示例**（`0_open-vocab-det-seg`）：`00_baseline-impl` → `01_mvp-verify` → `02_core-method` → `03_final-rets`。

### 2. 组件 / 模块

沿根计划 §3 方法中可分离的部分拆。每个系统模块成为一份子计划。

- **何时用**：方法能拆成可以较独立地构建与测试的模块。
- **产出**：可并行推进的子计划；依赖构成一个小图（共享接口），而非一条线。
- **示例**（`02_core-method`）：`020_desc-generation`（LLM 动态描述生成）、`021_set-matching`（多描述集合匹配）、`022_det-seg-heads`（共享检测 + 分割头）。

### 3. 实验 / 证据

沿根计划 §4 拆。**一层给出的是实验组；各条主张在它们下面一位数字。**

- **何时用**：贡献主要偏实证，有若干主张和消融，各自需要独立的实验管线。
- **产出**：为数不多的几个组——数据就绪、基线方法实现、消融实验、主结果——每个都是一块有自己完成判据的工作量。递归某个组才得到每条主张一个叶子：论文的主张与叶子一一对应，只是比组深一层，核对"每条主张都有实验"看的就是那一层。
- **示例**（`0_kv-cache-compress`——与上面阶段示例不是同一个项目的根计划，所以两边的前缀数字重复；认父靠 frontmatter 的 `parent:`，从不靠数字）：`00_data-prep`（LongBench 与 PG-19 测试集落到 `datas/`，完整性检查通过才算完成）、`01_baseline-expts`（实现被比较的方法并跑出它们的基线数字）、`02_ablation-expts`、`03_main-expts`（在消融定下来的配置上跑主结果——主张 3：等显存下能吃更长的上下文）；把 `02` 递归下去得到 `020_ablation-budget-alloc`（主张 1：按层分配缓存预算优于均匀分配）与 `021_ablation-evict-policy`（主张 2：按注意力累积量淘汰优于近期窗口）。
- **不要**把某一条消融与 `03_main-expts` 并排——那正是"一层只放同一类"排除掉的混层。

## 如何选择

- **默认选阶段**，除非根计划里程碑较弱或用户另有要求——它贴合计划已有的结构，并给出最清晰的执行顺序。
- 当系统还要建、且模块可并行推进时，优先选**组件**。
- 当代码已经能端到端跑起来、剩下的风险是实证性的（每条主张是否成立？）时，优先选 **实验 / 证据**——代码还跑不起来的话，这条轴没地方放建系统的工作。
- **阶段轴与证据轴通常是父子关系，不是竞争关系。** 实证类根计划的 §6 里程碑本就从 §4 实验倒推而来，两条轴读的是同一批内容——阶段轴按时间排成一条链，证据轴按证据类型排成一张宽 DAG。这一层选阶段轴并不等于放弃证据视角：它会在下一层回来，作为实验最重那个阶段的递归。只有阶段轴能容纳建系统的工作；只有证据轴会把数据就绪提到顶层单独成叶。据这两点决定，而不是看哪份单元清单更顺眼。
- **深度优先于广度：** 第 2 层按阶段拆、再对繁重的阶段在第 3 层递归拆，是完全可以的——往往更好：那个阶段是"核心方法"时按组件递归，是"完整实验"时按实验 / 证据递归。不要在单个扁平层里囊括一切；当多出来的广度是同一类别的若干实例时，"一层只放同一类"要求必须递归，而不只是更可取。

- **还不知道该做什么时，探针叶子是正当的一格。** 三条轴都假定方法已定下来；研究前期常常不是这样——先跑两三个小实验看这条路有没有戏，那时写不出主张表。这种单元照常是一个叶子，只是 §5 判据写成"看什么 → 哪种结果触发哪个决定（继续 / 改法 / 放弃）"，收尾时把那条决定连同证据写进 EXEC_LOG。它的数字只作未核实层、不进结果汇总表，所以不会把还没验证的猜想抬成主张——那正是前期最该避免的事。探针跑完，方向定了，再按上面三条轴拆真正的实验。

## 每份子计划的粒度

- 每次拆解目标 **3–7 份**子计划；≤10 是硬上限（命名规则）。少于 3 份通常说明父计划还不需要拆；多于 7 份通常说明该写类别的地方写成了实例——把它们归组再递归（一层只放同一类）。
- 每份子计划负责**一个内聚、可独立检查的块**——有自己的完成判据。某单元没有清晰的"完成"测试，要么太含糊，要么应并入某个兄弟。
- 明确写出**non-goals**，使相邻子计划不重叠；它们的并集应覆盖父计划的执行，且没有任何一块同时归两份子计划负责。

## 各轴隐含的依赖

把依赖记为每份子计划的 `depends_on` frontmatter 列表（必须先完成的兄弟前缀），并在父计划 `## Sub-plans` 索引里写出由此得到的顺序。拆分轴给出默认形状：

- **阶段 / 里程碑 → 线性链**。每个阶段交接给下一个：`01 depends_on ["00"]`、`02 depends_on ["01"]`……
- **组件 / 模块 → 小 DAG**。共享接口的模块依赖产出该接口的一方；相互独立的模块 `depends_on: []`，可并行。例如 `022_det-seg-heads depends_on ["020", "021"]`（若它同时使用描述与匹配器）。
- **实验 / 证据 → 组一层是宽 DAG，组内叶子大多相互独立**。数据就绪叶子是所有消费它的组的上游；基线实现与消融实验从它出发并行推进；主结果在消融定下来的配置上跑时就依赖消融实验。组内每条主张的实验管线通常自成一体（`depends_on: []`）；只有当一个实验确实复用另一个的产出时才加边。

务必保持**无环**。若两个单元看起来互相依赖，它们其实是一个单元——合并它们，或把共享的部分拆成第三个上游子计划、让两者都依赖它。

## 混合拆解

允许混合轴（要明确确认）。最常见的形状是**本层按阶段拆、再把繁重的阶段按组件递归**——但里程碑与主张不能整齐对应时，也可以在同一层里混合。混合时说清哪个单元来自哪条轴，并仍给每个单元一个 `depends_on` 列表。混合改变的是单元的来源，不是体量——这一层放的仍必须是同辈（一层只放同一类）。

- **示例**（`0_open-vocab-det-seg`，第 2 层混合）：
  - `00_baseline-impl` —— 来自**阶段**轴（在其上继续搭建之前，先端到端实现被比较的方法）；`depends_on: []`
  - `01_mvp-verify` —— 来自 **证据** 轴（先以低成本验证核心主张）；它与旁边的单元是同辈，因为它是一个阶段的工作量、而非 `03` 里的某一条消融——它的 §1 non-goals 把这次低成本三路验证之外的全部消融交给 `03`；`depends_on: ["00"]`
  - `02_core-method` —— 来自**阶段**轴（搭建完整方法）；`depends_on: ["01"]`
  - `03_final-rets` —— 来自**阶段**轴（其余全部主张/消融）；`depends_on: ["02"]`
  - 再把 `02` 按**组件**递归成 `020/021/022`（见上面的组件示例）。
  - 执行顺序：`00 → 01 → 02 → 03`，其中 `02` 展开成自己的组件 DAG。
