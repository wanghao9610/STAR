# 扫描策略——领域证据从哪里来、读到多深

这是文献库来源策略的轻量姊妹篇：那份策略为已定的方法构建可核验的 `reference.bib`；本策略只为 2–4 个候选方向回答"多拥挤、谁最近、缺口在哪"，深度到摘要为止，每方向几分钟。它不产出 bibtex、不写逐篇笔记、不向 `metds/refs/**` 写任何东西——选题定下后，由深度调研（`star-refs-reviewer`）在胜出方向上把那些建起来，起点就是这些扫描表。

## 硬规则（继承自家族）

对话或 idea 文件中出现的每篇论文都转录自本次运行抓取的记录——标题、venue、年份、引用数取自记录，记录 URL 登记在行旁。记忆可以提议查询词和同义词；只有抓到的记录才能进文件。绝不"修正"记录写的内容，绝不补记录里没有的字段。搜索找不到的论文只证明它没找到——要紧就照实说，绝不把凭记忆想起的论文当作扫描到的来转述。不做需登录的抓取，不绕过 CAPTCHA。Google Scholar 不是来源（无 API、CAPTCHA 拦截）；下面这些端点本来就是它索引的对象。

## 来源——要广度，不按固定优先顺序

与文献库"首个命中即止"的优先顺序不同，扫描需要分歧：每个方向至少跑两个来源——只用一个索引估出的竞争激烈程度，是那个索引的假象。

1. **Semantic Scholar 搜索**——竞争激烈程度与引用信号的主来源：
   - `https://api.semanticscholar.org/graph/v1/paper/search?query=<q>&fields=title,year,venue,abstract,citationCount,externalIds&limit=20`
   - 加 `&year=<from>-` 做时效检索式（例如近 18 个月）。
2. **arXiv API**——走势与最新工作的主来源：
   - `http://export.arxiv.org/api/query?search_query=all:<terms>&sortBy=submittedDate&sortOrder=descending&max_results=20`（Atom）
3. **DBLP 搜索**——为前两者浮出的结果确认 venue：
   - `https://dblp.org/search/publ/api?q=<query>&format=json&h=20`
4. **网页搜索**——综述、workshop 页面、点出领域行话的博客。网页结果提到的论文仍须经来源 1–3 的记录才能进文件；有用的非论文页面（综述博客、榜单）可在竞争激烈程度说明中带 URL 引用，标注 `web context`。

## 查询词

每方向 2–3 个：任务说法、机制说法、论文标题惯用的"X for Y"说法——外加一个时效检索式（近 18 个月的投稿）读走势。从第一轮结果里偷词来磨第二轮——领域自己的词比你的词好搜。但这 2–3 条里必须有一条用这个方向**不**用的说法——邻近领域对同一机制的叫法、这个任务更早的名字，或者用基准名代替任务名——并在 §3 那一块记下试过哪些替代说法。全部检索式都从方向自己的词汇出发，用来判断某个方向有多拥挤是对的，用来发现被抢先则恰恰是错的：抢先回答了你这个问题的那篇论文，用的是你压根没想到要用的词。

## 每方向记录什么

- **扫描表**——8–15 篇，按标题去重（preprint 与正式版同时浮出时留正式版记录）：标题 / venue / 年份 / 引用数 / 一小句相关性 / 记录 URL。
- **竞争激烈程度说明**——逐年数量走势、涉及的 venue、看得出的团队、有无约 18 个月内的综述、可见的 benchmark 饱和迹象。此处允许 web context 链接，照此标注。
- **3 篇最接近的工作**——每篇一行：它做了什么，以及它自己的摘要**没有**声称什么。
- **表面缺口**——写成"扫描到的工作都没做什么"。摘要深度下，诚实的动词是"摘要显示……"。
- **深度行**——`abstracts`、`abstracts+intros` 或 `skipped`。

## 每个检索收集器的返回格式

Stage 3 的检索分派出去时,每份交办说明由主 agent 构建——收集器绝不自己攒。说明里带着:该方向的 slug 与一句话问题;已经构造好的 2–3 条检索式和那条时效检索式;本次运行的日期,供缓存前缀用（收集器绝不自己去看时钟）;已解析好的输出语言;以及按份数分给它的那份 host 速率配额,写成数字——3 个并发收集器时,Semantic Scholar 与 DBLP 每 3 秒 1 次、arXiv 每 9 秒 1 次。那份预算按 host 算,不按 agent 算:三个收集器各自遵守一遍,等于把每个 host 的真实速率翻了三倍。

返回:`direction`、`rows`（8–15 条,已去重,各自带 `record_url` 和它写下的缓存路径）、`recency`、`web_context`、`surprises`、`failures: [{host, error, retries}]`、`queries_run`——别的都不返回。禁止事项,原文照录:记录里没有的字段绝不补;绝不自行加深（加深是主 agent 的触发动作,否则 `depth:` 那一行就是假的）;绝不给方向打分,也绝不评价这个领域。抓到的原始内容缓存在本次运行自己的前缀下、按该收集器自己的方向 slug 划分（conventions §6.4）,除此之外不写任何东西。

主 agent 多担一条职责,范围很小:每个方向重开一份缓存下来的原始内容,逐字确认其中两行。

## 深度——默认浅，触发才加深

默认只读标题 + 摘要。仅在 (a) 用户指明某方向，或 (b) 某条缺口判断直接决定入选方向去留时加深。加深的含义：该方向 top-3 最接近的工作的 intro 与 related work 首段，从论文自己的页面读（arXiv abs/HTML、ACL Anthology、CVF open access 或项目页）——然后在该方向的深度行记 `abstracts+intros`。绝不悄悄加深，绝不声称比深度行更深的阅读。

## 缓存、限速与失败

- 每个抓取原始内容**先**缓存到 `wkdrs/ideas_<date>/raw/<direction-slug>.<source>.<ext>` 再使用——缓存即审计线索与续跑起点。
- 按主机串行：Semantic Scholar 与 DBLP 约 1 请求/秒；arXiv 约 3 秒 1 请求。这份预算属于整个会话、按 host 算，不是每个 agent 各有一份（规约 §6.9）——本次会话里如果已经跑过会抓取远端的 skill，它就已经花掉了一部分。HTTP 429 / 503 → 指数退避（2s、4s、8s），至多重试 3 次，然后记录失败并继续。限速绝不是改用记忆填坑的理由。
- 某方向的搜索全部失败时，报告为"扫描失败：<主机与错误>"——绝不填充，绝不悄悄拿回忆顶替。
