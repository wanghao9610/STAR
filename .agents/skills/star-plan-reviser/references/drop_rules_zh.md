# 丢弃一份计划，以及把它收回来

在本次运行是丢弃或恢复时读——参数或描述提出了它，或 Step 0 发现目标已经带着 `dropped:`。评审，以及由评审引出的每一次修订，都不读本文件。在一次完整评审**过程中**出现的丢弃不走这条路：它是 Step 4 的一个候选项，像其他候选项一样获批，写的是下面同样的三处。

丢弃记录的是你已经做出的决定，所以这条路不审查计划：Step 0 照常解析目标，下面四步取代 Step 1–6，Step 7 照常汇报，且不写审查报告。把运行带到这里的是描述（规约 §7.12），所以在读任何东西之前先用一行说明这次走的是哪条路——描述读错了，代价就是这一行，而不是一处改动。

1. **读出什么会变暗**，只用开场那次摘要——不派收集器，不读 run 正文：目标每一个后代及其 `exec_status`、它们的 run 本来欠着的后续（代码审查、实验分析）、其下任何未合并的 `branch:`、现存的 `worktree:` 或未勾选的红线命令，以及任何 `depends_on` 指向该目标或其某个后代的、活着的叶子。
2. **把这份清单摆出来，只问一次**——每个后代一行、每处未了结一行——在同一个问题里确认丢弃与那一句原因——描述里写了理由就用原话，没写就在这里问。这是强制确认点（规约 §7.7）：任何参与度档位都要问，`low` 也不例外，绝不与别的东西打包。没有原因就不丢弃。
3. **写 `references/revision_rules_zh.md` 点名的那三处**——目标上的 `dropped: <日期> — <原因>`、父计划 `## Sub-plans` 那一行的 `— dropped <日期>` 标记、一条 `## Revision History`——并更新 `updated`。不编辑任何后代：它们靠继承变暗。
4. **汇报**什么变暗了、以及丢弃没有解决的事——现在指向已丢弃节点的依赖边，以及还留在磁盘上的分支、worktree 或红线命令——然后照 Step 7 提出提交提议。

把节点收回来是同一条路，只是清除字段而不是写入——把运行带到那里的同样是描述——并在提问之前多一道检查：任何祖先都不得处于已丢弃状态，否则继承会让它继续是暗的，而被清掉的字段反倒像个 bug。它的 Revision History 条目写明这个方向为什么重新活了过来。

在一次完整审查**过程中**浮现的丢弃不走这个模式——它是 Step 4 的一条候选，像别的候选一样逐条批准，写的是同样那三处。

## 一次丢弃写什么、不动什么

一个已经放弃的方向——整条流程应当不再统计、不再推荐、不再在它上面继续搭东西。这个字段只写在做出决定的那个节点上，别处一律不写：所有 skill 都按继承来读它，所以一行就带走整棵子树；日后在这个节点下面新增的子节点也一并被丢弃。

| 项目 | 规则 |
|---|---|
| 取值 | `dropped: <YYYY-MM-DD> — <一句话原因>`，日期取自系统时钟（规约 §4）。完整交代——试过什么、什么终结了它、由什么取代——写进同一次会话的 `## Revision History` 条目。 |
| 批准方式 | 本 skill 自己的一条候选，单独问：提问时点明随它一起变暗的东西——这个节点、每一个后代，以及它们的 run 本来欠着的后续。它**不**属于那些要转交给 star-plan-coach 的 strategic 候选：丢弃一个方向记录的是已经做出的决定，而选择由什么来取代它才是那场重新做计划的对话。 |
| 编辑范围 | 这个字段，外加父计划 `## Sub-plans` 那一行上的 `— dropped <date>` 标记。别的一概不动——父计划保留它的 `children:` 条目（删掉这个链接会让子文件的 `parent:` 悬空，也抹掉"这条路试过"的记录），每一个后代保留自己的 frontmatter，包括 `exec_status: done` 和它的 `exec_runs`。 |
| 向上汇总 | 往根计划 §5 的"已否定的路线"追加一行：这个节点、一句话说明什么结果否定了它、下次不要再走哪一段。这个节点自己的修订历史留着完整交代，但整棵子树已经变暗，此后没人会打开它——根计划那一行才是日后写 limitations、答审稿人时会读到的。 |
| 前缀 | 被丢弃的兄弟仍然占着它的编号；下一个子计划取下一个空位（规约 §5.6）。 |
| 取消丢弃 | 就是清除这个字段，和别的候选一样。先确认没有任何祖先处于已丢弃状态——否则继承会让这个节点继续是暗的，而被清掉的字段反倒像个 bug。 |
| 它没有解决的事 | 已丢弃子树下未合并的执行分支、现存的 worktree、未勾选的红线命令。在最终汇报里点名：记录的抢救与分支的废弃走 star-plan-executor（规约 §11.6），绝不在这里做。 |

两条入口，同一条规则。表达放弃这个方向的描述把运行带到丢弃那条路（见 `SKILL_zh.md`），它跳过审查，因为决定已经做出；在一次完整审查中浮现的丢弃则是 Step 4 的一条候选。两者写的都恰好是上面那三处。

`exec_status: abandoned` 仍是一个叶子的执行结局。`dropped:` 说的是节点：它把这个节点连同其下的一切移出计数、覆盖检查和下一步动作。一个叶子可以同时带着两者，树上渲染的是计划级的那个字段。
