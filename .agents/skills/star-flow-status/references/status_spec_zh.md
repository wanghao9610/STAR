# 状态规则 —— 如何读整条流程、如何挑下一步

这里的一切都靠读文件得到。绝不写任何东西。

计划树里的节点有先后次序，所以走一遍图。覆盖检查刻意做得很薄——只看存在性与新鲜度。优先顺序在两者之上挑出唯一的建议；未识别文件行查出产物改名。

## 限定范围 —— `PLAN_NAME` 收窄了什么

解析照规约 §5，只有一处不同：本 skill 从不提问，所以 §5.2 的"问一句"必须在纸面上有解。

- 数字前缀按第一个 `_` 之前的数字串**精确**匹配：`1` 解析到 `1_<slug>_plan.md`，绝不连带 `10_…`。两棵同 slug 的根正是靠这一条区分开，所以前缀只命中一份文件时，slug 本身有歧义也照样解析得出来。
- 参数命中**多于一份**计划文件时，每一份都各占一个根行渲染；回复第一行点明歧义，并给出每份对应的无歧义命令。
- 参数一份都没命中时，不渲染任何树：列出最接近的候选（前缀 + slug + 一句话状态），到此为止。

解析定下来之后，范围管整条回复：树只渲染这棵子树，三个计数在它上面算，覆盖检查只查它的产物，下一步也只在它里面挑。范围之外的计划只是被读到——没有它们 `parent:` 解析不出来——读完搁下。有两样东西仍覆盖全项目，并在各自定义处写明：未识别文件行，以及必须点名子树之外父计划的失配标记。`PLAN_NAME` 点名已丢弃（见下）的节点时，照常解析、照常渲染——它的文件在 `metds/plans/dropped/` 下，解析连同活跃目录一起读：这个字段收走推荐，不是主动查看。

## 每个文件读什么

每个计划文件的 frontmatter——`metds/plans/<prefix>_<slug>_plan.md`，以及丢弃搬移后 `metds/plans/dropped/` 下的同名文件——可能带：

- 总体计划（来自 coach）：六节的 `status:` 映射、可选的 `finalized:`、`updated:`，以及（拆解后）`children:` + 正文的 `## Sub-plans` 索引。索引里可能有**概要行**——`- （概要）` / `- (outline)`（规约 §0），还没展开成文件的单元：逐节点数一数，它们是叶子计数看不见的既定工作；预期顺序也从索引读（概要单元没有前缀，不在任何 `depends_on` 里）。
- 子计划（来自 decomposer）：`parent:`、`prefix:`、`traces_to:`、`depends_on:`、六个执行章节的 `status:` 映射、`updated:`。
- 已执行的叶子（来自 executor）：`exec_status:`（`pending`/`in_progress`/`done`/`blocked`/`abandoned`）——`done` 与 `abandoned` 都是**终态**：这样的叶子不再欠任何东西，也不会卡住下游的确认点。`skipped`——这个取值已经没有任何 skill 会写——同样读作终态，这里是它唯一还被认得的地方。`abandoned` 记录被自身 kill-criterion 判死的方向；理由写进计划的 `## Revision History`，让负结果留存；`exec_runs:`——一个只追加的 `wkdrs/<run>/` 目录列表，最新的在最后，**最后一项就是当前 run**；更早的条目是重跑（换个 seed、修掉一个 bug），留作记录。**run 名先在 `wkdrs/` 解析，再在 `wkdrs/dropped/` 解析**——丢弃把子树的 run 目录搬到一边而不改写这份列表，所以只有两处都找不到的条目才算孤儿。此字段出现前写的计划带单个 `exec_run:`；当作只有一项的列表读——executor 下次写入时会迁移它。
- 任何节点，在 `star-plan-reviser` 丢弃它之后：`dropped: <YYYY-MM-DD> — <一句话原因>`——这个方向已经放弃。**它靠继承生效，绝不向下复制**：一个节点算作已丢弃，是因为它自己带这个字段**或任一祖先带**，所以这个决定只写一次，写在做出决定的节点上；日后在已丢弃节点下新增的子节点也一并算已丢弃。完整交代在该计划的 `## Revision History`；父计划保留其 `children:` 条目与 `## Sub-plans` 索引行，并在那一行加 `— dropped <date>` 标记。丢弃同时把子树的文件搬到了一边，文件名不变——计划文件搬到 `metds/plans/dropped/`，run 目录搬到 `wkdrs/dropped/<run>/`，`tasks/<plan-name>/` 搬到 `tasks/dropped/`，启动脚本搬到 `execs/scpts/dropped/`——任何指针都没改写：`exec_runs`、`children:` 和每一条被引用的路径保持原文，按上面的两处解析规则找到实际位置。

对带 `exec_runs` 的叶子，另读当前 run 的 `wkdrs/<run>/EXEC_LOG.md`：步骤状态表（数 `done` / 总数、注意任何 `blocked`）、"待用户执行（红线）"清单、以及 Notes 里的任何"方向性信号"。加了 `--slim` 时，超过六行的表已经数好了——`[tally] 8 data rows | c3: done×7, blocked×1` 一行里就是这个计数和这个提醒；写成 `N distinct` 的列装步骤名或日期，不会是状态。无论表怎么处理，未勾选的待办项与方向性信号都原样打印，所以红线规则和 Step 3 需要的东西不会藏在计数后面。日志 frontmatter 的 `branch:` / `merged:` 随这次读取一并带回（规约 §11）。

扫描调用还会列出 执行分支（规约 §11）。某个分支匹配到一个叶子、而这个叶子的 run 目录在当前 checkout 里不存在，就是一次正在该分支上进行的 run：基础分支始终是准据（§11.3），所以这边叶子的 frontmatter 读作未完成是对的——渲染这个叶子时点出分支名，不是只当它 pending；分支侧状态只在下面某一行需要时才读，用只读的 `git show <run>:wkdrs/<run>/EXEC_LOG.md`（§1 的只读清单涵盖 `show`）。worktree 清单同样读法（§11.7–9）：路径以某个 run 名结尾的树就是那个 run 的家——渲染叶子时挨着分支一并点出——既没有叶子、也没有 run 记录认领的树，不归我们提。

覆盖检查所需的其它已登记产物，只按"存在与否"和各自那一个日期字段读——绝不读它们的正文。产物登记表见规约 §8；下面覆盖表逐行写明用哪个字段。

## 节点分类

- **根** —— 无 `parent:`（一份 coach 计划）。前缀 1 位。
- **内部** —— 有非空 `children:` 列表（被进一步拆解）。
- **叶子** —— `children:` 为空或不存在。只有叶子可执行。

按 `parent:`（权威）重建父子链，而非按前缀。父之下，子按 `depends_on` 拓扑排序；缺失或有歧义则回退到前缀升序。

## 状态符号图例（每节点一个）

- `✔` 完成 —— 总体计划节点设了 `finalized:`；叶子 `exec_status: done`。
- `✖` 被判死 —— 叶子 `exec_status: abandoned`：这个方向跑过，被它自己的 kill-criterion 判死。和 `✔` 一样是终态，也刻意与它成对——「做成了」还是「被判死」是读者扫一眼就该拿到的，所以不交给状态文字（`exec abandoned`）和进度汇总那一行（`abandoned 1`）去说，它们只是再说一遍。
- `◐` 进行中 —— 部分章节 `done`/`in_progress`，或六节全 `done` 但未设 `finalized:`（评分表还没跑），或叶子 `exec_status: in_progress`（有日志则显示 `k/n` 步）。
- `○` 待办 —— 尚未开始（`exec_status` 缺失/`pending`，或全部章节 `pending`）。
- `⊘` 受阻 —— 叶子 `exec_status: blocked`，或其 `depends_on` 未满足的叶子。
- `⏸` 待用户 —— EXEC_LOG 里有未勾选"待用户执行"红线命令的叶子。
- `⚠` 需关注 —— **太粗、无法直接执行**，有两种情形：其自身 §3 任务分解 / §5 完成判据大量 `[TBD]` 或 `【待定】` 的子计划叶子（两个记号一并计数——中文计划写的是后者），**或**带着 `finalized:` 却没有 `children:` 的总体计划——从未被拆解过，因而算作叶子（规约 §5.4），执行器会拒绝它。这是唯一的定义；第 3 层的资格判定一律依它，与生命周期规则最终渲染出哪个状态符号无关 → 建议 `star-plan-decomposer`。
- `⊗` 已丢弃 —— 节点自己带 `dropped:`，或它的某个祖先带。带字段的那个节点显示 `dropped <date> — <原因>`；它下面的一切显示 `dropped with <该节点前缀>`。

**每节点只有一个状态符号，生命周期状态优先。** 同时符合生命周期状态符号和 `⚠` 的节点，取生命周期的那个：finalized 之后又被改过的根仍是 `✔`，done 但没有 run 的叶子仍是 `✔`。失配属于失配段——绝不让一个失配标记盖掉节点真实所处的状态，否则这棵树就不再表示它字面的意思。`⏸` 和终态 `exec_status` 可能同时落在一个叶子上——某次运行留下未勾选的红线命令，之后叶子被关掉。终态优先，理由和生命周期状态符号压过 `⚠` 是同一个：叶子渲染成它的终态符号（`✔`，方向被判死时是 `✖`），那条仍在案上的命令交给失配段。`⏸` 用于 `exec_status` 尚未进入终态的叶子。

**`⊗` 压过上面每一个状态符号，`⚠` 也不例外。** 已被放弃的节点不再有任何人会去处理的进度，所以无论它的章节和 `exec_status` 说什么，它都渲染成 `⊗`——原状态保留在同一行的括号里（`dropped with 04 (exec done)`），因为子树被丢弃前走到了哪一步，正是保留这份记录的全部理由。优先顺序的任何一层也都不会挑起已丢弃的节点，`⚠` 那条「先去拆解」的路同样不会：放弃掉的方向不是待办。丢弃**不**收走磁盘上还在的东西——未合并的执行分支、现存的 worktree、未勾选的红线命令，各自照旧在下面的失配段里标出来。

`## Sub-plans` 里还有概要行的父节点，把它们写进自己的状态文字——`已拆解 2/4 个单元，2 个在概要`——绝不为它们单开一行：概要单元没有文件，所以不是节点。已展开叶子全到终态而概要行还在的父节点没有完成——计数行和下一步动作负责把这一点说出来。

每个叶子行显示其 `depends_on`、（正在执行时）`k/n` 步，以及——当前 run 记录了执行分支时——它的合并状态：`<run> unmerged`，日志写明之后则是 `merged`；run 还记录着现存 `worktree:` 时，后面加 `(wt)`。示例：

```
0_open-vocab-det-seg            ◐  总体方向 6/6 done, 已拆解 (5 个子计划)
├ 00_baseline-impl              ✔  exec done                        依赖: —
├ 01_mvp-verify                 ✔  exec done                        依赖: 00
├ 02_core-method                ◐  exec 进行中 2/5 步               依赖: 01
│ ├ 020_desc-generation         ✔  exec done                        依赖: —
│ ├ 021_set-matching            ◐  exec 进行中 2/4                  依赖: 020
│ ├ 022_det-seg-heads           ○  exec pending                     依赖: 020, 021
│ └ 023_contrastive-head        ✖  exec abandoned                   依赖: 020
├ 03_final-rets                 ⏸  待用户 (1 条红线命令)            依赖: 02
└ 04_alt-matcher                ⊗  dropped 2026-08-11 — 被 02 取代
  └ 040_hungarian-baseline      ⊗  dropped with 04 (exec done)      依赖: —
```

上例中的根是 `◐` 而非 `✔`，因为它的 `finalized:` 未设——六节全 `done` 本身并不能关闭一个总体计划节点，评分表还得跑。总体计划节点的状态符号只报告**它自己**的状态，绝不报告其子树：一个已 finalized 的根即使下面的子树只执行了一半，仍是 `✔`；子树没做完由进度汇总来说。上例里 `04` 是丢弃写在其上的节点，`040` 自己不带任何字段，读作已丢弃是因为它的祖先是——这个字段绝不向下复制。`023` 是另一种终态：它跑过，被自己的 kill-criterion 判死；和那对已丢弃的节点一样，它也退出执行进度的分母。

树的大小不改变这条规则。六十个节点的项目就打六十行；可以缩短的是每行状态文字——`◐ 2/5` 就是完整的一行——绝不是行的集合。把一棵子树换成一句话（"8 个叶子全部完成"），就丢掉哪个叶子是哪个；两次运行对同一棵子树给出不同概括，读者拿文件根本没法核。

## 进度汇总（三个数）

若这次运行被 `PLAN_NAME` 收窄过，三个数都在限定范围内算（见上面限定范围一节），不按整个项目算。

**已丢弃的节点连同其子树在这三个数之外，分母也不算它**——放弃过一个分支的研究因此仍能读成「全部完成」。改在三个数下面用一行报出来：`已丢弃: 04 之下 2 个节点 —— 不计入上面三个数`。

1. **总体方向完整度** —— 各总体计划（来自 coach 的根/内部节点）里：`done` 的章节数 /（6 × 总体计划数）。注明哪些未 `finalized:`。
2. **拆解覆盖度** —— 内部节点（已拆解）vs 被标 `⚠` 的粗糙叶子（定义见上文）。`## Sub-plans` 里还有概要行的节点算部分拆解：把它连同剩余数写在数字旁边（`0：2 个单元在概要`）。
3. **执行进度** —— 叶子 `exec_status: done` / 总叶子数；以及所有有 run 的叶子 EXEC_LOG 步 `done` / 总数之和。永远不会再跑的叶子不进分母，免得这个比值永久卡在 100% 以下：`abandoned` 和已丢弃的叶子一样退出分母，两者都在数字旁点名（`已丢弃 2，abandoned 1`），保持看得见。

## 覆盖检查（已完成的工作还差什么）

每一行**必须全部条件同时成立**才触发。其余一律沉默——特别是：还在跑的 run 什么都不欠，未 `done` 的叶子对下游什么都不欠。**任何一行都不会在已丢弃的节点、或它下面的任何东西上触发**：放弃掉的方向不欠任何东西。第 8、13 行里的「每个叶子」只数活着的叶子——已丢弃的叶子不是没做完的叶子。触发的行报一句话：欠什么、欠在哪个节点或哪个 run、以及补上它的命令。限定范围：给了 `PLAN_NAME` 时，只检查属于该子树的产物（以及从其叶子 `exec_runs` 可达的 run）。

有七行特别容易做错：

- **第 4 行读日志自己的日期，绝不读文件 mtime。** 扫描给每个 run 打的 `[dates seen]` 行收集日志里的每一个日期——frontmatter 的 `updated:`、每条 `model_trail`、步骤表里的任何日期——其中最新的那个就是这个 run 最后一次动过的时间，正是审查日期该比对的东西。步骤表的日期列可有可无，这一行不依赖它。mtime 一概不看：它会因一次 checkout 或备份而变动。
- **第 7 行是精确对账，不是拿 mtime 猜。** `star-metd-summarize` 逐个源计划记下"读取时该计划带的 `updated` 值"。拿那个记录值和计划当前的 `updated` 比——绝不用文件 mtime，它会因无关的事变动（一次 checkout、一次格式化）。
- **第 8 行要等整棵树。** summarizer 编译的是已确定的方法——只要还有叶子未执行、或总体计划未定稿，它自身的就绪门槛就不会放行——所以覆盖检查只在每个叶子都 `done`、每个总体计划都带 `finalized:` 之后才推荐它，无论更早完成了多少叶子。
- **第 10 行只对已经在记 digest 的项目触发。** 与第 2、7、8 行不同，产物缺失并不触发它：digest 是工作辅助，不是研究欠下的交付物，从没跑过 `star-expt-digest` 的项目并不欠账。所以这一行只问“已有的序列有没有落后”。“最新那份序列 digest”指 `mode` 为 `incremental`、`window` 或 `all` 的最新一份——`plan` 模式的 digest 是回溯性阅读，它的 `covers.through` 不能当作续接点，这与该 skill 自己的 `scope_spec_zh.md` 对上次覆盖日期的定义一致。
- **第 14 行去记录所在的地方读。** 在分支 checkout 上，记录就在工作区里；从基础 checkout 看，执行分支清单是触发器，只读的 `git show` 是读取手段。它的审查条件是分支侧的 `CODE_REVIEW_<date>.md`；一份都没有时，改由第 3 行在分支侧状态上触发，而且它在这一档里本来就排在前面。住在 worktree 里的 run，工作文件在树里，但已提交的记录同样应答这里的 `git show`；合并本身仍走 executor，它会在树里续跑（§11.8）。
- **第 1 行是这里最弱的信号。** `star-plan-coach` 把种子记在计划 §1 的正文里（"Seeded from `metds/ideas/<slug>_idea.md`"），不是 frontmatter 字段，所以检测靠 slug 匹配加上对想法文件名的正文 grep。一份由想法长出来、后来改名的计划会被读成"未立项"。只有第 1 行触发时，说明这条检查是启发式的。
- **第 15 行是个粗筛，不是对账。** 第 7 行比的是记录下来的那个 `updated` 值；分析报告没有这样的记录值，所以这一行只能比日期先后、会多报：改一句 §1 措辞和调低一个 §5 阈值触发得一样。这是有意的——reviser 的 `exec_status` 复位只是一次提议；提议被拒，就留下一个 `done` 叶子，它最新那份分析打的是计划已不再写的判据。比的是计划的 `updated` 与报告文件名里的*日期*，永远不看文件 mtime。重新打分确认什么都没变，代价是一份报告；不这么做，代价是一个没人追得回判据的判定。

## 下一步动作（唯一的建议）

自上而下按优先顺序走，取**第一个**能给出候选的层。其余欠账留在覆盖检查里，此处不重复。

1. **待用户** —— 某个 `⏸` 叶子有未勾选的红线命令。写明该命令；只有用户能清掉它，在那之前下面几层都不重要。只有一件事排在这条命令之前：该 run 目录里还没有 `CODE_REVIEW_<date>.md` 时，先推荐 `star-code-reviewer <叶子>`，把待跑命令紧挨着写在它下面——bug 在算力烧掉之前最便宜，而第 3 行覆盖不到这里，因为该叶子还不是 `done`。这两条归属不同：审查属于那八个 agent 可以自己启动的 skill，是接下来真正要跑的那条（见下）；待跑命令则打印出来，归用户。
2. **已完成工作的欠账** —— 落在已完成之事上的覆盖检查触发项，按"欠账滚得多快"取：回填（第 9 行）→ 审查（第 3、4 行）→ 合并（第 14 行）→ 分析（第 5、15 行）→ 生成结果汇总表（第 6 行）→ 凝练方法（第 7、8 行）→ 文献（第 2 行）→ digest（第 10 行）。第 9 行排在最前，因为它把其余欠账一起藏起来：在被接入项目里已完成的叶子拿到 `exec_status: done` 之前，第 3、5 行根本无法在它们身上触发，而第 3 层还会建议你去执行一个成果早已在磁盘上的叶子。合并（第 14 行）紧随审查之后：未合并的分支卡住每一个依赖它的叶子（规约 §11.3），也让自己的记录在基础 checkout 上看不见——这两笔代价都随围绕它执行的每一个叶子越滚越大。除第 1 行外的每一条覆盖行都能在这一层取到；第 1 行归第 4 层，因为"开一个新题目"不是欠账。digest 排在最末，也是这里唯一一条推迟不付出代价的欠账：每份 digest 都由留在磁盘上的分析报告重新编译，而且无论隔多久，序列都不会出现缺口。文献虽然在流程里靠前，却排在倒数第二：缺综述的代价是写作时的定位，而未审代码的代价是压在它上面的每一个叶子。欠账优先于进度，因为它会滚：每多执行一个建立在未审代码之上的叶子、每多引用一次过期结果汇总表里的数字，将来要返工的面就更宽。而下一个叶子不会过期。
3. **下一个可执行叶子** —— **执行顺序里最靠前**、且同时满足以下全部的叶子：`exec_status` 不是终态（`done` / `abandoned`）也不是 `blocked`；它自己和它的祖先都没被丢弃；其 `depends_on` 里每个前缀都能解析到一个 `exec_status` 为 `done` 的兄弟；它不是 `⚠` 粗糙叶子（若是，改为建议先拆解它）；且没有现存的 执行分支与它匹配——这样的叶子是在那个分支上进行中的一次 run（归第 14 行或普通的续跑管），不能当新叶子开跑，理由那一句要写明。"执行顺序" = 由 `depends_on` 得到的拓扑序，以前缀升序破平局，深度优先遍历（使某个已拆解节点自己的叶子排在它后面的兄弟之前）。输出 `→ 下一个: star-plan-executor <前缀或 slug>`。**没有叶子够格、而某个在活节点的 `## Sub-plans` 里有一条概要行、其索引顺序里的前置单元都已到终态时，下一步就是展开它**：输出 `→ 下一个: star-plan-decomposer <父计划前缀或 slug>`，理由里带上该单元的标题——这是只认斜杠调用的 skill，所以这条命令永远打印给用户，agent 绝不自行启动。
4. **已定稿但未立项的想法** —— 即覆盖检查第 1 行。只有当树全部完成且不欠任何东西时才会走到这一层——那正是开下一个题目的时候。

给一句话理由和命令。 点名的每一条命令各判各的，第 1 档那一对也不例外：落在那八个 agent 可以自己启动的 skill 上、且目标已经定死的那条，就是接下来要跑的东西，而不只是打印出来的东西——拾起发生在本次运行结束之后，本 skill 自己不启动任何东西（规约 §10）；而紧挨着它的那条红线命令照旧打印出来，等用户。若各层都给不出候选，说清是以下哪一种：不欠任何东西且每个叶子都已了结——整项研究已经完成，转交给 `star-code-release`，或用 `star-idea-storm` 开下一个题目；某个未满足的依赖（写明）；需拆解的粗糙叶子；或 `metds/plans/` 为空（转交给 `star-plan-coach`；连想法也没有则 `star-idea-storm`）。范围内每个节点都已丢弃时，这本身就是答案：说明这个范围里没有活着的东西，若有最近的活着的范围就点出来。

## Drift / 一致性标记（只报告，绝不修复）

- **可能过期的子计划** —— 某子计划 `updated` 早于其父计划 `updated`（父计划在拆解后被改）。建议 `star-plan-decomposer <父计划>` 对账。
- **悬挂链接** —— 某 `children:` 项找不到对应文件，或某计划文件的 `parent:` 指向不存在的文件、或未被其父计划 `## Sub-plans` 索引列出。
- **坏依赖** —— 某 `depends_on` 前缀解析不到现存兄弟，或依赖图里有环。
- **孤儿 run** —— 某个 `exec_runs` 条目的 run 目录在 `wkdrs/` 与 `wkdrs/dropped/` 两处都不存在，或某 EXEC_LOG 的 `source_plan` 与叶子不符。
- **done 但没有 run** —— 某叶子 `exec_status: done` 却没有 `exec_runs`（或其 run 目录已不在）。覆盖检查第 3、5 行都要求 run 目录存在，所以这样的叶子对下游悄悄什么都不欠；改在这里标出来——手工标成 done 的叶子要么是记账疏漏，要么是 run 被删了。
- **终态但红线命令未清** —— 某叶子处于终态 `exec_status`，其当前 run 却还带着未勾选的「待用户执行」命令。要么是命令跑过没勾，要么是叶子带着它被关掉。图例把这个叶子渲染成 `✔` 或 `✖`，所以这一行是读者唯一能知道那条命令还挂在案上的地方，优先顺序里的待用户那一档也就不再挑它。
- **finalized 之后又被改过** —— 某总体计划节点的 `updated` 晚于其 `finalized:`：那个 `✔` 已经不再有评分表背书。建议 `star-plan-coach <slug>` 重新关闭它。
- **概要行与文件重复** —— `## Sub-plans` 里某条概要行的单元，同一索引里已有展开的子计划条目盖住了：这个单元既是行又是文件，计数会把它算两次。建议 `star-plan-decomposer <父计划>` 去对齐。
- **分支遗留** —— 列出的某条分支匹配不到任何叶子、却被某次 run 的 `branch:` 记录点名（清单按名字形状匹配，既没有叶子、也没有 run 记录认领的分支不是本项目的——别动它）；某个日志已带 `merged:` 的 run，其分支却还在（删除被拒或被推迟——只标记）；或某叶子当前 run 记录着 `branch:`，这个分支却已不存在（分支从 run 底下被删——executor 把这当作 blocker）。
- **worktree 遗留** —— 列出的某棵树，其 run 的日志已带 `merged:`（移除被拒或被推迟——只标记）；某次 run 的记录点名 `worktree:`，这棵树却已不存在（树从 run 底下被删——executor 把这当作 blocker）；或列出的某棵树既没有叶子、也没有 run 记录认领——不是本项目的，别动它（§11.9）。

- **活着的叶子依赖了已丢弃的节点** —— 某个 `depends_on` 前缀解析到的节点已被丢弃。这条依赖永远满足不了，于是这个叶子会一直读作 `⊘` 受阻，而优先顺序一声不响地从它旁边走过去。两边都点名，把这条边交给 `star-plan-decomposer <父计划>` 重画——若这个依赖方本来也该一起丢弃，则交给 `star-plan-reviser <叶子>`。
- **已丢弃，但活儿还在磁盘上** —— 某个已丢弃节点的当前 run 还记录着未合并的 `branch:`、现存的 `worktree:`，或未勾选的「待用户执行」命令。丢弃收走的是推荐，不是资源：这些东西放着不管仍然有代价。答案不再是合并——抢救记录、废弃分支走 `star-plan-executor`（规约 §11.6）。这样的 run 留在活跃路径上也是正当的：丢弃把它的搬移暂缓到这些了结之后。
- **已丢弃，文件却不在该在的地方** —— 某个已丢弃节点或后代，其计划文件仍直接躺在 `metds/plans/`，或其 run 目录、`tasks/<plan-name>/`、`execs/scpts/<run>.sh` 仍在活跃路径上——搬移规则出现之前丢弃的项目，或一次中断的丢弃；被上一条暂缓搬移的 run 属于上一条，不算这里。反向同样触发：`metds/plans/dropped/` 下有计划自己和任何祖先都不带 `dropped:`。把补完搬移的命令原样打印出来——`git mv metds/plans/<文件> metds/plans/dropped/`、`mv wkdrs/<run> wkdrs/dropped/`，存在时再加 `tasks/`、`execs/scpts/` 两处的对应命令——反向的则转交 `star-plan-reviser <节点>`；本 skill 从不动手。

本段保持简短；无任何标记时整段省略。

## 未识别文件行（查出产物改名的那道检查）

上面的覆盖检查按文件名匹配产物。如果某个产出方 skill 改了写出来的东西，覆盖检查会悄悄不再触发那一行——这是一次漏报。这一行把那种失败翻转成看得见的。只数**报告形**文件，让 run 产物（权重、图、原始日志）绝不进来：

- 直接位于某个 `wkdrs/<run>/` 目录下的 `*.md`，且文件名不是 `EXEC_PLAN.md`、`EXEC_LOG.md`、`CODE_REVIEW_<date>.md`、`EXPT_ANALYSIS_<date>.md`、`REVIEW_<date>.md`；
- 直接位于 `wkdrs/` 下四个已登记非 run 目录里的 `*.md`，且用了 §8 未在该处登记的名字：`wkdrs/reviews/`（没有 run 时走的那条共用退路目录）登记 `code_<scope>_<date>.md` 与 `<prefix>_<slug>_<date>.md`（数字前缀）；`wkdrs/env_<name>_<date>/` 目录登记 `ENV_REPORT.md`；`wkdrs/digests/` 登记 `EXPT_DIGEST_<date>.md` 与 `MODEL_LEDGER.md`；`wkdrs/results/` 登记 `results.md` 与 `results_<slug>.md`。其余任何 `wkdrs/` 子目录一律按上一条当作 run 目录审计——`wkdrs/dropped/` 除外，它本身不是 run 目录：审计的是它里面的每个 `wkdrs/dropped/<run>/`；
- `metds/` 顶层的 `*.md`，其主名不属于 `overview`、`framework`、`dataset`、`training`、`evaluation`、`codearc`、`adopt`，**且**带有 `type:`、`generated:`、`sources:` 三者之一。这三个字段合起来是"编译文档"的指纹：按三者取并、而不是只认 `type:`，能抓到既改了输出名又丢掉 `type:` 的产出方；而 `metds/` 下手写的笔记三者皆无，保持沉默。

不要递归进入子目录（`analysis/`、`raw/`、`refs/`）——各产出方自己的工作空间，本就不在产物登记表内。报一行：`⚠ N 个未识别的报告文件` + 至多三个路径。N 为 0 时整行省略。这是命名不一致，不是对文件本身的判断：规约 §8 的产物登记表和磁盘上的实际情况已经分叉，两者之一需要更新。
