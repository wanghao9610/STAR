# 编排规范

本 skill 如何组织勘察与迁移工作。对应的规范：executor 的 `agent_dispatch_spec.md`——同一套思路，适配到勘察与迁移场景。协作工具可用、且委派确有帮助时就委派有边界的分组或组；没有这个条件才本地执行。委派时调用你的子代理工具：勘察分组使用只读子代理，迁移组使用可写子代理。两个确认点、验证、提交与失败后的恢复始终由主 agent 负责。

## 角色

- **主 agent（架构师）**——制定方案、执行两个确认点、划分工作、亲自重跑检查、每组提交一次、恢复失败的组。
- **勘察分组**——只读（`survey_spec_zh.md`）；默认本地顺序执行，有边界且独立时可委派。
- **迁移组**——每组一个工作单元；无论本地执行还是委派，写权限仅限本组文件。

## 迁移分组

1. 只取确认点 2 批准的条目。
2. 分组时保证**文件所有权互不相交**——而且要算出来、不是假定：对每个候选项跑 `grep -rln "<该模块带点号的完整 import 路径>" ${CODE_NAME}`，这些命中加上该项要移动的文件，**就是**它的所有权集合；集合相交的项并成一组。用带点号的完整路径而不是裸模块名：并多了只损失并行度，绝不损失正确性。需要修 import 的位置恰恰是迁移者派发之后才发现的，所以这件事不能等到那时候——不先算，两个并行的迁移者就可能改到同一个文件，按组 `git restore` 也就失效了：任何文件不得同属两组（被移动的文件和因移动而需改 import 的文件都算）。两条目争用同一文件时，合并成一组。
3. 沿 import 链把组按上游优先排序。可委派时，相互独立的组可并发；否则逐组执行。
4. 每组前置条件：其涉及路径在 git 中是干净的（没有未暂存/未提交的改动）。

## 工作交办说明（每个迁移组，本地或委派皆同）

每组的执行绑定：

- **范围**——本组迁移条目原文照录，外加："**只做**这些条目；不顺手改别的，不做条目之外的重命名，不做风格美化"（AGENTS.md §3）。
- **文件**——它拥有的明确文件清单（被移动的文件 + 需修 import 的位置）。
- **操作性质**——移动/重命名及其连带的 import/路径修正；不改任何行为。
- **运行时**——主 agent 已经解析好的解释器绝对路径，逐字给它；迁移者不再自己去读 `.env`。`python -m compileall -q` 永远可用（无需依赖）。缺包是它要返回的 blocker，绝不是它自己去装的东西（conventions §3.5）。
- **边界**——只跑轻量验证。红线上的迁移项**备好命令返回，绝不执行**；绝不安装或改动环境（§3.5）——缺包是它要返回的 blocker。
- **返回**（结构化）：`changed`——文件，每项一行；`ran`——命令 + 结果，或 `none`；`check`——本组绑定检查的结果，`pass`/`fail` + 证据；`blockers`——或 `none`；`handoff`——为用户备好的红线命令，或 `none`。

## 每组完成之后

**带 handoff** → 把命令移进迁移记录的待用户执行区，该项到此为止；不要跑它。

**主 agent 亲自重跑验证**——绝不信任自报的 `pass`（包括自己的：重新执行检查，不凭记忆）：

1. `python -m compileall -q ${CODE_NAME}`；环境可用时再做 import 扫描与快速测试。
2. **通过** → 提交 `star-code-architect: migrate <ids> — <summary>`，只暂存本 skill 涉及的路径；更新迁移记录。
3. **失败** → 把失败信息回传，有限次重试（≤2）。仍失败 → 恢复该组路径（`git restore` / `git checkout -- <paths>`），在 `codearc.md` §6 把其条目标 `blocked` 并记下 blocker，继续其他组。

## 红线（本 skill 版本）

以下操作绝不擅自执行——准备好确切命令、写进汇报、移交用户：

- 涉及 CUDA/C++ 编译的环境构建（带扩展算子的 `pip install`、含此类依赖的 `conda env create`）。
- 超过约 1 GB 的下载（权重、数据集）。
- 完整测试套件、benchmark，以及任何训练。

纯 Python 的轻量安装仅在用户当场明确同意后才可执行。拿不准就当重操作处理。
