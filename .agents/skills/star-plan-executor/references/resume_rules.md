# Resume Rules — a run already recorded is picked up, not planned again

Read at Step 0 where the digest gives this leaf a non-empty `exec_runs`, where a branch named for it exists, or where `wkdrs/<run>/` is already on disk. A leaf with none of the three is a fresh run and never reads this file.

- **Resume verification separately from committing.** Read each member action's evidence and the recorded work-unit note. Preserve an existing commit choice, including per-action commits. Resume the first unverified action or final check; when the whole unit is already verified but uncommitted, inspect its current diff and evidence, then make the authorized commit at its recorded granularity without repeating unchanged checks. Under a per-action choice, retain broader integration checks as unfinished work until verified. A failed later action never erases earlier verified, uncommitted changes. A commit id alone never proves action completion.
- The sub-plan frontmatter carries only `exec_status` + `exec_runs` (append-only, newest last; the last entry is the current run).
- Before executing changed actions, reassess `references/design_check.md` applicability against the current EXEC_PLAN. A previous engineering-only exemption does not cover newly introduced experiment design or a heavy command; unchanged, previously checked design needs no repeat.
- On re-invoke, read the run dir and resume from the first unfinished step. For an awaiting STOP-line command, existing outputs alone do not establish success. Bind them to its exact command, code/review versions and attempt, inspect its exit result, verify the expected outputs and preserve the raw logs/results before finalization's done-criterion verification.
- **The executor acknowledges a launched attempt before marker removal.** Run `bash .agents/skills/star-plan-executor/scripts/launch_state.sh inspect --run wkdrs/<run>`. `waiting` retains the markers and returns to the existing wait; `exited` requires output verification against its stored argv, versions and expected paths. Save the verification result in an existing raw check log or another evidence file under the run; then call `acknowledge --run wkdrs/<run> --attempt <id> --evidence <verification-file> --verified-output <path>` (repeat the last option for every verified output). A zero exit requires all expected paths to exist and be explicitly verified; only after acknowledgment tick the Awaiting-user item (`- [ ]` → `- [x]`) with the receipt attempt and outputs, and verify the done-criterion. A nonzero exit is acknowledged with the failure evidence (verified-output options may be omitted), durably recorded as `failed`, and reopens or blocks the affected action; do not tick it as successful or set `done` from that exit. The helper appends and flushes an inspectable receipt containing the original command/version/attempt/PID/log/output/exit identity to the existing EXEC_LOG before removing matching markers; it never rewrites historical entries or changes a step status.
- **Repeat collection is idempotent.** A `star-launch-receipt` in EXEC_LOG is the durable acknowledgment. After interruption, `already_collected` from `inspect` or `acknowledge` reuses that receipt, finishes only its remaining marker cleanup, and resumes the unfinished status/criterion update without collecting or charging cost twice. Re-running acknowledgment for an older receipt never removes a newer attempt's markers. Legacy three-line PID/log/output markers, plain exit-code files, missing exits and mismatched IDs remain evidence, with command/version or outcome explicitly `unknown` until reconciled; do not delete or automatically upgrade them, infer success from a dead PID, or launch another attempt over them.
- A closed current run — its EXEC_LOG `status: done`, or a `reconstructed:` header — on a leaf whose `exec_status` is not `done` is a re-run, not a resume: plan fresh from Step 1 under a suffixed run name (the run-name rule where the run records are created), appended to `exec_runs`; the closed run stays as history.
- **A `tier=exec` delegate resumes the execute–verify loop and nothing else.** Dispatched once the plan is approved and EXEC_PLAN and EXEC_LOG are on disk, it picks up at the first unfinished step, works the loop exactly as the manifest writes it, and returns when the loop ends — it does not perform finalization or user-facing reporting; it still runs each assigned action check and returns its evidence. It may not edit EXEC_PLAN: a step it cannot do as written is marked `blocked` with the reason and returned rather than improvised, a STOP-line command goes into the log's awaiting-user area and it returns there too, and a change at the sub-plan's granularity goes to "Pending amendments" for the run that dispatched it to settle. That run re-reads the log when the delegate returns and carries on from there.
- **A branch or a worktree is found before the run dir.** A branch `<prefix>_<slug>*` matching the leaf, or a `worktree:` line in the run's records, is where that run lives — the base checkout showing the leaf unexecuted proves nothing (conventions §11.3). Follow `branch_rules.md`'s "Resume": what the switch waits on, why a worktree run never switches the invoking checkout, and that a recorded branch or tree gone from disk is a blocker to report, never silently rebuilt.
- **A review's findings reopen steps.** If the run dir holds a `CODE_REVIEW_<date>.md` carrying blocker or major findings the log does not record as settled, those come before anything else on re-invoke: reopen each step a finding lands in (status back to `in_progress`, the finding's id in its note), or append one remediation step to `EXEC_PLAN.md` where a finding spans several. Reuse and cite an existing specific, applicable remediation decision; otherwise settle the batch once with the plan decision, then run it through the execute–verify loop. A valid `auto=unattended` grant takes the recommended remediation batch only when it changes no research goal/scope, key input, §5 done-criterion, or approved cost and deletes or overwrites nothing; otherwise ask. An awaiting STOP-line command is handed back again only after that. A finding the user decides not to act on is recorded as settled in the log with that decision, so the next re-invoke leaves it alone.
- **A review's applied fixes are verified against the run.** Where the newest `CODE_REVIEW_<date>.md` records fixes as `applied` or `applied unasked` and the log holds no re-verification entry naming that review, map the touched files to the EXEC_PLAN actions that own them. Accept a prior action check when its exact command, raw result/artifact, and code version are inspectable and the fix cannot affect what it checked; otherwise re-run the narrow affected check. Always re-run checks after integration changes behavior, dependencies, or checked code. If the run had reached finalization, verify the done-criterion on the same basis rather than unconditionally repeating every test or costly command. Record the evidence and review name under the action it verifies. A failed check reopens its action as above. An awaiting STOP-line command is handed back again only after that, and the review step obtains a new review only when relevant code changes made the recorded review stale.
- **On an execution branch, the run ends at the merge authorization point.** When every action is `done`, the §5 done-criterion holds, and the newest review's blocker/major findings are settled, the one remaining action is the merge (conventions §11.4). An existing specific, applicable merge authorization is used without another question. Otherwise an ordinary run asks at every involve level; a valid `auto=unattended` grant takes only the clean reviewed squash merge and guarded empty-worktree cleanup without asking, as `branch_rules.md` enumerates. The token alone does not authorize conflict resolution, discard, overwrite, or deletion of the execution branch. Those decisions and what becomes of a worktree afterwards are all in its "The merge authorization point".
- The write-back applies once: rows marked `synced` (EXEC_PLAN) or checked off ("Pending amendments") are never re-applied; only unsynced, undecided pending rows are offered at finalization.
