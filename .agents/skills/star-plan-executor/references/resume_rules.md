# Resume Rules — a run already recorded is picked up, not planned again

Read at Step 0 where the digest gives this leaf a non-empty `exec_runs`, where a branch named for it exists, or where `wkdrs/<run>/` is already on disk. A leaf with none of the three is a fresh run and never reads this file.

- The sub-plan frontmatter carries only `exec_status` + `exec_runs` (append-only, newest last; the last entry is the current run).
- On re-invoke, read the run dir and resume from the first unfinished step. If STOP-line commands were awaiting and their outputs now exist, first bind each output to its exact recorded command and code version, then resume at Step 5's done-criterion verification; preserve the raw logs/results as evidence.
- **A `tier=exec` delegate resumes the execute–verify loop and nothing else.** Dispatched once the plan is approved and EXEC_PLAN and EXEC_LOG are on disk, it picks up at the first unfinished step, works the loop exactly as the manifest writes it, and returns when the loop ends — it does not perform Step 5 finalization or user-facing reporting; it still runs each assigned action check and returns its evidence. It may not edit EXEC_PLAN: a step it cannot do as written is marked `blocked` with the reason and returned rather than improvised, a STOP-line command goes into the log's awaiting-user area and it returns there too, and a change at the sub-plan's granularity goes to "Pending amendments" for the run that dispatched it to settle. That run re-reads the log when the delegate returns and carries on from there.
- **A branch or a worktree is found before the run dir.** A branch `<prefix>_<slug>*` matching the leaf, or a `worktree:` line in the run's records, is where that run lives — the base checkout showing the leaf unexecuted proves nothing (conventions §11.3). Follow `branch_rules.md`'s "Resume": what the switch waits on, why a worktree run never switches the invoking checkout, and that a recorded branch or tree gone from disk is a blocker to report, never silently rebuilt.
- **A review's findings reopen steps.** If the run dir holds a `CODE_REVIEW_<date>.md` carrying blocker or major findings the log does not record as settled, those come before anything else on re-invoke: reopen each step a finding lands in (status back to `in_progress`, the finding's id in its note), or append one remediation step to `EXEC_PLAN.md` where a finding spans several. Reuse and cite an existing specific, applicable remediation decision; otherwise settle the batch once with Step 3's plan decision, then run it through Step 4's execute–verify loop. A valid `auto=unattended` grant takes the recommended remediation batch only when it changes no research goal/scope, key input, §5 done-criterion, or approved cost and deletes or overwrites nothing; otherwise ask. An awaiting STOP-line command is handed back again only after that. A finding the user decides not to act on is recorded as settled in the log with that decision, so the next re-invoke leaves it alone.
- **A review's applied fixes are verified against the run.** Where the newest `CODE_REVIEW_<date>.md` records fixes as `applied` or `applied unasked` and the log holds no re-verification entry naming that review, map the touched files to their Step 4 actions. Accept a prior action check when its exact command, raw result/artifact, and code version are inspectable and the fix cannot affect what it checked; otherwise re-run the narrow affected check. Always re-run checks after integration changes behavior, dependencies, or checked code. If the run had reached Step 5, verify the done-criterion on the same basis rather than unconditionally repeating every test or costly command. Record the evidence and review name under the action it verifies. A failed check reopens its action as above. An awaiting STOP-line command is handed back again only after that, and Step 7 obtains a new review only when relevant code changes made the recorded review stale.
- **On an execution branch, the run ends at the merge authorization point.** When every action is `done`, the §5 done-criterion holds, and the newest review's blocker/major findings are settled, the one remaining action is the merge (conventions §11.4). An existing specific, applicable merge authorization is used without another question. Otherwise an ordinary run asks at every involve level; a valid `auto=unattended` grant takes only the clean reviewed squash merge and guarded empty-worktree cleanup without asking, as `branch_rules.md` enumerates. The token alone does not authorize conflict resolution, discard, overwrite, or deletion of the execution branch. Those decisions and what becomes of a worktree afterwards are all in its "The merge authorization point".
- The write-back applies once: rows marked `synced` (EXEC_PLAN) or checked off ("Pending amendments") are never re-applied; only unsynced, undecided pending rows are offered at Step 5.
