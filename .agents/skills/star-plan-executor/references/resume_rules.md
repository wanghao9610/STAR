# Resume Rules — a run already recorded is picked up, not planned again

Read at Step 0 where the digest gives this leaf a non-empty `exec_runs`, where a branch named for it exists, or where `wkdrs/<run>/` is already on disk. A leaf with none of the three is a fresh run and never reads this file.

- The sub-plan frontmatter carries only `exec_status` + `exec_runs` (append-only, newest last; the last entry is the current run).
- On re-invoke, read the run dir and resume from the first unfinished step. If STOP-line commands were awaiting and their outputs now exist, resume at done-criterion verification.
- **A `tier=exec` delegate resumes the execute–verify loop and nothing else.** Dispatched once the plan is approved and EXEC_PLAN and EXEC_LOG are on disk, it picks up at the first unfinished step, works the loop exactly as the manifest writes it, and returns when the loop ends — it never verifies the done-criterion, syncs amendments, or reports. It may not edit EXEC_PLAN: a step it cannot do as written is marked `blocked` with the reason and returned rather than improvised, a STOP-line command goes into the log's awaiting-user area and it returns there too, and a change at the sub-plan's granularity goes to "Pending amendments" for the run that dispatched it to settle. That run re-reads the log when the delegate returns and carries on from there.
- **A branch or a worktree is found before the run dir.** A branch `<prefix>_<slug>*` matching the leaf, or a `worktree:` line in the run's records, is where that run lives — the base checkout showing the leaf unexecuted proves nothing (conventions §11.3). Follow `branch_rules.md`'s "Resume": what the switch waits on, why a worktree run never switches the invoking checkout, and that a recorded branch or tree gone from disk is a blocker to report, never silently rebuilt.
- **A review's findings reopen steps.** If the run dir holds a `CODE_REVIEW_<date>.md` carrying blocker or major findings the log does not record as settled, those come before anything else on re-invoke: reopen each step a finding lands in (status back to `in_progress`, the finding's id in its note), or append one remediation step to `EXEC_PLAN.md` where a finding spans several; settle the batch once, the way Step 4 settles the plan, then run it through Step 5's execute–verify loop. A valid `auto=unattended` grant takes the recommended remediation batch when it changes no plan scope and deletes nothing; otherwise ask. An awaiting STOP-line command is handed back again only after that. A finding the user decides not to act on is recorded as settled in the log with that decision, so the next re-invoke leaves it alone.
- **On an execution branch, the run ends at the merge confirmation point.** When every step is `done`, the §5 done-criterion holds, and the newest review's blocker/major findings are settled, the one remaining action is the merge (conventions §11.4). Ordinary runs ask whatever the involve level; a valid `auto=unattended` grant takes the clean reviewed merge and guarded worktree cleanup without asking, as `branch_rules.md` enumerates. That decision, the never-automatic discard path, and what becomes of a worktree afterwards are all in its "The merge confirmation point".
- The write-back applies once: rows marked `synced` (EXEC_PLAN) or checked off ("Pending amendments") are never re-applied; unsynced pending rows are re-offered at Step 6.
