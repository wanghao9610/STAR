# 计划同步回写规则 — 让子计划与实际执行保持一致

当执行确实偏离子计划时,先取得用户授权,再把偏差**写回子计划**(`metds/plans/<prefix>_<slug>_plan.md`),让用户日后重读计划时看到的就是实际执行的内容。对话或运行记录中已有明确、适用的指示或决定,就构成授权;引用并沿用它,不重复询问。泛泛的"实现这个计划"不授权改变研究目标、范围或完成判据。本文件定义:什么算偏差、变更项形式、写回流程,以及**不许**用它的边界。

## 实质性(要同步) vs 细节(不同步)

EXEC_PLAN 本来就*应该*比子计划更具体——"更精确"**不是**偏差,只有一个例外(**ENRICHED**,见下)。只同步**实质性**偏差,以子计划自身的粒度判断:

- 某个 §3 步骤被**新增、删除、替换或重排**;
- 某项 §2 输入/依赖被证实**有误或缺失**(实际用的数据集/权重/模块与写的不同);
- 某项 §4 产出物**路径或形态变了**;
- §5 完成判据被**调整**(阈值、指标或检查方式);
- 子计划未写明的某个值经**执行敲定**,且某份方法文档会引用它(**ENRICHED**,见下)。

不算实质性:一个 §3 步骤内部更细的子步骤;没有任何方法文档会引用的实现选择、命令与路径。拿不准时当作细节。

## ENRICHED:执行敲定、且文档会引用的值

子计划同时也是方法文档编译的**来源**——`star-metd-summarize` 只读计划、别的什么都不读。子计划没写明、执行时定了下来、而某个 `metds/*.md` 章节会引用的值,因此不是细节:不回写,它就会在那份文档里变成永久的 `TBD`。

在范围内——该值必须是某个文档章节会引用的,且该行必须写明那个章节:

| 执行敲定的值 | 被谁引用 |
|---|---|
| 超参——lr、schedule、batch size、epochs | `training.md` §3 |
| 实际使用的初始化 / backbone | `training.md` §2 |
| 复现入口——读者会重跑的命令与 config | `training.md` §5、`evaluation.md` §5 |
| 某个组件行为所依赖的关键 config | `framework.md` §2 |
| 实际采用的 split / 预处理选择 | `dataset.md` §3 |
| §5 写明了 seed / 重复策略时，实际跑的那些 seed 值 | `training.md` §3 |

不在范围内:任何文档都不引用的东西——内部开关、临时路径、环境细节(那些归 EXEC_LOG 与 `freeze.txt`)——以及计划已经写明的值(改动那种值是 MODIFIED,不是 ENRICHED)。**如果你说不出哪个文档章节会引用它,它就是细节。**

## 变更项形式

每条偏差一行,类型仿 OpenSpec 的变更项:

- **ADDED** —— 子计划里没有:`ADDED §3.5:"<新步骤>" —— 原因:<…>`
- **MODIFIED** —— 做法与写的不同:`MODIFIED §3.2:"<原文>" → "<新做法>" —— 原因:<…>`
- **REMOVED** —— 写了但不会做:`REMOVED §3.4 —— 原因:<已过时 / 被 … 覆盖>`
- **ENRICHED** —— 子计划没写,执行敲定了它:`ENRICHED §3.2:lr 未写明 → 1e-4 —— 被引用:training.md §3`

规划时发现的行进 EXEC_PLAN 的"与子计划的偏差"表;执行中冒出来的行进 EXEC_LOG 的"待同步修正"。

## 两个同步点,每项授权只取一次

1. **执行前**。规划时已知的偏差逐字列入 EXEC_PLAN。已有用户指示明确选定这些改动时,记录其来源并直接同步,不再问一遍。否则只呈现一次并取得批准,再于执行前写回获批行。合法的 `auto=unattended` 只有在一条推荐战术行的实质不改变研究目标/范围、关键输入、§5 完成判据和已批成本时才可采用；节号或 ENRICHED 标签绝不会把这些变化变成常规细节。
2. **收尾**。执行中冒出的偏差累积在"待同步修正"——绝不为它们中断执行。收尾时先沿用已有的明确适用决定;仍未决定的行**一次性**呈现(*全部同步 / 逐条挑 / 不同步*),只写回获授权的行。若本轮弃跑或被阻塞,未同步且未决定的行留在日志里,下次续跑收尾时再提出;已经批准或跳过的行绝不重复询问。

## 写回流程

对每条获授权的行:

1. **先重读子计划**。若其 §2–§5 在本轮开始后已被改动(用户手改、重新拆解),保留这些编辑。只有改动互不重叠或文字在机械上等价、预期组合结果没有歧义、且本轮已有实现/整合授权时,才直接协调。若两边竞争,或需要在用户意图、研究做法、范围或验收之间取舍,就呈报冲突并询问;绝不盲目覆盖。单凭 `auto=unattended` token 不构成冲突消解授权。
2. **原地更新受影响的 §2–§5 段落**为确认后的内容;正文读起来必须是当前事实,而不是一块补丁。
3. **追加一条 `## Revision History` 条目**——与 `star-plan-reviser` 写入的是同一个只能追加的小节(文件末尾没有则创建;绝不改写既有条目)。每次同步一个 `###` 块,格式与 reviser 兼容:

   ```markdown
   ## Revision History

   ### <YYYY-MM-DD> — star-plan-executor · <model_id> (run: <prefix>_<slug>, 执行前 | 收尾)
   - MODIFIED §3.2:"<原文>" → "<新做法>" —— <原因>
   - ADDED §3.5:"<新步骤>" —— <原因>
   - ENRICHED §3.3:lr 未写明 → 1e-4 —— 被引用:training.md §3
   ```

4. **更新 frontmatter 的 `updated`**;frontmatter 里其他字段一概不碰。
5. **在来源处标记已同步**(EXEC_PLAN 的 `synced` 列 / EXEC_LOG 的勾选框)。标记过的行绝不二次应用。

日期统一取写入时的系统时钟(`date +%F`),标题与 frontmatter 更新使用同一个值;绝不从文字或模型上下文推断、编造日期。

## 边界:永远不同步的东西

- **§1 目标与范围、§6 局部风险**——目标级偏差意味着任务变了,而不是做法变了;那是重新拆解(`star-plan-decomposer`)的事,不是同步回写。
- **任何父计划**——父计划归 `star-plan-coach` / `star-plan-decomposer`(向上反馈)。
- **任何未经用户具体授权的研究范围、关键输入、已批成本或 §5 完成判据变化**——实现授权、节号、ENRICHED 标签与 `auto=unattended` 都不会把这些变化变成常规细节。得到具体授权时,在 Revision History 明记旧 → 新。若 §5 变化与根计划 §4 指标 / §5 kill-criteria 冲突,它就是计划级发现:记录、呈报、向上反馈,不要同步。
- **测量出来的结果**——ENRICHED 行携带的是执行*选定*的值(lr、backbone、split),绝不是它*测出*的值。分数归 `wkdrs/<run>/EXPT_ANALYSIS_<date>.md`;一份记录自己结果的计划,在所有由它编译出的文档里都会被读成设计意图。
- **事后审计与基于证据的修订**——评定一轮执行实际达成了什么、并据证据修订计划(含 §1/§6),是 `star-plan-reviser` 的职责;同步回写只负责在执行过程中让 §2–§5 与已获授权的执行现实保持一致。

§5 的同步回写必须在 Revision History 条目里明写旧 → 新,让"什么算完成"永远不会悄悄漂移。
