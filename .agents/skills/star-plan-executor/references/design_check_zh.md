# 算力前的设计检查

## 适用条件与委派

实现前阅读已写好的 EXEC_PLAN 和叶子计划。只要工作会报告支撑研究主张的实验结果，设定或改变指标、benchmark、数据划分或选择、影响评测的预处理、权重或其训练数据假设、seed／重复次数、baseline 或消融对比，或准备跨过 STOP line（重计算或高成本操作边界）的命令，就执行这项检查。已获授权的运行仍须检查。小实验和数据准备任务也可能符合条件，不能仅凭任务名称或规模豁免。

仅当记录的动作明确不涉及上述任何条件时才跳过，例如只修复打包问题、用导入测试验证且不影响实验的任务。在 EXEC_PLAN 中记录 `design check: not applicable` 和具体原因。信息缺失不能证明不适用：先查看相关计划内容，仍无法判断时执行检查并报告不确定性。动作自身的验证、代码审查和运行授权继续适用。恢复执行时，若变更的动作引入或改变上述条件，在执行前重新判断；已检查且未变化的设计无需重复检查。

适用时，在 EXEC_PLAN 中记录原因，并按共享规约 §6（范围与独立性）、§10.8（模型档位选择）和 §13（当前宿主的委派参数），请求 PLAN 档的一次独立阅读。交给审查者这份检查表、已写好的 EXEC_PLAN、叶子计划，以及根计划的 §4（指标与算力预算），不传入产出过程的对话。检查表语言与叶子 frontmatter 一致。审查者只读取这三份证据文件，返回下列条目，不写文件、不排序、不作决定、不运行命令。主代理重读每个 `fail` 所引的证据，修正授权范围内的执行计划缺陷，仅对尚未确定的研究范围、验收、关键输入或成本提问。没有获准使用的独立审查者时，本地检查一次并记录缺少独立视角。

## 检查表

对着实现开始前已经完成的 EXEC_PLAN 跑，不是对着子计划原文跑。根计划与叶子已经过各自的检查表（`star-plan-coach` 的 `plan_rubric.md`、`star-plan-decomposer` 的 `subplan_rubric.md`）；这里问的是页面上这次具体的 run 是否仍然满足它们，外加两件两张表都没覆盖的事。证据只有 EXEC_PLAN、叶子子计划、根计划 §4 三份文件。证据不在这三份里的条目一律 `unclear`，绝不 `pass`。

每条返回一个条目——`item`、`verdict: pass | fail | unclear`、`evidence`（引用的那一行，或"缺什么"的确切陈述）、`fix`——别的都不返回。不排序、不决定、不运行任何东西。

1. **这次 run 产出的是它那条主张需要的那个数字** —— 叶子的 `traces_to` 指向根计划 §4 的某条主张或某一节，而这里的某个动作会在 §4 为那条主张点名的 benchmark 上写出那条主张所依据的指标。产出别的指标，或在那条主张不使用的 benchmark 上产出对的指标，是算力花掉之前的一个 `fail`，而不是花掉之后的一行 `unmeasurable`。（`plan_rubric.md` 第 5 条，对着这次 run 重问一遍。）

2. **这次 run 报告的每个数字都写明了它的 split，且没有任何东西是在那个 split 上选出来的** —— 每个报告动作都写明它从哪个 split 报告，且这次 run 里没有任何 checkpoint、阈值或超参是在同一份数据上挑的。在报告数字的那个 split 上挑最好的那一轮，正是 `star-expt-analyst` 的泄漏清单事后会抓到的问题，代价是整轮 run。只写了报告用的 split、没写选择用的 split，判 `unclear`，修法是加一行说明选择用的是哪个 split。

3. **评测 benchmark 不太可能落在 §2 点名的那批权重的预训练语料里** —— 叶子的 §2 点名 `inits/` 下的权重；根计划 §4 点名这次 run 报告的 benchmark。说明这批权重训练所用的语料在这两份计划里有没有写，以及它是否可能包含那份评测数据。语料没写不算 `pass`，判 `unclear`，修法是在 §2 加一句说明这批权重见过什么。写下 `unknown` 是可以接受的回答；不问这个问题不是。

4. **§5 写明的 seed 或重复次数，就是这次 run 实际发起的次数** —— §5 写明了它那个阈值在什么 seed / 重复策略下测量，或明确接受单 seed。数一下 EXEC_PLAN 的各个动作实际发起了几个配置。§5 要求 ≥N 个 seed 而 EXEC_PLAN 只发起一个，判 `fail`：一次永远产不出它所点名证据的 run，不可能达成那条判据。以指标为判据的 §5 根本没写策略，那是 `subplan_rubric.md` 第 6 条的 `fail`，不是这次 run 该悄悄替它解决的事。

5. **这次 run 对比的每一臂拿到的预算是可比的** —— EXEC_PLAN 若同时发起 baseline 与本方法，或两个消融变体，说明各自做了多少搜索：试了几格，或 `默认值，未搜索`。投入不等本身不判 `fail`；投入没写才判 `fail`，因为这样产出的对比事后无从辩护。引用已发表的数字而非自己复现的，只要计划写明了出处就判 `pass`。（`plan_rubric.md` 第 7 条，改成可以数的形式。）

6. **消融的某一臂与其参照之间，只在那条主张点名的那个部件上不同** —— 对这次 run 相对某个参照发起的每个变体，列出两份配置之间有差异的字段。差异多于一个、而主张又把差值归因于其中之一，判 `fail`：这样产出的表格，其表题声称隔离的部件其实没被隔离。EXEC_PLAN 记录的配置不足以回答时判 `unclear`，修法是在动作里点名这两份配置。

7. **跨过红线的东西写明了成本，而计划付得起** —— 每个交回用户的动作都带着 GPU×小时或调用次数与花费，且根计划 §4 的算力预算是写明的。计划付不起的成本，是留给用户的一个决定，而不是事后成本表上的一个意外。

这项检查报告执行设计的证据，不重新选择研究问题或调整已经定下的 §5 阈值。`unclear` 条目写明缺少什么证据，不能凭假设判定设计通过。
