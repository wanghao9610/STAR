# 续跑规则——已有记录的运行是接着跑,不是重新规划

在 Step 0 读:摘要给这片叶子的 `exec_runs` 非空、存在以它命名的分支、或 `wkdrs/<run>/` 已经在磁盘上,三者任一即读此文件。三者都没有的叶子是全新运行,从不读它。

- 子计划 frontmatter 只带 `exec_status` + `exec_runs`(只追加,最新的在最后;最后一项是当前 run)。
- 再次调用时读 run 目录,从第一个未完成步续跑。若之前有红线命令待执行、现在其产出已存在,先把每份产出绑定到记录中的确切命令与代码版本,保留原始日志/结果作为证据,再从 Step 5 的完成判据验证处续起。
- **带 `tier=exec` 的受托者只续跑执行—验证循环,别的都不做。** 它是在计划获批、EXEC_PLAN 与 EXEC_LOG 已落盘之后派出来的:从第一个未完成步接手,完全照 skill 说明文件写的那样把这个循环跑完,循环一结束就返回——它不执行 Step 5 的最终收尾或面向用户的报告，但仍运行分配给自己的 action 检查并返回证据。它不得修改 EXEC_PLAN:照原样做不了的步骤标 `blocked` 并写明原因后返回,绝不自行发挥;红线命令写进日志的待用户区后同样返回;在子计划粒度上改了方法的,记进"待同步修正"交给派它出来的那次运行去定。那次运行在受托者返回后重读日志,从那里接着走。
- **先找分支或 worktree,再找 run 目录。** 与该叶子对应的 `<prefix>_<slug>*` 分支、或运行记录里的 `worktree:` 一行,就是那次运行所在的地方——基础分支上的 checkout 显示这片叶子没执行过,说明不了任何事(规约 §11.3)。照 `branch_rules_zh.md` 的"续跑（Step 0）"走:切换前怎样保护用户改动、进了 worktree 的 run 为何绝不切换发起它的 checkout、以及记录里的分支或树在磁盘上没了是要上报的 blocker,绝不悄悄重建。
- **审查发现会重开步骤。** 若 run 目录里有 `CODE_REVIEW_<date>.md`,且它带的 blocker/major 发现没有在日志里记为已处理,再次调用时它们排在一切之前:把每条发现落在的 action 重开(状态回到 `in_progress`,备注里写上该发现的编号),一条发现跨多项时改为在 `EXEC_PLAN.md` 追加一个补救 action。已有明确、适用的补救决定时引用并沿用;否则像 Step 3 的计划决定那样整批决定一次,然后走 Step 4 的执行—验证循环。合法的 `auto=unattended` 只有在补救不改变研究目标/范围、关键输入、§5 完成判据或已批成本,且不删除或覆盖内容时才采用推荐整批;否则照问。待跑的红线命令要等这之后才再次交回。用户决定不处理的发现,连同这个决定一起在日志里记为已处理,下次再调用就不再重开它。
- **审查应用的修复要对照本轮核验。** 最新的 `CODE_REVIEW_<date>.md` 把修复记为 `applied` 或 `applied unasked`、而日志里没有点名这份审查的复验条目时,把被触及的文件映射到 Step 4 的 action。原 action 检查的确切命令、原始结果/产物、代码版本可核查,且修复不可能影响其所检内容时,可以沿用;否则重跑最窄的受影响检查。整合改变了行为、依赖或被检代码后始终重跑受影响检查。本轮已走到 Step 5 时,按同样原则核验完成判据,而不是无条件重复每项测试或昂贵命令。把证据和审查名记进 `EXEC_LOG.md` 对应 action。检查失败就按上面方式重开。待跑的红线命令要等这之后才再次交回,Step 7 仅在相关代码改变使原审查过期时取得新审查。
- **在执行分支上,这轮工作终于合并授权点。** 每个 action 都 `done`、§5 完成判据成立、最新审查的 blocker/major 都已处理时,剩下的唯一动作就是合并(规约 §11.4)。已有明确、适用的合并授权时直接沿用,不重复询问。否则普通运行在任何参与度档位都问;合法的 `auto=unattended` 只按 `branch_rules_zh.md` 逐项列出的守卫,直接完成审查干净后的 squash 合并与空 worktree 清理。单凭该 token 不授权解决冲突、弃用、覆盖或删除执行分支。这些决定、以及事后那棵树怎么了结,都在它的"合并授权点"里。
- 同步回写只生效一次:标了 `synced` 的行(EXEC_PLAN)和勾掉的行("待同步修正")绝不二次应用;只有未同步且未决定的待定行才在 Step 5 再次提出。
