# 续跑规则——已有记录的运行是接着跑,不是重新规划

在 Step 0 读:摘要给这片叶子的 `exec_runs` 非空、存在以它命名的分支、或 `wkdrs/<run>/` 已经在磁盘上,三者任一即读此文件。三者都没有的叶子是全新运行,从不读它。

- 子计划 frontmatter 只带 `exec_status` + `exec_runs`(只追加,最新的在最后;最后一项是当前 run)。
- 再次调用时读 run 目录,从第一个未完成步续跑。若之前有红线命令待执行、现在其产出已存在,则从完成判据验证处续起。
- **先找分支或 worktree,再找 run 目录。** 与该叶子对应的 `<prefix>_<slug>*` 分支、或运行记录里的 `worktree:` 一行,就是那次运行所在的地方——基础分支上的 checkout 显示这片叶子没执行过,说明不了任何事(规约 §11.3)。照 `branch_rules_zh.md` 的"续跑(Step 7)"走:切换前要等什么、进了 worktree 的 run 为何绝不切换发起它的 checkout、以及记录里的分支或树在磁盘上没了是要上报的 blocker,绝不悄悄重建。
- **审查发现会重开步骤。** 若 run 目录里有 `CODE_REVIEW_<date>.md`,且它带的 blocker/major 发现没有在日志里记为已处理,再次调用时它们排在一切之前:把每条发现落在的步骤重开(状态回到 `in_progress`,备注里写上该发现的编号),一条发现跨多步时改为在 `EXEC_PLAN.md` 追加一个补救步骤;像 Step 4 确认计划那样整批确认一次;然后走 Step 5 的执行—验证循环。待跑的红线命令要等这之后才再次交回。用户决定不处理的发现,连同这个决定一起在日志里记为已处理,下次再调用就不再重开它。
- **在执行分支上,这轮工作终于合并确认点。** 每一步都 `done`、§5 完成判据成立、最新审查的 blocker/major 都已处理时,剩下的唯一动作就是合并(规约 §11.4)——任何参与度档位都要问。那道问题、弃用路径、以及事后那棵树怎么了结,都在 `branch_rules_zh.md` 的"合并确认点(Step 7)"里。
- 同步回写只生效一次:标了 `synced` 的行(EXEC_PLAN)和勾掉的行("待同步修正")绝不二次应用;未同步的待定行在 Step 6 再次提出。
