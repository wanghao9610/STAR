# 朝目标自动推进工作流

> 本文件是 [`star-auto.md`](star-auto.md) 的中文对照版。运行时以英文原文件为准。

用户敲下了 `star-auto`——这次调用运行的就是本文件。敲下它即规约 §10.7 所定义的自动授权：本次运行追逐目标期间，每个下一步动作点名的 skill 都可以直接启动，包括只许显式调用的那七个；备好的红线命令也可以直接启动而非交回。`involve=low` 时，同一份明确授权还覆盖下文列出的 executor 链本地实现、机械审查修复与 Git 生命周期动作；除此以外，被启动的运行仍与用户亲手点名时完全一致。

调用形状：`star-auto <目标> [stop=<停止线>] [involve=<档位>]`。

## 解析调用

- 先剥掉 `involve=<档位>`，只取停止线文本之外的——`stop=` 之前的，或整个调用末尾的那个 token；停止线里出现的同样字样是停止线文字，不是 token（规约 §7.7）。什么都没设档位时——没有 token、`.env` 里也没有 `INVOLVE`——本次运行解析为 `low` 而非 `medium`：自主运行对自己的裁量题取标注的推荐项并逐条记录（§7.8）。`low` 时，本次调用本身预先批准 executor 推荐的执行计划、按路径暂存与提交、创建执行分支或 worktree、不删除内容且不改变行为的审查修复、审查干净后的 squash 合并，以及仅在持久产物已迁出且 `git status --porcelain` 为空时移除 worktree。这些动作不发授权问题，全部留记录。需要删除内容的审查修复跳过并转交，不自行猜。合并后的执行分支默认保留且不发问，避免无人值守清理依赖强制删除。这项例外通过内部 token `auto=unattended` 传给 executor 与 code reviewer；它不属于用户调用格式。
- 再剥 `stop=`：从这个 token 起到剩余文本末尾的全部内容就是停止线，用户自己的话写的自然语言——`stop=any single training over 4 hours, or any paid API call`、`stop=用卡超过 2 张就停`（中英皆可，混写也行）。**给了**，它就是本次运行不得越过的线：启动一条备好的命令之前，先陈述其预期开销并逐条对照——越线的、或无法对照判断的，照 §2 原样打印交回。**没给**，本次运行不设上限：备好的红线命令自主启动，以完成目标为先（§2 的唯一例外）。无论哪种，每次启动都连同陈述的开销记入决策记录。除上面的干净 worktree 移除外，授权与停止线都不覆盖删除、覆盖、`sudo`、系统级或驱动安装、历史改写、强制 Git、`push`、丢弃未合并工作或解决合并冲突——遇到这些就停止并报告，不自行猜过去。
- 剩下的就是目标。没有目标——问用户要；绝不从仓库里替用户猜一个。

## 循环之前

一次 grep 读出 `.env` 的 `STAR_LANG`、`INVOLVE` 和三个模型键（§7.6、§7.7、§10.8），把每个选中的档位条目拆成模型与可选的 `@<深度>`；这个宿主能指定受托者用哪个模型时，再用会话上下文里那条溯源提示给出的解析命令读一次本会话正在跑的模型（§8），下面每次启动才能判断本档是否要求不同模型或宿主支持的逐次深度。把目标变成运行可查验的判据——某个叶子要到达的 `exec_status`、必须存在的文件、报告里要出现的指标——开跑第一行写明判据、停止线（或说明没设）和解析出的档位。变不成判据的目标，先问清，不追。

## 循环

1. 磁盘上的启动标记还在、退出文件却没出现时——本次调用留下的，或上一次留下的——先按下文「等待已启动的命令」续上等待；状态检查等退出事件之后再跑。标记旁边已经有退出文件时，那就是退出事件：读一次日志尾部，收取交接点名的输出，删掉这对标记，再按第 2 步红线命令那一条启动 executor。否则经宿主原生 skill 机制运行 `star-flow-status`，取它唯一的下一步动作。不推进目标判据的动作不取：一行说明后留给以后的调用，改取推进判据的那个下一步——状态报告列出的欠账里，按它排欠账的顺序第一条与目标相关的；没有就取目标自己的叶子，或它第一个未满足的依赖，前提是状态的「下一个可执行叶子」规则会接纳它。
2. 启动被点名的那个：
   - 属于 agent 可拾起的八个——走宿主原生机制，完全按 §10.2–10.6 执行，并把本次运行解析出的档位以 `involve=` token 附在调用上：每次被启动的运行各自解析档位（§7.7），不带 token 的启动会退回 `.env`，而不是本次运行的默认值。点名的是 `star-plan-executor` 或 `star-code-reviewer` 且档位为 `low` 时，再附上 `auto=unattended`；该 token 传递本次调用的授权，skill 在解析目标或描述前先剥掉它。
   - 属于只许显式调用的七个——授权覆盖它：先声明一行（匹配上了什么、取了哪个目标），然后派一个子代理完整读取该 skill 在本宿主的 `SKILL.md` 并遵循它，本次运行解析出的档位以同一个 `involve=` token 写进交办说明；结束时在决策记录里留一行，`匹配到什么 → 跑了什么 → 写了哪些文件`（§10.5）。
   - 一条备好的红线命令——先按上面的停止线规则判断。可以启动时，按下文「等待已启动的命令」启动并记录（脱离会话、写下标记、等在退出事件上而不是靠刷新）。命令退出后，收取交接点名的输出，再启动 `star-plan-executor <叶子>`，带上与上面第一条相同的 `involve=` token，`low` 时也带上同样的 `auto=unattended`：它的续跑规则把这份输出绑定到记录在案的命令、勾掉那条待用户项，并在它的 Step 5 查验判据。然后回到第 4 步，接着跑那次运行点名的下一步。这样等不了的命令（本地没有可守的进程、也没有它的进展会触碰的文件）就结束本次运行，报告写明在等什么。守卫因审查缺失或过期而拒掉的启动不算失败的动作：对那个 run 跑 `star-code-reviewer` 就是下一步，审查不再留有未解决的 blocker 或 major 问题之后，启动才跟上。被用户的停止线拦下时，打印命令、停下、报告。
   - **这个宿主能指定受托者使用的模型或思考深度时**，上面每一次启动都应用该宿主为所属档位提供的控制（§10.8），具体机制由该宿主自己的包装文件说明，交办说明在 `involve=` token 旁带上 `tier=<档位名>`，`STAR_LANG` 为空时再用一行写明对话语言；决策记录随每次启动写明档位、实际模型，以及请求的深度或 `default`。
3. 目标没定死就列出候选并等待（§5.2、§10.3），一次启动一个工作单元（§10.4）。`low` 时，`auto=unattended` 覆盖的动作按上面的守卫条件直接执行，不发问。其余必问确认点照问照等（§7.2）；没有人能回答时——headless 运行——就停在那里报告，不替用户假设。被启动的运行递回来的问题同样分流：该档位不问的裁量题取推荐项并记录；歧义或超出无人值守授权的动作交给用户。问题答复之后，在同一目标上再次启动同一个 skill，把问题和答复一并带上；能从磁盘续跑的 skill 会从停下的地方接着做。
4. 每次运行结束后，接着跑它点名的下一步——在本授权之下，那七个与那八个同样照跑（§10.6）——没有点名时，重跑 `star-flow-status`。
5. 失败过的动作不在同一目标上重试。失败换来的转交——一次修订、一次修复——本身就是下一步动作，跑一次；它也失败时，停下报告。

## 等待已启动的命令

等待由事件驱动：命令退出时运行才回来，不是按时钟回来。靠刷新做监控——反复读日志、重跑状态 skill、隔一会儿来一次 watch 看看进展——正是本节要杜绝的：每次刷新都花掉完整的一轮模型调用，一次训练能熬过几千轮。

- **后台脱离启动，留下标记。** 命令放进后台、不随会话退出，并包一层让退出码落进文件——`rm -f wkdrs/<run>/.await.exit; nohup bash -c '<命令>; echo $? > wkdrs/<run>/.await.exit' > <日志> 2>&1 &`，开头的 `rm` 清掉上一次启动留下的退出文件——日志放在该运行 `wkdrs/<run>/` 下（交接里已写的重定向照用），同一条 shell 调用里写下标记 `wkdrs/<run>/.await`：第 1 行进程号，第 2 行日志路径，第 3 行交接点名要收取的输出。等待盯的是退出文件而不是进程号：沙箱化的宿主常常无权对不是自己启动的进程做 `kill -0` 或 `ps`——那种拒绝看起来就像进程退出了——而文件在任何沙箱里都读得到。这对标记文件是本命令自己的启动状态——既不是计划也不是报告——等待结束时一并删除。
- **在 shell 里守住这一轮。** 宿主的 shell 自己会通报脱离命令结束的（后台调用退出即有通知），就走那个机制启动，由通知交还回合。其余宿主用一条阻塞的 shell 调用等——睡眠和复查都在 shell 里循环，循环不花 token：

  ```bash
  run=wkdrs/<run>; log=$(sed -n 2p "$run/.await")
  deadline=$((SECONDS + 550))    # 不超出宿主单次调用的时限
  while [ ! -f "$run/.await.exit" ] && (( SECONDS < deadline )); do sleep 20; done
  if [ -f "$run/.await.exit" ]; then echo "exited $(cat "$run/.await.exit")"
  else echo "running — 日志最后写入 $(date -r "$log" '+%H:%M:%S' 2>/dev/null || echo '（还没有日志）')"; fi
  ```

  返回 `running` 就原样再发同一条调用，中间什么都不做——不读日志、不跑状态检查、不 watch，至多一行文字。返回 `exited` 才结束等待：读一次日志尾部，收取交接点名的输出，删掉这对标记。退出文件迟迟不出现、日志又停滞很久，这一种情况才轮到进程号来裁——宿主连这一探都不许时，就以日志的沉默为准，报告为停滞，绝不当成正常退出。
- **停滞也是事件。** `running` 行带着日志的最后写入时间；只有这个时间停住不动、超出命令自身记录节奏的合理范围，或者返回 `exited`，才做一次诊断性阅读——`star-expt-analyst watch` 就是这种诊断的形状。绝不按定时器跑，绝不为"看一眼"而跑。
- **跨调用。** 两次调用之间只有磁盘上的东西延续——而标记就在磁盘上。新调用发现 `.await` 还在、旁边却没有 `.await.exit`，就直接续上这里的等待（第 1 步）；外层反复重新驱动本命令的驱动器，每次重驱只花一轮，而不是一整趟监控。两个文件都在时，就把这对标记当作一次没被等到的退出事件，照样收取（第 1 步）。

## 何处结束

在下列第一个到达处报告并停止：目标判据通过；无人值守授权之外的必问问题无人可答；命令越过用户的停止线，或已启动的命令等不了；受守卫的 Git 动作遇到脏工作树、冲突或其他前置条件失败；一整轮——一次状态检查加上它引出的那个动作，问题答复后的再次启动也算在内——既没写任何文件，也没改动任何状态字段（计划的 `status` 或 `exec_status`、日志里的一步、一个复选框）；第 5 条走投无路。最终回复写明跑了什么、每次运行写了哪些文件、目标判据的结果，以及——中途停下时——正在等待的确切命令、问题或失败守卫。两次调用之间什么都不延续：重敲这条命令就从各次运行留下的树状态续起——还活着的启动标记也在内——停止线以新调用里写的为准。

## 本命令绝不做的事

它启动 skill、启动它们备好的命令，并在 `low` 时只传递上面逐项列出的 executor 链授权。它自己不写计划、不写报告、不写代码——所有产出都来自它启动的运行。它绝不削弱 `star_commit_guard.sh`。一次调用一个目标；下一个目标是下一次调用。
