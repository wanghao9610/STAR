# Drive the workflow toward a goal

Use this procedure when the user requests `star-auto` with a stated goal. Within that request, conventions §10.7 covers starting the skills needed for the goal, including the seven explicit-only skills, and prepared STOP-line launches that meet the conditions below. At `involve=low`, the requested workflow also includes the executor chain's routine local implementation, mechanical review fixes, and Git lifecycle described below. Each started run keeps its skill's scope and artifact ownership, the user's limits, and the host's permission requirements.

Invocation shape: `star-auto <goal> [stop=<stop line>] [involve=<level>]`.

## Parse the invocation

- Strip `involve=<level>` first, taken from outside the stop text — before `stop=`, or as the invocation's final token; the same words inside the stop line are stop-line text, not the token (conventions §7.7). When nothing sets a level — no token, no `INVOLVE` in `.env` — this run resolves to `low`, not `medium`: it takes the marked recommendation on routine judgment calls and logs each (§7.8). At `low`, the requested workflow includes the executor's recommended in-scope plan, explicit-path staging and commits, execution-branch or worktree creation, behavior-preserving review fixes that delete nothing, a clean reviewed squash merge, and removal of a worktree only after its durable artifacts have moved out and `git status --porcelain` is empty. Reuse that workflow decision and log each operation; obtain any approval the host separately requires. Review fixes that require deletion are skipped and routed. Retain the merged execution branch. Pass the internal `auto=unattended` token to the executor and code reviewer with the originating user request, goal and limits in the dispatch brief or run record (conventions §10.7); the token only carries that existing scope and is not part of the user-facing invocation shape.
- Then strip `stop=`: everything from that token to the end of what remains is the stop line, natural language in the user's own words — `stop=any single training over 4 hours, or any paid API call`, `stop=用卡超过 2 张就停` (either language, or both at once). **Given**, it is the line this run must not cross: before launching a prepared command, state its expected cost and judge it against each condition — a command that crosses the line, or that cannot be judged against it, is printed and handed back exactly as §2 says. **Absent**, no additional workflow cost ceiling was set: prepared commands may launch within the goal after their resource scope and cost are assessed, their review is current, and host permission allows them (§2). Either way every launch is logged in the decisions record with its stated cost. Apart from the clean worktree removal above, neither the request nor any stop line covers deletion, overwrite, `sudo`, system or driver installation, history rewriting, forced Git, `push`, discarding unmerged work, or resolving a merge conflict — retain the state and report the missing specific authority.
- What remains is the goal. No goal — ask for one; never infer a goal from the repository.

## Before the loop

Read `STAR_LANG`, `INVOLVE` and the three model keys from `.env` in one grep (§7.6, §7.7, §10.8), splitting each selected tier entry into its model and optional `@<depth>`; and — where this harness can name the model a delegate runs on — read the model this session is running once through the resolver command the session context's provenance line supplies (§8), so each start below can tell whether its tier requires a different model or a supported per-dispatch depth. Turn the goal into a check the run can verify — the `exec_status` a leaf must reach, the file that must exist, the metric a report must show — and open with one line stating that check, the stop line (or that none was set), and the resolved involve level. A goal that cannot be turned into a check is asked about, not pursued.

## The loop

1. When a launch marker remains on disk — left by this invocation or an earlier one — run the metadata helper's `inspect` below before choosing another action. `waiting` resumes "Waiting on a launched command"; `exited` or `already_collected` starts the executor as step 2's STOP-line bullet says, with the markers retained for its acknowledgment. A legacy marker, plain exit code, or mismatched attempt requires explicit reconciliation: preserve the evidence and report the unknown command/version or exit identity. Otherwise run `star-flow-status` through the harness's native skill mechanism and take its single next action. An action that does not advance the goal's check is not taken: say so in one line, leave it for a later invocation, and take the next action that does — the first triggered follow-up line that bears on the goal, taken in status's order for outstanding follow-ups; else the goal's own leaf, or its first unmet dependency, when status's next-runnable-leaf rule would admit it.
2. Start what it names:
   - One of the eight the agent may pick up — the harness's native mechanism, exactly as §10.2–10.6 say, with this run's resolved level appended as an `involve=` token: each started run resolves its own level (§7.7), so a start that carries no token would fall back to `.env`, not to this run's default. When the named skill is `star-plan-executor` or `star-code-reviewer` and the resolved level is `low`, append `auto=unattended` too; that token transmits this invocation's grant and is stripped before the skill reads its target or description.
   - One of the seven explicit-only — the grant covers it: announce one line first (what matched, which target), then dispatch one subagent that reads that skill's harness-owned `SKILL.md` in full and follows it, this run's resolved level passed in the brief as the same `involve=` token; when it ends, one line in the decisions record, `what matched → what ran → what it wrote` (§10.5).
   - A prepared STOP-line command — apply the stop-line rule above. When it may launch, launch and log it as "Waiting on a launched command" below says (detached, marker written, the wait held on the exit event rather than on refreshes). Once it exits, read the log tail once and start `star-plan-executor <leaf>` with the attempt identity, unchanged markers, the same `involve=` token, and at `low` the same `auto=unattended`, as the first bullet above. The executor verifies the outputs against the recorded command and versions, durably acknowledges collection in EXEC_LOG before marker removal, ticks the awaiting item only on verified success, and verifies the criterion in its finalize step. A nonzero exit is collected as a failed result and routed under step 5; it never satisfies the criterion. Then continue at step 4 with the next action that run names. A command that cannot be waited on this way (no local process to hold, no file its progress would touch) ends the run, and the report names what it is waiting on. A launch the guard declines for a missing or stale review is not a failed action: `star-code-reviewer` on that run is the next action, and the launch follows a review that leaves no blocker or major finding unsettled. When the user's stop line stops the launch, print the command, stop, and report.
   - **Where the harness can name the model or thinking depth a delegate runs with**, every start above applies the controls that harness exposes for its tier (§10.8), that harness's own command wrapper saying how, and its brief carries `tier=<name>` beside the `involve=` token and, where `STAR_LANG` is empty, the dialogue language in one line; the decisions record names the tier, actual model, and requested depth or `default` with each start.
3. An unsettled target names the candidates and waits (§5.2, §10.3), and one unit of work runs per start (§10.4). At `low`, operations covered by the recorded user request follow the guarded behavior above; host-required approvals remain separate. Every other mandatory confirmation point still asks and waits (§7.2); where nobody can answer — a headless run — it stops there and reports rather than assumes. A question a started run hands back is triaged the same way: a routine judgment call the level delegates is settled with its marked recommendation and logged as the agent's decision, while ambiguity, missing authority or a host-required approval goes to the user. Once settled, start the same skill again on the same target with the decision and its source; a skill that resumes from disk picks up where it stopped.
4. After each run ends, take the next action it names — under this grant the seven are taken as the eight are (§10.6) — and where none is named, run `star-flow-status` again.
5. Classify a failed action from its actual result. A policy or permission refusal stops that action: report the reason and apply conventions §10.8's intervention rule before choosing any route. For an implementation failure, do not retry the same action on the same target. Its corrective routing — a reviser pass, a fix run — is a next action taken once; when it too fails, stop and report.

## Waiting on a launched command

The wait is event-driven: the run comes back when the command exits, not on a clock. Monitoring by refresh — re-reading the log, re-running the status skill, a watch pass to see how it is going — is what this section exists to prevent: every refresh spends a full model turn, and one training run outlives thousands of them.

- **Prepare identity before launching.** Use `.agents/skills/star-plan-executor/scripts/launch_state.sh` as `state` and invoke it with `bash`; the helper uses shell tools and needs no Python environment. The metadata helper never launches a command or grants launch authority. It requires an existing `wkdrs/<run>/EXEC_LOG.md`. Its `prepare` command stores exact command argv, explicit code and review versions, wrapper PID, raw log and every expected output, emits a unique attempt ID, and refuses any outstanding marker or exit file. Versions must identify the checked source and review, including relevant dirty changes; a date or `unrecorded` is insufficient. Keep the guarded `bash execs/scpts/<run>.sh` launch visible and subject to the same guard; do not hide it in the helper or evaluate a recorded command string. For example, after the applicable review/cost/permission checks, substitute the actual paths and recorded versions, then use:

  ```bash
  nohup bash -c '
    set +e
    state=$1; run=$2
    attempt=$(bash "$state" prepare --run "$run" --pid "$$" \
      --log "$run/launch.log" --output "$run/<expected-output>" \
      --code-version "$3" --review-version "$4" -- bash execs/scpts/<run>.sh) || exit $?
    bash execs/scpts/<run>.sh
    rc=$?
    bash "$state" exited --run "$run" --attempt "$attempt" --exit-code "$rc" || exit $?
    exit "$rc"
  ' star-launch "$state" "wkdrs/<run>" "<code-version>" "<review-version>" \
    >> "wkdrs/<run>/launch.log" 2>&1 &
  ```

  Repeat `--output` for every handoff output; retain any required handoff redirections without overwriting prior evidence. A launch-tool acknowledgment is not proof preparation succeeded: allow the detached wrapper to finish preparation, then call `inspect --run wkdrs/<run>` once to confirm its marker. If no marker appears, use that wrapper's own completion/error rather than declaring the command launched or starting another copy; an interrupted startup has an unknown outcome. `.await` keeps PID, log path, first output on its first three lines for existing readers; line four is JSON with complete launch identity. `.await.exit` is JSON with the matching attempt ID and exit code, written atomically even after a command failure. A stale or plain exit file cannot complete a new attempt. The helper serializes metadata through `.await.lock`; that file carries no progress facts. Markers remain until the executor appends and flushes its collection receipt to the existing EXEC_LOG, then removes only that attempt's markers. No launch clears an earlier attempt.
- **Hold the turn shell-side.** On a harness whose shell itself announces a detached command's completion, launch through that mechanism and let the announcement return the turn. Everywhere else, wait inside one blocking shell call — sleep and re-check in the shell, where iterations cost nothing:

  ```bash
  run=wkdrs/<run>; log=$(sed -n 2p "$run/.await")
  deadline=$((SECONDS + 550))    # stay inside the harness's per-call time limit
  while [ ! -f "$run/.await.exit" ] && (( SECONDS < deadline )); do sleep 20; done
  if [ -f "$run/.await.exit" ]; then bash "$state" inspect --run "$run"
  else echo "running — log last written $(date -r "$log" '+%H:%M:%S' 2>/dev/null || echo '(no log yet)')"; fi
  ```

  Keep the shell call within the current host's per-call maximum; reduce the example deadline when the host requires it. `running` re-issues the same call with nothing in between — no log read, no status pass, no watch, and no text beyond a note that it is still running. A matching `exited` ends the wait: read the log tail once and hand the retained markers to the executor for verification and acknowledgment. A helper identity error stops collection and preserves the evidence. A missing exit file with a long-stalled log is the one case the process id settles — and where the harness denies even that probe, report a stall or unknown outcome, never a clean exit.
- **A stall is an event too.** The `running` line carries the log's last write time; a diagnostic read — `star-expt-analyst watch` is its shape — happens only when that time stops moving for longer than the command's own logging rhythm makes plausible, or on `exited`. Never on a timer, never to check in.
- **Across invocations.** Nothing carries between invocations except what is on disk. Inspect any retained marker before waiting or collecting (step 1). A matching exit routes to the executor; an existing receipt routes to its idempotent acknowledgment, which finishes interrupted cleanup without collecting twice. Legacy PID/log/output markers and plain exit files retain their evidence and need explicit reconciliation; never invent a trustworthy command or version for them.

## Where it ends

Report and stop at the first of: the goal's check passes; a mandatory question outside the unattended grant has no one to answer it; a command crosses the user's stop line, or a launched one cannot be waited on; a guarded Git operation finds a dirty tree, a conflict, or another precondition failure; a full pass — one status pass and the action it led to, a restart after an answered question included — wrote no file and moved no status field (plan `status` or `exec_status`, a log step, a checkbox); step 5 runs out of moves. The final reply names what ran, what each run wrote, the goal check's result, and — when the run stopped short — the exact command, question, or failed guard it is waiting on. Nothing carries between invocations: re-typing the command resumes from the tree as the runs left it — a live launch marker included — and the stop line is read fresh from the new invocation.

## What this command never does

It starts skills, launches the commands they prepare, and at `low` transmits only the executor-chain grant enumerated above. It writes no plan, report, or code of its own — everything produced comes from the runs it starts. It never weakens `star_commit_guard.sh`. One goal per invocation; the next goal is the next invocation.
