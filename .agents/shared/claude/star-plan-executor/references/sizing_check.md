# Sizing Check — what a leaf that came out too big gets

Read at Step 1 only where a sizing signal fires on a fresh leaf; the signals themselves stay in SKILL.md. Nothing here is written to disk: the run either ends handing the split back, or continues as it stands.

The split preview goes in the text above the call: 2–5 cards, each a slug, a one-line objective, and the done-criterion that unit would own, then the execution order in one line. Name it a preview and say what that means — no file written, no prefix assigned, no `depends_on` drawn, and `star-plan-decomposer` still picks its own axis and confirms its own list. Its cut lines are the signals that fired (one unit per done-criterion, per STOP-line crossing, per kind of work), not a fresh axis analysis. Needing more than 5 cards is itself the finding — say so in a line instead of listing them. Then ask via AskUserQuestion: *split it first* (recommended once a strong signal fired) — the run ends here having written nothing, the command goes back as `star-plan-decomposer <leaf> <the preview in one clause>` with the sketch carried as a lead (conventions §7.12), and execution resumes at `star-plan-executor <the leaf it produces>` — or *execute it as it stands*, which costs: every STOP-line crossing stops and resumes the run, one `blocked` step holds up everything behind it, and a failure re-runs the leaf entire. Executing part of the leaf is not offered — narrowing the scope is a decision nobody made (conventions §10.4).

Where Step 1's executability item is already routing back to the decomposer, this rides in that question rather than following it. Record the verdict and the signals in `EXEC_LOG.md`'s "Notes / decisions" when Step 4 creates it (conventions §7.8), so a resume does not reopen it and a later reader knows the leaf was flagged and run anyway.
